# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Ce que c'est

Coach de fitness temps réel **dans le navigateur** (`web/static/app/`, joué sur iPad) : la caméra de l'appareil détecte la pose (MediaPipe Tasks Vision, sur l'appareil), l'application compte les répétitions, guide à la voix (annonces françaises pré-enregistrées), enregistre l'historique dans IndexedDB et fait progresser les objectifs. Site **purement statique**, déployé sur GitHub Pages ; aucun serveur. Des gestes (bras en croix, bras levés) pilotent la séance à trois mètres de l'écran.

Une version desktop Python (OpenCV, Flask, SQLite) a existé et a été **retirée** : son code reste au tag `derniere-version-desktop`. Un portage natif Swift est envisagé à long terme.

## Commandes

```bash
python -m scripts.servir_statique 8001   # serveur local sans cache ; sans argument, le port vient de `PORT` (entrée `statique-dev` de .claude/launch.json, en `autoPort`)
node scripts/tester.mjs                  # toutes les vérifications, ~5 s ; s'arrête au premier rouge
node scripts/tester.mjs ligues ressenti  # seulement ces tests-là
node scripts/tester.mjs --mettre-a-jour  # réécrire les réponses figées (changement VOULU et compris)
node scripts/lister_annonces.mjs         # réécrit audio/A_ENREGISTRER.md, la feuille de prise de son
python audio/nettoyer_sons.py            # audio/a_traiter/ -> web/static/sons/ (pydub + ffmpeg)
python video/illustrer.py video/a_traiter/curl.mp4 "Curl biceps droit" --miroir "Curl biceps gauche"
node video/illustrer_tout.mjs            # tout video/a_traiter/ : prise nommée comme sa vidéo (`squat_charge.mov`), côté opposé en miroir
```

**Vidéos des fiches** (`video/illustrer.py` → `web/static/videos/<fichier_video(exercice)>`) : détourée, redessinée en aplats, recadrée sur le corps, en boucle (raccord cherché entre deux silhouettes semblables, fondu), H.264 pour Safari. Le nom vient de `fichier_video` (`videos.js`), **appelé par node** : la règle reste en JS, et l'application relit la vidéo sous ce même nom. Le détourage croise deux méthodes qui se trompent en sens contraires — RobustVideoMatting (`video/modeles/`, empreinte SHA-256 vérifiée) voit le corps mais perd l'haltère ; la pièce vide du début de vidéo (trouvée seule : les images où RVM ne voit personne) voit l'haltère mais perd un t-shirt blanc devant un mur blanc. Tournage : caméra immobile, quelques secondes de pièce vide pour un exercice à haltère. **Une vidéo d'exercice se montre en miroir** : l'utilisateur se voit en miroir (caméra avant) et imite du même côté de l'écran, donc pour un exercice « droit » le membre qui travaille est à **droite** de l'image — en vue vraie, il imiterait avec l'autre bras et la détection, qui vérifie le bras droit, ne compterait rien. La prise est supposée en vue vraie (ce qu'enregistre l'iPad ; seul son aperçu est en miroir), le script la retourne, `--miroir` écrit la vue vraie pour le côté opposé. Ne pas activer « Caméra avant en miroir » : la vidéo serait retournée deux fois ; la planche de contrôle rappelle le sens à vérifier. Vidéos brutes, essais et modèle ne sont jamais versionnés (on y voit une personne chez elle).

Aucun linter. La CI (`.github/workflows/demo.yml`) lance `tester.mjs` puis publie `web/static` à chaque push sur `main` ou `travail` — une autre branche ne déploie rien, en silence. Une branche publiée doit aussi être autorisée par l'environnement `github-pages` (Settings > Environments), sans quoi son déploiement est refusé.

**Déroulé : on travaille sur `travail`, `main` est la version sûre.** Un seul site, le dernier push gagne : pousser `travail` la met en ligne, et l'utilisateur l'essaie en séance dans la web app de l'iPad (son stockage est séparé de Safari, la base y vit — l'essai ne peut pas se faire ailleurs). Validée, `travail` est fusionnée dans `main`. Si un essai casse l'application, on republie `main` (Actions > Demo > Run workflow). Ne rien pousser sur `main` qui n'ait été essayé, et ne pas pousser `travail` sans prévenir : c'est l'application de tous les jours qui change.

## Le principe : chaque règle n'existe qu'une fois

C'est la raison du retrait du desktop : chaque règle vivait en Python et en JS, et l'essentiel de l'énergie passait à les tenir d'accord. **Ne jamais réintroduire un jumeau d'une règle JS, dans aucun langage.** Un outil peut être écrit en Python tant qu'il n'applique aucune règle (`nettoyer_sons.py`, `empreinte_deploiement.py`, `servir_statique.py`) ; un outil qui *applique* une règle importe le module JS (d'où `lister_annonces.mjs` et `verifier_annonces.mjs`, qui ont besoin de `normaliser_nom`).

Les noms JS restent en **snake_case** (héritage du portage) : ne rien renommer, c'est aussi la carte du futur portage Swift.

## Tests

`scripts/tester.mjs` enchaîne :
- **`verifier_methodes.mjs`** : chaque `this.methode()` appelée existe, et les `<script type="module">` inline n'ont pas de faute de syntaxe (`node --check` ne lit que les `.js`, or le module de l'application fait trois mille lignes dans `app/index.html` — une faute y donne un écran blanc).
- **`sommaire.mjs`** (sans argument) : chaque page a un titre et une description pour le sommaire du site.
- **`suivi.mjs`** (sans argument) : la lecture des fiches de suivi (`suivi.js`) sur une fiche écrite dans le script, puis chaque fiche de `docs/exercices/` et le modèle du skill ont un titre et des cases.
- **`verifier_donnees.mjs`** : les JSON de `donnees/` se tiennent (voir *Données*), bornes de ligue (dix-huit, croissantes) et tables de variantes (retour, départ) comprises, et un barème pour tout mouvement compté (sans lui, l'application le jouerait hors moteur, en silence). C'est l'ancien rôle des validations au chargement, qui n'existent plus nulle part ailleurs.
- **`verifier_annonces.mjs`** : les tables du coach se tiennent (voir *Coach vocal*).
- **`verifier_instruments.mjs`** : chaque instrument du banc d'essai redit exactement le jeton de sa détection, et toute détection a son instrument.
- **`verifier_compteur.mjs`** : la position de départ déclarée d'un mouvement (`depart`), que les entrées figées, plus anciennes, ne portent pas.
- **`verifier_tentatives.mjs`** : quand une répétition refusée s'explique et avec quelle raison (hésitation, hors position, forme à la même image, départ), sur un instrument minimal écrit dans le script ; la persistance qui confirme un échec (une image isolée ne fait pas parler) ; et la composition de la voix par le lecteur.
- **`verifier_mise_en_place.mjs`** : l'ouverture d'une série comptée (immobile en position, « c'est parti », rien compté avant), que le rejeu des scénarios coupe. La durée attendue y est **écrite**, pas relue dans le moteur : relue, le test suivait la constante, et une durée mise à zéro passait inaperçue.
- **`verifier_cotes.mjs`** : un mouvement unilatéral du mauvais côté — le pied avant d'une fente, le compteur fantôme de l'autre côté (seul : on parle ; les deux bras ensemble : silence), l'échec du genou arrière qu'il fait taire, la planche latérale du mauvais côté.
- **`verifier_gestes.mjs`** : les gestes de contrôle de face et pas de dos (mains rapprochées vues de dos, nez deviné, allongé), et le délai d'affichage de l'anneau.
- **`verifier_migration.mjs`** : une base de version 1 ou 2 (et sa sauvegarde) arrive intacte en version courante — cas écrits à la main : `comparer_historique` ne rejoue que des écritures de la version courante.
- **`verifier_familles.mjs`** : le départ selon la note et la règle du matériel, sur des tables minimales écrites dans le script (un réglage de barème ne doit pas faire rougir une règle).
- **`verifier_createurs.mjs`** : les règles des créateurs de séances et de programmes, sur des tables écrites dans le script — catégories d'un mouvement, zone et matériel d'un programme, séances et programmes perso (un autre profil n'en voit rien, un renommage emporte les programmes qui citent la séance), entrelacement recalculé, exigences préremplies, refus d'un programme, promotion d'une création perso.
- **`verifier_simulation.mjs`** : le simulateur tourne sur les données déployées pour six profils de matériel, le départ de tous les exercices et le parcours des chaînes de variantes à deux notes, de façon déterministe ; et le moteur y tient ce qui n'est pas affaire de réglage — aucun niveau ne recule, **aucune séance ne demande un haltère que le profil n'a pas** (dès que la famille offre un mouvement faisable), une note plus haute ne part jamais plus bas sur le même mouvement, une variante change d'un cran à la fois, la première entrée dans une forme chargée se fait au palier équivalent. Les baisses de volume n'y sont pas des erreurs : les corriger est le rôle de la page.
- **`verifier_semaine.mjs`** : la semaine d'un programme sous un jour de début et un ordre choisis, une semaine vide, le passage à l'heure d'hiver — des cas écrits à la main, que les réponses figées (toutes lues au réglage par défaut) ne visitent pas.
- **`verifier_duree.mjs`** : la durée estimée d'une séance (`duree.js`) sur des blocs et des tempos écrits dans le script — repos entre séries et entre exercices, superset (repos croisés, `repos_apres` du partenaire jamais joué), circuit en tours, pas de repos après le dernier bloc, tempo manquant, arrondi du libellé.
- **`verifier_circuit_tours.mjs`** : un circuit de plus de deux blocs (A B C D, trois tours), que les scénarios figés ne visitent pas — ordre, chaque repos, **une paire qui rend la suite d'avant**, la tête qui fait le nombre de tours, refaire en plein tour et à sa frontière, fin à la main, variante refusée, amorces, changement de bloc, refus de `problemes_des_blocs`.
- **`verifier_corrections.mjs`** : l'instant où le coach dit une faute de forme (durée minimale, rappel, épisode interrompu, amplitude à la répétition comptée, rien sur un gainage pas encore tenu) — des poses au hasard ne tombent jamais pile sur ces seuils.
- **onze `comparer_*.mjs`** : rejouent des milliers de questions figées (poses, scénarios de séance, historiques, barèmes, ligues, objectifs, programmes, ressenti, annonces, variantes, écritures d'historique) et comparent aux réponses de `tests/fixtures/*.jsonl.gz`.

**Les réponses figées ont été produites une dernière fois par l'ancienne implémentation Python**, qui faisait autorité, puis figées. Un rouge veut donc dire « le comportement a changé », pas « c'est faux ». Si le changement est voulu, `--mettre-a-jour` réécrit les réponses avec ce que rend le code — **jamais pour faire taire un rouge non compris**. `scripts/fixtures.mjs` porte la mécanique (`Releve.verifier(ou, cible, cle, obtenu)` désigne la réponse par son *emplacement*, pour pouvoir la réécrire sur place).

Trois décisions tiennent ces tests :
- **Les entrées sont figées aussi** (`tests/fixtures/donnees/`) : un test qui lirait les `donnees/*.json` vivants virerait au rouge au premier réglage de barème sans qu'une ligne de code ait bougé. La validité des données vivantes, c'est `verifier_donnees`.
- **Poses et réponses sont séparées** pour les détections (`poses_detections` figées pour toujours, 9 Mo ; `detections` les jetons, 115 Ko) : un changement de seuil ne réécrit que les jetons. En mise à jour, **toutes** les fonctions de `DETECTIONS` sont rejouées, si bien qu'une détection ajoutée entre d'elle-même dans le jeu.
- **Les familles construites restent** : les poses contiennent, après les tirages au hasard, des familles construites autour des seuils (bras levés buste orienté, un bras levé, élévation, planches, contacts coude-genou, pompes au mur…), et les scénarios des scénarios écrits (`superset_refaire`, `decompte_final`, `pompes_peu_profondes`, `changement_en_cours`, `variante_en_cours`) — les états profonds d'une machine à états sont hors de portée du hasard. Ces entrées ne peuvent plus être régénérées : une nouvelle règle qui demande un cas que le jeu ne visite pas se teste par un script dédié ou une famille ajoutée à la main. **Les familles de gestes ont été construites en miroir** (capture du desktop : épaule gauche à gauche de l'image, visibilité du nez au hasard) : depuis que les gestes exigent d'être de face (`de_face`), elles rendent toutes « faux » et c'est `verifier_gestes` qui couvre le geste de face.

Corollaire : **un mouvement retiré du catalogue garde sa détection et son instrument** tant que les entrées figées le contiennent (`squat_sur_chaise_detection`). Les retirer ferait rejouer ses scénarios sans détection, et `--mettre-a-jour` remplacerait des réponses vérifiées par « rien n'est compté ».

**Un test qui n'a jamais échoué ne prouve rien** : après un changement, saboter la règle et vérifier que le test rougit fait partie du travail. Limite connue : des poses tirées au hasard ne tombent jamais *exactement* sur un seuil, donc un `<` devenu `<=` passe inaperçu aux détections ; `verifier_instruments` imprime les jetons peu visités, dont les seuils sont mal vérifiés. `camera.js` n'a aucun test (il importe MediaPipe depuis un CDN) ; `seance.js` est couvert en partie seulement (par `comparer_seances` et `comparer_variantes`).

## Données (`web/static/donnees/`)

Des **sources éditées à la main** — plus rien ne les fabrique. Chaque fait n'a qu'une source :
- **`reglages.json`** — tous les nombres réglables : barèmes (`specs`), ligues, XP, note d'athlète, retour et départ des variantes, temps d'une répétition par mouvement (`tempo`, pour la durée estimée seulement — exigé par `verifier_donnees` pour tout mouvement compté). Édité depuis `dev/baremes.html` (qui recopie aussi les sections qu'il n'édite pas). **Le pourquoi de chaque réglage est dans `docs/reglages.md` : le lire avant de changer une valeur.**
- **`baremes.json`** — le *socle* qui ne se règle pas : échelles d'haltères, matériel par exercice (`halteres`, `brut`), accessoires, matériel par défaut, repères écrits de la note.
- **`composer_baremes(socle, reglages)`** (`paliers.js`) assemble les deux au chargement : specs complétées de leurs défauts, `xp.*` renommés dans `ligues`. **Toute page qui construit un `Baremes` passe par là** — l'application, `dev/baremes.html`. Avant, l'application relisait une *copie* des réglages : éditer `reglages.json` n'aurait rien changé.
- **`fiches.json`** — le texte des fiches (cinq champs). Édité depuis `dev/fiches.html`.
- **`mouvements.json`** — ce qui est couplé au code : `detection`, `erreurs`, `amplitude` (par **nom** de fonction de `detections.js`), `orientation`, `changements`, variantes, `materiel`, `est_echauffement`, `aussi_exercice` (voir *Échauffement*), `delai_min_reps` (voir *Détection*), `en_developpement` (un mouvement en cours d'ajout, rangé à part au banc d'essai — `est_en_developpement`, `nature.js` ; écrit à l'ajout, retiré à la clôture), `autre_cote` (`{mouvement, membre}` d'un mouvement unilatéral, réciproque, vérifié par `verifier_donnees`). **`avec_fiches(mouvements, fiches)`** (`seance.js`) y remet le texte au chargement, dans l'application comme dans la démo.
- **`categories.json`** — la catégorisation des mouvements, **cachée dans l'application** : `muscles` (→ `partie`), `parties` (→ `region`), `regions` (`accompagne` : le tronc ne fait une zone que seul), `chaines`. Chaque mouvement porte `categories: {muscles, chaine}`, muscle principal en tête ; partie et région **se déduisent** (`categories.js`), elles ne s'écrivent pas. L'application n'en montre que les étiquettes d'un programme (zone, « sans haltère », « jouable avec mon matériel »), dont la règle du matériel vit dans `Variantes.jouable_avec_le_materiel` — posée au moteur du profil, ou à un moteur d'inventaire déclaré vide.
- **`seances.json`**, **`programmes.json`** — les séances et les programmes **communs**, édités depuis **l'outil maître** `dev/createur.html` (absent de l'application, joint par le sommaire). Il prend les mêmes éditeurs et les mêmes refus que l'application (`editeur_seance.js`, `editeur_programme.js`, `problemes_des_blocs`, `problemes_du_programme`), montre durée estimée et étiquettes, rend les deux fichiers **à l'identique** de leur forme (un espace d'indentation, pas de saut de ligne final : coller sans rien changer ne fait aucun diff). Renommer une séance y emporte les programmes qui la citent, pas l'historique (la page le dit) ; supprimer une séance citée est refusé. **Promouvoir** lit une sauvegarde en mémoire (`importer`, jamais enregistrée) et rend commune une création perso — refusé si le programme promu ne passe plus `problemes_du_programme` (une séance qu'il cite a été renommée depuis). Un onglet montre la catégorisation de chaque mouvement, en lecture.
- **`sons.json`** — les tables du coach : `fichiers` (clé → variantes `.wav`), `priorites`, `delais`, `silences`, `sortie` (amplification), `textes` (le texte de chaque brique), `briques` (clé → fichier), `fragments`, `orientations`, `longueur_maximale_nom`.

Les pages `dev/` rechargent les données déployées, les rendent éditables, recalculent tout avec les mêmes modules que l'application, et rendent le fichier prêt à coller : on colle dans `web/static/donnees/`, on pousse. Leur brouillon (`localStorage`) est jeté si le fichier déployé a changé depuis.

**Le nom d'une séance est à la fois sa clé et son titre**, et il est référencé ailleurs : valeurs du dict `seances` de chaque programme (sans quoi le programme ne pilote plus rien), `nom_seance` des séances enregistrées (« dernière fois », semaine du programme), `seances_perso` des profils. Renommer une séance casse ces liens en silence ; `verifier_donnees` attrape seulement ceux des programmes.

**Aucun mouvement de tirage ne se fait sans haltère** (les quatre mouvements de dos en exigent) : une séance sans matériel couvre poussée, jambes et gainage, et le dit dans sa description. Ajouter un exercice demande sa détection, son instrument, sa fiche, sa spec, son entrée de matériel, ses bornes de ligue — `verifier_donnees` signale ce qui manque. **Un ajout suit le skill `ajouter-exercice`** (`.claude/skills/ajouter-exercice/`) : questionnaire, deux poussées (banc d'essai, puis séance), médias après ; son avancement vit dans une fiche de suivi `docs/exercices/<nom>.md`, supprimée à la fusion dans `main`, et se lit sur l'iPad dans `dev/suivi.html` — qui ne coche rien : la fiche reste la seule source, et la page y ajoute le constat de ce que le site contient (catalogue, fiche, vidéo, voix, détection, barème), sondé au nom que lit l'application. Le nom d'un mouvement est une clé définitive : un échauffement appelé à devenir un exercice compté reste un mouvement, et l'exercice en sera un second.

## Architecture (`web/static/`)

`app/` l'application ; `demo/` le banc d'essai d'un exercice isolé ; `dev/` les pages de réglage ; `js/` les modules ; `sons/` les annonces (nom de fichier = texte prononcé). Feuilles de style partagées à la racine (`palette.css`, `hud.css`, `programmes.css`, `exercices.css`, `ressentis.css`, `ancrages.css`, `graphique.css`, `programme_resume.css`, `editeur.css`).

**Une page qui garde sa logique pour elle est invérifiable.** Les règles vivent dans des modules purs (`circuit.js`, `moteur.js`, `seance.js`, `tutoriel.js`, `progression`…), testables dans Node ; la page ne fait que câbler.

**Un cycle d'imports ne se rattrape pas en module ES** : il laisse une liaison non initialisée et la page meurt au chargement sur un `ReferenceError` qui ne nomme aucun des deux fichiers. Sortir la feuille dans un module sans dépendance (c'est l'origine de `cible_manuelle.js`, ré-exporté par `objectifs.js`).

### Messages

**Tout texte destiné à l'utilisateur porte une clé** (`messages.js`) : une fonction d'erreur de forme retourne une clé, `texte()`/`libelle_etape()` ne lèvent jamais (elles tournent dans la boucle d'images, où une exception gèle l'écran) et une clé inconnue rend `null` — rien à l'écran. Ajouter un message se fait dans ce module.

L'état de séance porte quatre champs qui ne se confondent pas : `erreur` (faute de forme, bandeau rouge), `consigne` (quoi faire, bandeau bleu), `stage` (jeton brut du détecteur), `etape_libelle` (sa traduction). **Une faute de forme n'existe que pendant l'effort** : `peindre_hud` ne montre le bandeau rouge qu'en phase `exercice`. **Une consigne d'absence s'efface dès que le corps revient** : remise à `null` en tête de la branche « corps vu » de la boucle.

### Séance (`circuit.js`, `moteur.js`, `seance.js`, `etat.js`)

- **`Circuit`** : une séance en cours, faite de `BlocExercice` (mode, séries, répétitions/durée, repos). Phases `preparation` → `exercice` → `recuperation_serie` → … → `termine`/`abandonne`. L'entrelacement (`entrelace_avec`, superset gauche/droite) est la logique la plus délicate (`_est_entrelace`, `terminer_serie`). **Invariant : la phase `exercice` implique un bloc courant** — la règle vit dans la classe, pas chez les appelants.
- **`executer_mode`** dispatche vers répétitions / maintien / chrono / AMRAP / échauffement, et retourne toujours un triplet `(derniere_rep, repetitions, serie_terminee)`. Une fin de série passe par `_finaliser_serie`, et l'état temporel du bloc se nettoie dans `reinitialiser_etat_serie`, seul endroit qui en connaît la liste.
- **Un maintien ne se corrige pas avant d'avoir été tenu** : faute de forme et « reprends la position » attendent `position_maintien_validee`, le premier `maintien` de la série — remis à zéro avec la série (`CHAMPS_TEMPORELS`) : oublié, il survivait, et la correction partait dès la série 2 pendant qu'on se remettait en planche.
- **Deux mesures du temps, incompatibles** : chrono et AMRAP en temps *mural* (ils ne se mettent pas en pause hors champ) ; maintien et échauffement en *deltas* image par image, **plafonnés à `INTERVALLE_MAX`** (0,5 s), pour qu'un retour dans le champ ou un onglet suspendu ne crédite pas d'un coup tout le temps écoulé.
- **L'horloge est celle de la séance, `seance.maintenant()`**, jamais `performance.now()` en dur — y compris pour les repos et `duree_totale`. C'est ce qui permet de rejouer 45 minutes de séance en quelques millisecondes dans les tests.
- **Un bloc porte `repetitions` et `duree` à la fois ; seul le mode dit lequel est joué.** Point d'entrée unique : `cible_du_bloc(bloc)` (adossé à `MODES_CIBLE_TEMPORELLE`, AMRAP compris). Jamais de `repetitions || duree`. Une **cible nulle dans l'unité jouée** est refusée (`problemes_des_blocs`) : elle finirait la séance entière à la première image, en silence.
- **Circuit en tours** : des drapeaux « avec le bloc suivant » consécutifs font une **chaîne** (`chaines_entrelacees`), jouée A B C D, A B C D… ; **une paire est une chaîne de deux**, une seule règle. La **tête** (le bloc que personne ne vise) ouvre chaque tour, et **son** nombre de séries fait le nombre de tours (`problemes_des_blocs` refuse des séries inégales, et un échauffement dans une chaîne). Le repère `_exercice_precedent_entrelace` nomme toujours la tête et le tour ouvert (`_tour`) ; `serie_actuelle` reste le numéro du tour d'un membre à l'autre. **Le repos avant une série est le `repos_entre_series` du bloc qu'on va jouer** : sur la tête, le repos entre deux tours ; sur un membre, la transition. Après le dernier tour, le `repos_apres` de la tête ; ceux des membres ne sont jamais joués. Une pause qui change de bloc (`change_de_bloc()`) annonce l'exercice qui vient, comme un repos entre exercices. `amorce_annonce` : « premier » tant que rien n'est fait, « pour finir » au dernier tour seulement. L'éditeur partagé (`editeur_seance.js`) lit les chaînes avec la même fonction : en-tête « Superset » ou « Circuit · N tours », « Repos entre tours » sur la tête, « Transition » sur les membres, dont le repos après est grisé.
- **Échauffement** : détection *facultative* (affichage seulement, jamais une condition d'avancement) et **invisible dans les statistiques**, exclu à la source par `resultats_par_exercice` (point d'entrée : `est_echauffement(bloc)`). Ne pas ajouter de filtre en aval. **C'est le mode du bloc qui décide, pas le mouvement** : le drapeau `est_echauffement` d'un mouvement dit seulement où le proposer, et un échauffement qui a une détection de comptage peut être **aussi un exercice** (`aussi_exercice: true`) — les Jumping jacks se jouent en échauffement au chrono ou comptés en AMRAP, sous le même nom. Toute lecture passe par `nature.js` (`propose_en_echauffement`, `est_exercice`, `est_compte`) : listes de l'application, éditeur, démo, `dev/fiches.html`, vérificateurs. Un drapeau à part, et non « un échauffement avec détection » : le Squat lent emprunte la détection du squat pour l'affichage sans être un exercice.
- **Deux barres de progression, jamais en même temps** : échauffement ou exercices, décidé par `dans_echauffement`. **Chaque segment se lit dans l'état de sa série** (`etat_des_series(blocs)`, champs `series_exercices` / `series_echauffements` du payload), jamais dans un compte à plat : avec `series_terminees`, un superset remplissait le premier exercice deux fois plus vite. Seules les séries du mouvement joué comptent (une variante ne remplit pas avec celles du quitté). Toucher un groupe ouvre une bulle (nom entier, pastilles de `pastilles.js` — le même `resume_series` que l'historique —, compte en direct), dans la seule barre touchée.
- **Variante en pleine séance** (`passer_a_la_variante`) : le bloc repart à la série 1 sur la variante ; chaque série enregistrée porte le nom de son mouvement ; le mouvement quitté garde sa ligne (`bloc.abandons`) ; le `Circuit` ne connaît pas le catalogue (`variante_possible()` rend un nom, l'appelant résout l'`Exercice`). Refusée sur un bloc entrelacé.
- **Pas de repos après le dernier bloc** : une fin de bloc passe par `_finir_bloc`, qui ne pose `repos_exercice` que s'il reste un `prochain_bloc()` (le partenaire d'un superset sauté). Corollaire : « refaire » n'est plus offert à la toute fin, la séance est déjà `termine`.
- **Refaire la dernière série** ne se déduit pas de l'état courant (`terminer_serie` a cinq sorties) : `terminer_serie` écrit un repère `_derniere_serie_terminee` **avant toute mutation**, `refaire_derniere_serie` le restaure (y compris `_exercice_precedent_entrelace`, et `index_exercice` d'abord) et oublie tout de suite le résultat désavoué.
- **Terminer une série à la main** est le seul chemin vers un `completee` faux : `terminer_serie_manuellement` interroge `objectif_serie_atteint`. La durée réalisée se lit avec `duree_realisee(bloc, etat)`, jamais en chaînant les compteurs de modes (un gainage lâché avant une seconde est *falsy*).
- **`payload_etat`** (`seance.js`) est le contrat de l'écran : il relit les champs dérivés du circuit au lieu de les recopier au fil de la boucle.

### Progression (`paliers.js`, `niveaux.js`, `objectifs.js`, `ressenti.js`, `calibration.js`, `variantes.js`, `programmes.js`, `ligues.js`, `cible_manuelle.js`)

Rien n'est stocké hormis l'historique et les ancrages : tout se recalcule à la lecture.

**Le moteur d'un profil s'assemble dans `construire_progression`** (`progression.js`) : l'application et le simulateur passent par là, sans quoi deux assemblages finiraient par différer d'une dépendance et le simulateur décrirait un autre moteur que celui qui joue. À reconstruire quand le matériel change.

**Niveau ≠ objectif, et rien ne doit brouiller la distinction.** Le *niveau* est le plus haut palier **jamais** validé (preuve stricte, ne recule jamais). L'*objectif* est ce que la prochaine séance demande : il monte ou descend, et peut passer **sous** le niveau (délestage, pas régression).

- **Barème** (`paliers.js`) : voir `docs/reglages.md`. Invariant du volume ; tranches de longueurs inégales, donc **parcourues** (`_iterer_tranches`), jamais calculées par modulo ; ordre cible → poids → séries ; **tranche ouverte** sans fin, si bien qu'un objectif n'est jamais hors d'atteinte. Le générateur de tranches est infini : tout appelant pose sa condition d'arrêt. `est_suivi_par_le_moteur(nom)` dit si un exercice a des paliers. Quiconque calcule un volume sans palier en main passe par `volume_exercice(nom, …)`, qui connaît la charge du corps. **Un barème ne mélange jamais le poids du corps et les haltères** : un mouvement sans haltère n'a que le cran du poids du corps, un mouvement chargé que des haltères (le squat qui allait de l'un aux autres est devenu deux mouvements reliés par les variantes). **`chargeable(nom)`** dit si le matériel offre un poids **dans** la fourchette du barème, sans le repli d'`echelle_exercice` (qui rend un barème calculable, pas un mouvement faisable). Bizarrerie voulue : le palier suivant peut demander **moins** de répétitions quand il monte en charge (l'écran l'explique).
- **Matériel** (`materiel.js`) : un inventaire `{poids: quantité}`, dont dérivent l'échelle à un haltère et celle à la paire. `normaliser(null)` rend le matériel supposé (profil muet), un inventaire déclaré vide reste vide. Trois listes : la gamme proposée au questionnaire, ce qui est déclarable (1-60 kg au demi-kilo), et le matériel **supposé** — figé sur l'ancienne gamme : l'allonger changerait le barème de tout profil muet. Le repli « barème toujours calculable » vit dans `echelle_exercice`, pas sur l'inventaire (il rend un barème calculable, pas un mouvement faisable : c'est `chargeable` qui le dit).
- **Niveaux** (`niveaux.js`) : une performance valide un palier si elle est au moins aussi lourde **et** au moins aussi volumineuse, au **maillon faible** (séries `completee` seulement). `etat_niveau` distingue trois cas qu'un écran ne doit pas confondre : hors barème (`niveau` null, ce n'est pas « niveau 0 »), barème épuisé, cas ordinaire. `montees_de_niveau` rejoue l'historique en ordre chronologique.
- **Ancrages** : recalent un niveau que l'historique ne prouve pas. Un ancrage fait **table rase et plancher** à la fois. Repère chronologique : `apres_seance_id`, **jamais la date** (`JJ/MM/AAAA` ne se compare pas). C'est un journal : seul le dernier ancrage compte. L'écran ne demande jamais un numéro de niveau, mais une **performance**, et refuse celle qui n'atteint pas le palier 1.
- **Objectifs** (`objectifs.js`) : trois règles dans l'ordre — repère de la dernière séance ± ressenti ; exercice jamais fait → départ de la note d'athlète ; sinon `niveau + 1`. Une note relevée à la main pose un plancher. Un exercice jamais fait dont une **variante plus facile** a un niveau part de l'**entrée** depuis cette variante (`_entree_par_une_variante`) : vers une forme chargée, le palier de **même volume** que le niveau acquis à vide (`palier_d_entree`, la répétition à vide pesant le `charge_corps` de la forme chargée) ; entre variantes sans charge (pompes, gainage), le palier 1. Un bloc échappe au moteur pour trois raisons seulement : pas de barème, mode qui ne mesure pas la même chose, cible manuelle. `appliquer_a_blocs` (dictionnaires) et `appliquer_a_circuit` (`BlocExercice`) partagent `objectif_pour`. Le drapeau « 1re fois » est posé par l'affichage, jamais par une fonction partagée avec l'écriture.
- **Ressenti** (`ressenti.js`) : toute la progression tient dans la table `AJUSTEMENT` : réussi +1, « facile » +2, « trop facile » +3 ; échoué 0, « trop dur » −1. Pas de réponse = comportement de base. Le repère est le **palier visé** à la dernière séance, re-dérivé des cibles stockées (`_cible_visee`), jamais le niveau. Un échec ne fait **pas** reculer (`base_apres_echec`). Une ancienne série de test (`CIBLE_TEST`) n'est ni réussie ni échouée (`est_serie_de_test`). Les écrans ne proposent que les réponses qui *changent* quelque chose ; pas de bouton neutre.
- **Note d'athlète** (`calibration.js`) : une note générale 1-10, traduite par les **bornes de ligue** (rang par note), jamais par un numéro de niveau ; rien n'est ancré. Elle monte toute seule (`note_mesuree`, lue sur la **dernière** séance de chaque exercice, pas le record) ; relevée à la main, elle pose un plancher jusqu'à la séance suivante (repère `note_relevee_apres` = id de séance). `arrondi_python` reproduit l'arrondi au pair (`Math.round` diffère sur les demis exacts).
- **Variantes** (`variantes.js`) : une substitution est une **préférence du profil** (`utilisateurs.variantes`, `{original: joué}`), jamais une donnée de séance — elle ne doit **jamais atteindre une séance écrite** : `appliquer_au_circuit` sur le seul chemin de jeu, `substitution` pour l'affichage. `definir` vérifie la chaîne, la jouabilité et l'unité. **On remonte tout seul** (`montees`) : une séance menée à son terme qui prouve la performance de retour fait passer au cran du dessus — lue sur la séance jouée, jamais sur le record ; un cran par séance et par clé ; rien sur une séance abandonnée. La montée est une annonce de fin de séance avec un bouton « Rester sur… ». **On ne descend que sur proposition** (`propositions`, un bouton) : après un échec au palier 1, après une bascule en séance, ou après un échec **au départ** — un mouvement jamais réussi dont aucune variante plus facile n'est réussie non plus, donc atteint par la note et non par une montée (sans quoi celui qui se surestime à l'accueil descendrait palier par palier jusqu'au palier 1 avant qu'on lui propose plus facile). Après une montée, un échec fait refaire la séance : proposer de redescendre aussitôt faisait osciller entre la forme à vide et la forme chargée. Un programme garde l'exigence du mouvement complet (`via_variante`) sans toucher à l'avancement. **Vers une forme chargée, le seuil de retour se lit « avec le premier haltère du profil »** (`volume_a_vide_pour_charger`) : traduit à vide par la part du corps, il demande d'autant plus de répétitions à vide que le premier haltère est lourd — on reste plus longtemps à vide avec des 10 kg qu'avec des 5 kg, et l'entrée ne fait jamais perdre de répétitions. Un seul nombre fait les deux traductions, seuil et entrée : `charge_corps` (`equivalence_a_vide`). **Le matériel l'emporte sur la préférence** : un mouvement que le profil ne peut pas charger (`chargeable`) se joue sous la première variante plus facile qui se charge (`substitution`), ne se propose pas (`versions`), et on n'y monte pas (`montees`) — et ce n'est **jamais écrit dans la table**, le matériel changeant. **Le mouvement de départ** d'une famille jamais jouée (ni ligne d'historique, ni ancrage) vient de la note effective (`selon_la_note`, table `variantes.depart` : pour la tête d'une chaîne, la note à partir de laquelle on démarre sur chaque mouvement) ; tous les écrans lisent la table par `variantes_en_cours` (`progression.js`), et `demarrer` l'**écrit** sur le profil — seulement relu, le choix s'effacerait dès la séance suivante, la famille ayant été jouée. **Une séance écrite nomme la forme la plus dure** (« Squat chargé ») : la note et le matériel font jouer la forme à vide à qui en a besoin.
- **Programmes** (`programmes.js`, lecture seule) : une performance à atteindre par exercice ; rien n'est stocké. La ligne affiche la **prescription** et sa traduction sur le barème (par le **volume**, ce qui aplatit la structure des séries). Une seule convention de charge partout : **le poids d'un haltère**. Le `pourcentage` est la moyenne des avancements (bornés à 100 %). Le lien libellé → séance est une **donnée** (`seances` du programme). **Un programme se vit à la semaine** (`semaine_du_programme`) : une semaine **du calendrier**, à partir de 0 h le jour choisi par le profil (`programme_jour_debut`, lundi par défaut), jamais un cycle ouvert par la première séance (il glissait au premier retard et marquait ratées des semaines faites). Cases cochées par identifiant ; une séance dans le désordre coche la première case vide de son libellé ; l'ordre des cases est une préférence du profil **par programme** (`programmes_ordre`), recalée sur le fichier par `ordre_des_seances` (seul point d'entrée). Les semaines passées se suivent **sans trou** : une semaine vide compte `0/n` et casse la série. Rythme multiple du nombre de séances (`programme_tours`, borné à la lecture). Les trois réglages relisent tout l'historique (rétroactifs). Dates en heure murale naïve (`Date.UTC`). Un programme se crée depuis ses séances : `exigences_depuis_seances` propose, pour chaque bloc **piloté par le moteur** (`pilote_par_le_moteur`, `objectifs.js` — le même critère que celui qui pilote un bloc), une exigence égale à ce que la séance prescrit ; `completer_exigences` recale des exigences écrites sur ces propositions (**l'écrit gagne**, le disparu s'en va). `problemes_du_programme` porte tous les refus, et `verifier_donnees` les pose aux programmes déployés — dont un libellé lié **sans exigence**, que `libelles_seances` ferait disparaître de la semaine. **Promouvoir** une création perso (`promotion.js`, outil maître) retire `cible_manuelle` des blocs et refuse une collision de nom sauf `remplacer` explicite — le cas ordinaire d'une copie perso qui garde le nom de la commune.
- **Ligues** (`ligues.js`) : le rang vient du **volume** du palier atteint, comparé à des **bornes par exercice en volume absolu** (`seuils_par_exercice`), avec repli sur une table relative pour un exercice sans bornes — repli qui masque aussi un branchement oublié. Hors barème = pas de ligue. `rang_pour_volume` sature au dernier rang. La ligue générale avance d'un cran par niveau général, et c'est le **coût** du niveau général qui porte l'exigence. Inégalité de cadence assumée entre mouvements chargés (deux axes de croissance) et au poids du corps (un seul). `ligue_pour_rang` rend `cle` et `division_index` pour les écrans.
- **Cible manuelle** (`cible_manuelle.js`) : un bloc dont la cible s'écarte du palier proposé est marqué et le moteur ne le touche plus. La marque appartient à un **profil** (`cible_manuelle` = liste d'identifiants ; un format inconnu vaut « personne »). **Une séance menée à son terme entérine ses cibles figées** (`enteriner_cibles_manuelles`), seulement sur une séance locale. L'éditeur part des valeurs **du moteur** (`blocs_a_editer`) : sinon enregistrer sans rien toucher figerait tout.

**Fiche d'exercice** : niveau, ligue, graphique, recalage et consignes au même endroit. La cible d'un exercice jamais fait se lit dans `objectifs_par_exercice` (« Première séance »), jamais dans le palier 1. Pas de jauge ni de total de paliers sur une fiche : ce qui exprime un objectif appartient aux programmes.

### Détection (`detections.js`, `positions.js`, `compteur.js`, `landmarks.js`, `outils.js`, `instruments.js`)

Chaque mouvement a une fonction `*_detection(corps)` qui rend un jeton (`debut`/`fin`/`milieu`/`maintien`/`repos`). **`debut` et `fin` désignent un moment du comptage, pas une posture** : le compteur s'arme sur `debut` et compte sur `fin`, la fin de la phase concentrique (le haut d'un curl, le verrouillage d'une pompe, le retour debout d'un squat). Un mouvement compté a **deux seuils** (hystérésis : les déplacer ensemble), un maintien un seul.

Règles apprises, à appliquer à toute nouvelle détection :
- **Un angle se lit en 2D** : une flexion dans le plan sagittal (genou, hanche) est illisible de face. Préférer un repère **vertical** rapporté à un segment du corps (`_descente_hanche`) dès que la fiche demande une vue de face.
- **Une distance se rapporte au corps** : en coordonnées brutes, elle dépend de la distance à la caméra. Le soulevé de terre mesurait poignet-cheville en fraction d'image ; à trois mètres, debout, on restait sous le seuil du haut et il fallait plier les coudes pour compter. Il lit la hauteur des poignets **en tibias** (`hauteur_poignets`). Le squat (distance coude-genou brute) a le même défaut.
- **Un mouvement unilatéral vérifie qu'il est fait du bon côté** : le genou arrière d'une fente se plie aussi à 90°, et une fente du mauvais pied comptait. Le bas d'une fente exige que le genou mesuré soit **plus haut que l'autre** (`genou_au_dessus_de_l_autre`, en tibias, lisible de face comme de profil) — au bas seulement : debout, pieds joints, rien ne distingue les jambes.
- **Bilatéral vu de face** : les deux côtés doivent franchir le seuil (vieux bug `a and b < seuil`). **Vu de profil**, le membre éloigné est estimé : moyenner (gainage), ou lire **le bras le mieux vu par `visibility`** quand l'estimation décroche (`_bras_proche`, pompes) — jamais par `z`.
- **Une détection dit quelle forme a le corps *et* où il est** : sans condition de position, un développé épaule comptait des bras baissés, un développé couché comptait debout. Une condition de position partagée par `debut` et `fin` fait tomber tout le reste en `milieu`.
- **Un maintien se reconnaît à ce qui le rend difficile** (hanche décollée, épaules soulevées), pas à sa seule forme. Vérifier au banc qu'une condition d'effort filtre vraiment.
- **Une faute de forme ne retire jamais une répétition.** **Ce qui compte et ce qui est bien fait sont deux seuils** : les pompes arment à 120° (`SEUIL_COMPTAGE_POMPE`) et `Exercice.amplitude` + `suivre_amplitude` avertissent au moment où la répétition compte si le point le plus bas n'est pas passé sous `SEUIL_PROFONDEUR_POMPE` (une pose figée de scénario est construite à 110° : ne pas le monter à 110 sans nouveau cas). Même schéma pour l'extension triceps : au-delà de `ECART_COUDES_AVERTISSEMENT` le coach avertit, au-delà de `ECART_COUDES_MAX` la répétition ne compte plus — le refus est une condition de position de la détection, pas une répétition retirée.
- **Mesurer ce que la fiche demande, pas un angle qui dépend d'autre chose** : le crunch se lit à l'inclinaison du buste (« décolle les épaules »), plus à l'angle épaule-hanche-genou, qui dépendait de la flexion des genoux et, exigé des deux côtés vus de profil, ne comptait presque rien.
- **Devant une détection qui compte mal, lire d'abord ce que la fiche omet de demander** avant de déplacer un seuil (le squat : le contact coude-genou n'était demandé qu'en troisième ligne).
- **Une mise en place n'est pas une répétition** : le compteur prend le premier jeton vu pour position de départ, sauf si le mouvement déclare la sienne (`depart` dans `mouvements.json`, `Exercice.depart`, passé à `CompteurMouvement.mettre_a_jour` par ses trois sites d'appel). Le développé couché part bras tendus (`fin`) : s'allonger coudes pliés puis pousser en place comptait une répétition à chaque série.
- **Une série comptée s'ouvre quand on est en place** (`attendre_mise_en_place`, `moteur.js`) : le même jeton **à une extrémité** (ou le `depart` déclaré) et le buste immobile (`vitesse_du_buste`, `immobilite.js`, mesure partagée avec la démo) pendant `DUREE_MISE_EN_PLACE`. Alors le coach dit « c'est parti » (`debut_serie`, que le moteur dit seul désormais : une série qui ne compte pas s'ouvre à sa première image) et le compteur reçoit ses premiers jetons — sa position de départ est la position tenue. **Rien ne compte avant**, ni faute ni tentative : se rendre à sa place, prendre l'haltère faisaient parler le coach. Une image manquée remet l'attente à zéro ; un geste ±1 ouvre la série en silence ; le chrono d'un AMRAP part à l'ouverture. L'état vit sur le bloc (`CHAMPS_TEMPORELS`) : une série refaite ou remise à zéro se rouvre. **Le rejeu des scénarios figés la coupe** (`executer_mode({ mise_en_place: false })`) : leurs poses tirées au hasard ne restent jamais immobiles, plus rien n'y compterait, et `--mettre-a-jour` remplacerait des comptes vérifiés par zéro.
- `CompteurMouvement` refuse deux répétitions à moins de `DELAI_MIN_ENTRE_REPS` (un écho de détection), avec l'horloge de la séance. Un mouvement plus rapide, où chaque pas compte (montées de genoux : 3 à 4 par seconde), déclare le sien (`delai_min_reps`, de 0,1 à 0,3 s, passé par ses trois sites d'appel comme `depart`) : l'hystérésis de sa détection empêche déjà l'écho d'un aller-retour d'une image. Le compteur fantôme de l'autre côté garde le délai par défaut.
- **Chaque côté compte, sans compteur nouveau** : pour un mouvement alterné, `debut` est la position neutre (genoux au même niveau, la garde) et `fin` l'un **ou** l'autre côté à son extrémité (une mesure qui prend le max des deux côtés, l'instrument ne sachant que des « et »). Chaque pas repasse par le neutre, et debout immobile, on est à `debut` : la mise en place marche telle quelle (`depart: "debut"`). Quand deux mesures doivent porter sur **le même côté** (la main qui touche et le pied opposé du stance jack, le pied le plus haut et sa portée du switch kick), un helper choisit ce côté une fois (`main_qui_touche`, `pied_haut`) et chaque mesure le relit.
- **Une condition qui exclut le voisin** sépare deux mouvements que la même mesure confondrait : le talon-fesse exige des genoux au même niveau (sinon une montée de genou comptait), le switch kick un pied lancé loin de la hanche (sinon un talon-fesse comptait), le Heisman un pied d'appui hors de la hanche (sinon une montée de genou sur place).
- **Vérifier une étape par le seuil d'un autre mouvement** : le burpee s'arme au bas d'une pompe, avec `SEUIL_COMPTAGE_POMPE` — la même règle que les pompes, si bien qu'un burpee sans pompe ne s'arme jamais. Un mouvement à trois positions se ramène ainsi au compteur à deux.
- **Le ski est la seule détection qui lit un repère extérieur au corps** (le centre de l'image) : sans mémoire, rien d'autre ne dit de quel côté on a sauté. L'amplitude reste en largeurs d'épaules, et la fiche demande de se placer au milieu. Repli prévu si le banc le prend en défaut : un repère pris à la mise en place.

**Gestes de contrôle** (`positions.js`) : ils ne doivent pas se confondre avec un mouvement d'exercice. **Tous se font de face** (`de_face` : buste debout, épaule gauche à droite de l'image — la vidéo arrive brute —, nez vu à `visibility` ≥ 0,5) : de dos, l'image inverse gauche et droite, et deux mains simplement rapprochées passaient pour des bras croisés (une pause a sauté ainsi). `deux_bras_leves` exige un **buste debout** (sinon le haut d'un développé couché remettait la série à zéro). Un bras seul corrige le compte (droit +1, gauche −1) à condition que **l'autre poignet soit sous son épaule**. La règle du compte vit dans `ajuster_repetitions` (phase `exercice`, modes à compte) ; un +1 ne touche que le compteur et c'est `executer_mode` qui l'annonce et clôt la série ; un −1 fait reculer `derniere_rep`. `bras_en_x` ne contraint que les abscisses : la hauteur est libre.

**Instruments** (`instruments.js`) : chaque détection redécrite en mesures et zones ordonnées, pour le banc d'essai **et pour expliquer une répétition refusée**. Jamais sur le chemin du comptage ; c'est une copie des seuils, tenue par `verifier_instruments`.

**« Ça ne compte pas »** (`SuiviTentatives`, `expliquer_tentative` dans `moteur.js`) : une tentative qui a vraiment progressé (au-delà de `PROGRESSION_SIGNIFICATIVE`) sans atteindre l'autre extrémité se dit, voix et bandeau, avec sa raison. Aller interrompu (un crunch pas assez haut) ou retour incomplet (une pompe pas assez descendue : le compteur ne se réarme pas). Le rôle d'une mesure se lit sur ses zones (`role_mesure`) : **chemin** (zones opposées, où se mesure la progression), **position** (même zone des deux côtés, sans raison : hors d'elle, une image ne fait rien progresser — sinon marcher entre deux séries ferait parler), **forme** (même zone, avec une raison : l'écart des coudes du triceps), **cible** (zone d'arrivée seule). La raison : une forme qui manquait **à l'image où le chemin était arrivé** (les meilleures valeurs mesure par mesure ne le verraient pas), sinon la première mesure bloquante qui en porte une (`raisons` sur la mesure, petit vocabulaire `RAISONS` partagé entre mouvements, car chaque clé est une prise de son), sinon la phrase générique du demi-cycle. **Une raison est un constat, pas un ordre** (« tu ne descends pas assez bas », non « descends plus bas »), **au présent**, qui ne s'accorde pas : une voix enregistrée une fois sert à tous les profils. Le suivi suit le `depart` du compteur. La voix est `coach("repetition_non_comptee", raison)`, que le lecteur compose en « Ça ne compte pas » + la brique de la raison, en une entrée ; le bandeau reste jusqu'à la répétition comptée suivante, devant l'avertissement d'amplitude et derrière une faute du moment. **Un échec se confirme avant d'être dit** (`confirmer_verdict`, fonction pure partagée avec la démo) : il attend que l'extrémité où il s'est clos dure `PERSISTANCE_VERDICT`, et il est abandonné si le jeton la quitte ou si une répétition compte. Sans cela, un curl vu de face faisait dire « tu ne montes pas assez haut » sur des répétitions comptées : avant-bras pointé vers la caméra, le poignet se projette sur le coude, l'angle 2D se lit « bras tendu » une image, et le suivi close l'aller. Le journal du banc d'essai, lui, reste brut.

**« C'est l'autre jambe »** (`surveiller_autre_cote`, `moteur.js`) : la détection de l'autre côté (`Exercice.autre_cote`, résolu par `autre_cote_pour`) alimente un `CompteurMouvement` **fantôme** sur le bloc. Quand il compte et que le vrai ne compte pas dans `FENETRE_AUTRE_COTE` (deux bras d'un curl partent souvent ensemble), le coach dit `coach("repetition_non_comptee", "raison_autre_<membre>")` — « Ça ne compte pas : c'est l'autre jambe » — avec le même bandeau. Pendant `SILENCE_APRES_AUTRE_COTE`, l'échec d'une tentative se tait (`expliquer_tentative({ muet })`) : dans une fente du mauvais pied, le genou mesuré, l'arrière, échoue lui aussi, et le coach disait sa phrase générique au lieu du pied. Un maintien (planche latérale) : le jeton `maintien` de l'autre côté tenu `TENUE_AUTRE_COTE`, une fois par épisode, le bandeau dès la première image. Rien avant l'ouverture de la série. Les scénarios figés ne le visitent pas (le catalogue figé n'a pas le champ).

**Repère gauche/droite** : le navigateur passe la vidéo brute au modèle, l'étiquetage est correct ; `Camera.miroir` ne touche que le dessin. Les séances importées de l'ancien desktop (capture en miroir) portent l'étiquetage inversé sur les exercices asymétriques.

### Fiches et texte

Une fiche (`Exercice.fiche()`) a des champs qui ne se recouvrent pas : `description`, `mise_en_place` (avant de commencer, cadrage caméra compris), `instructions`, `sensations` (ce qu'on doit sentir et ce qui ne doit pas arriver), `erreurs_frequentes` (pédagogie écrite — à ne pas confondre avec `erreurs`, des **fonctions**). `orientation` est le seul champ que le coach **prononce** (cinq valeurs ; `null` = « rien de sûr à dire », jamais « face » par défaut). `changements` (`[fraction, "sens"|"jambe"|"bras"]`) fait dire au coach de changer de sens, de jambe ou de bras pendant un échauffement (`annoncer_changements`, sans état sur le bloc). **Un champ d'`Exercice` oublié dans `exercice_pour` ne lève rien** : il vaut `undefined` partout (c'est arrivé à `orientation`, et le coach n'a jamais dit où se placer).

`dev/fiches.html` montre chaque fiche telle qu'elle s'affiche, à côté de ce que le coach dira et de ce que la détection vérifie : c'est ce qui rend une contradiction visible. Ses avertissements (jargon, phrase de plus de dix-huit mots, accord genré) aident et ne bloquent rien — **un relevé qui crie partout apprend à ne plus être lu**. Elle dit aussi quelles vidéos restent à tourner (encart par fiche, « sans vidéo » dans la liste, compte global), en sondant chaque fichier par une requête `HEAD`.

Elle sert aussi à rédiger une **commande de fautes de forme** : sous chaque fiche, les fautes à ajouter, modifier ou supprimer, chacune avec un genre (position, mouvement incomplet, amplitude insuffisante), ce qu'on voit sur le corps, la phrase du bandeau et une phrase courte pour la voix. La commande n'est **pas une donnée** : la page rend un texte à coller dans la conversation, et une faute développée part dans ses seules maisons (`detections.js`, `messages.js`, `sons.json`). Son brouillon (`dev.fautes`) n'est **jamais jeté au déploiement**, contrairement à celui des fiches : une commande s'écrit sur plusieurs soirées. Les extrémités d'un mouvement compté y sont nommées par leurs jetons et décrites par les zones de l'instrument — `debut` et `fin` sont des moments du comptage, pas des postures (le `debut` d'un squat est en bas).

**Vidéo d'un mouvement** (`videos.js`) : `videos/<fichier_video(nom)>`, nom **dérivé** du nom du mouvement — pas de champ ni de liste à tenir. **Une vidéo absente est une absence d'illustration, jamais une panne** : `montrer_video` garde son cadre caché tant qu'elle n'a pas chargé, et le laisse caché sur une erreur (même règle que les sons). Elle s'affiche sur la fiche, dans le guide du premier passage, dans la carte « Consignes » du HUD et sur la démo. **Une vidéo qu'on ne voit pas ne décode pas** (`jouer_si_visible`) : sur l'iPad, elle disputerait sa puissance à la détection de pose. `verifier_donnees` refuse une vidéo **orpheline** (mouvement renommé) ; une vidéo manquante n'est pas une erreur, on les tourne par lots.

### Coach vocal (`annonces.js`, `lecteur.js`, `sons.json`)

Il n'y a **aucun TTS** : toutes les voix sont enregistrées à la main. D'où la règle : **une annonce se compose, elle ne s'enregistre pas en entier.** Une phrase est une suite de briques, chacune enregistrée une fois. **L'écrit est gratuit, la voix est chère** : l'écran peut tout dire, la voix factorise.

- **Deux critères décident d'un découpage** : la **recombinaison** (le nom d'un mouvement se dit derrière trois amorces — « prochain exercice », « le premier exercice sera », « pour finir ») et la **couture**, qui doit tomber sur une pause que la phrase a déjà. D'où une charge enregistrée **entière** (« prépare un haltère de 8 kilos ») : couper avant le nombre tombe dans un groupe nominal et s'entend.
- **Le nom du fichier est le texte prononcé**, normalisé (`normaliser_nom`) : la feuille de prise de son se **dérive** (`lister_annonces.mjs`) au lieu d'être tenue à la main. `sons.json` porte `textes` *et* `briques` ; `verifier_annonces` contrôle que chaque brique porte le fichier que son texte produit, l'absence de collision, la longueur des noms, les orientations, les amorces de `Circuit` et les changements, et que la charge cousue par fichiers (`fichier_assemble`, ce que fait l'application) mène au même nom que son texte.
- **L'amorce se tranche dans `Circuit.amorce_annonce(bloc)`** (comparaison d'identité, pas d'index ; une séance d'un bloc est « premier »).
- **Une séquence est indivisible** (`Lecteur.sequence` empile une seule entrée). **Un fichier absent est un silence, jamais une panne** : on enregistre par lots.
- **Une clé inconnue de `fichiers` se tait** (`coach()` ne lève pas) : une table de clés qui ne lève pas se vérifie de l'extérieur. Rétablir un palier sonore demande sa clé, son fichier, sa priorité et le seuil qui l'appelle — tous, ou aucun. **Un fichier que rien ne déclare est aussi muet qu'un fichier absent** : relancer le diff entre `sons/` et ce que réclament les tables.
- **Corrections de forme : une clé, deux canaux.** La clé `forme_*` qu'une détection rend désigne la phrase du bandeau (`messages.js`) **et** la phrase courte dite (`sons.json`, `textes` + `briques` + `fichiers`) ; une faute sans voix se tait d'elle-même. `annoncer_faute` (`moteur.js`) ne la dit que si elle **dure** (`DUREE_AVANT_CORRECTION`), la redit tous les `RAPPEL_CORRECTION` tant qu'elle persiste, et une interruption ouvre un nouvel épisode ; le repère vit sur le bloc (`CHAMPS_TEMPORELS`). Une amplitude manquée se dit une fois, à la répétition comptée, **avant** les encouragements (une fin de série vide la file). Priorité 4 : sous les événements, au-dessus du rythme. `verifier_annonces` refuse une voix `forme_*` sans message du même nom — le moteur ne l'appellerait jamais.
- **Lecteur** : un son à la fois ; file à priorités ; un événement ≥ 5 vide les petits sons en attente ; un **blanc entre deux phrases** (`silences.entre_annonces`), mais **un chiffre n'est pas une phrase** — un son de rythme (priorité ≤ `silences.priorite_rythme_max`) part tout de suite et remplace celui de son espèce. Délai minimal par type (`delais`), sans quoi une correction se répète à chaque image. `silence_avant` (`silences.presentation`) sur la seule annonce longue (présentation du prochain exercice) ; **sous `silences.repos_minimal` secondes de repos, on n'annonce que ce qui vient** ; sans repos, le changement de bloc se détecte via `_derniere_serie_terminee`.
- **Sortie amplifiée** : sur l'iPad, la musique (Spotify) et le coach partagent un seul volume système, et les prises sont ~10 dB sous une musique masterisée. Tout son passe par la chaîne de `_brancher_sortie` (gain `sortie.amplification_db`, puis un limiteur qui rabat les crêtes), construite dans `_adopter` — un contexte recréé a la sienne. Sans la clé, 0 dB : le son tel qu'enregistré. Se règle à l'oreille, sur l'appareil, musique en route.
- **Écouteurs** : un contexte qui sort de `running` est relancé ; un `devicechange` **recrée** le contexte (WebKit garde parfois un contexte « running » muet) ; une entrée jouée sur un contexte arrêté est jetée ; une relance refusée s'arme sur le prochain `pointerdown`. `son_actif()` alimente le voyant du HUD.
- **iOS** : le son se prépare **au clic** (`lecteur.preparer()` dans le gestionnaire du geste) — sans lui, tout reste muet plus tard sans erreur.
- **Pendant les pauses** : `annoncer_temps_repos` (repère sur la séance, remis à `null` à chaque entrée en pause et au retour à l'effort ; `Math.trunc`). « À la moitié » a été retiré : **devant un coach trop bavard, chercher d'abord l'annonce qui redit ce qu'une autre dit déjà.**
- Les briques de cadrage dormantes restent déclarées : les retirer rendrait orphelins des `.wav` enregistrés.

### L'application (`app/index.html`)

**Ordre d'une séance : installation → guide d'exercice → préparation → effort.**
- **Installation** : la caméra vérifie que le corps entier tient dans l'image (`POINTS_DU_CORPS_ENTIER`, dérivé de `PARTIES`) pendant deux secondes ; une seule consigne, « recule ». Elle se referme sur ce seul contrôle, sans geste. C'est **sa sortie** qui présente le premier exercice (`fermer_installation`) ; la branche `preparation` d'`annoncer_changement` est délibérément muette (la phase est posée dès le constructeur). Le voile de repos est retiré pendant qu'on se place, le HUD masqué.
- **Guide d'un exercice** (premier passage sur un mouvement) : suspend le comptage sans suspendre la séance — un drapeau de page, **pas une phase** ni `statut = "paused"`. Calque en `z-index: 11`, hors de `#restOverlay`. Il ne redit pas l'exercice (l'annonce vient de passer) : il dit seulement « c'est la première fois qu'on fait cet exercice, regarde bien comment on fait, croise les bras quand tu as terminé » (briques `guide_*`, à la priorité de l'annonce, donc après elle). En début de séance, cette phrase remplace la consigne de préparation : `fermer_installation` annonce d'abord, puis ouvre le guide (`changer_exercice` rend vrai s'il s'est ouvert). Fermé **par geste**, il vaut pour l'entrée en série ; par le bouton « J'ai compris », non. Son `HoldPosition` est à lui. Il montre la vidéo du mouvement à côté des consignes, et la met en pause en se refermant.
- **Préparation** : un seul geste (bras en croix 1,5 s) lance la séance. Valider une série, remettre à zéro, ±1 : **3 s**. L'anneau de geste montre la tenue la plus avancée ; `progression_maintien` lit l'avancement **sans appeler `update`** (qui ne rend la transition qu'une fois), par `HoldPosition.progression_visible()` : **rien pendant `DELAI_AFFICHAGE_GESTE`** (0,75 s), puis de zéro à plein jusqu'à l'instant où le geste est pris — un poignet qui passait un instant devant l'autre faisait clignoter l'anneau. Le délai retarde l'anneau, pas le geste.
- **Tutoriel d'installation** (`tutoriel.js`, pur) : une seule étape, la place autour de soi — **avant d'ajouter une étape, chercher qui la dit déjà**. Il rend des clés : `sons.textes` pour le bandeau, `sons.briques` pour la voix.
- **Cadrage** (`cadrage.js`) : **ne parler que lorsque la détection ne peut pas travailler** — un contrôle de distance « approche-toi » se déclenchait sur une planche parfaitement cadrée, et a été supprimé. Les points requis sont **observés** (corps espion `Proxy`), pas déclarés. La `visibility` n'entre pas dans le calcul (elle s'effondre sur le membre éloigné d'une vue de profil). Il se tait au décompte. `message_de_cadrage` garde son contrat `{partie, action}` pour pouvoir rebrancher une consigne fine sans prise de son.

**Accueil d'un profil neuf** (`#ecranBienvenue`) : identité d'abord (pas de profil inventé), puis matériel, note, programme, gestes, appareil. **Tout ce qui se touche vient d'abord** ; la caméra s'ouvre à la fin et à partir de là plus rien ne se clique. Une phrase par écran, deux écrans par étape au plus, **aucune voix** tant qu'on lit — *le canal suit la distance*. Le questionnaire de matériel **part vide** (cocher à sa place, c'est répondre à sa place). Chaque étape écrit ce qu'elle récolte en la quittant (`recolter_etape`) ; `onboarding_termine` ne se pose qu'à la dernière. La garde est dans `ouvrir_pour_le_profil`, appelée au démarrage **et** au changement de personne. La pratique (`#ecranPratique`, balisage de `.installation`) est une machine à états (`PHASES_PRATIQUE`) : chaque consigne de geste dit à quoi il sert ; aucune phase ne se franchit au doigt ; « Passer cette étape » avance d'une phase. La caméra se demande depuis un bouton, avant tout `await` ; un refus n'est jamais bloquant ; en sortant, elle est suspendue et non fermée. L'accueil a sa propre boucle d'images.

**La mémoire des tutoriels vit sur le profil** (`tutos_vus`), pas en `localStorage` : deux personnes partagent la tablette. Toute lecture passe par `tutos_vus(profil)` (pas de champ = rien vu ; aucune migration n'ajoute de champ). `marquer_tuto_vu` rend un booléen pour éviter une écriture inutile.

**Profils** : « Qui s'entraîne ? » s'impose à chaque lancement (`profil_a_choisir`) ; le dernier profil est pré-désigné via `localStorage` (commodité de l'appareil, pas donnée d'entraînement). **Changer de profil ou de matériel reconstruit le moteur** (`construire_moteur`) : `Baremes` normalise l'inventaire une fois pour toutes. Profil en lecture seule par défaut ; quatre mesures facultatives (`poids_corps_kg` : jamais raccourci en `poids`, qui désigne la charge). Supprimer un profil descend les clés étrangères ; le dernier profil ne se supprime pas ; l'export est proposé avant.

**Historique** (`historique.js` + `stockage.js`) : la base est un **objet JS ordinaire** de collections reprenant d'anciennes tables (`utilisateur_id` seulement sur les racines `seances` et ancrages ; filtrer les racines puis descendre). Les identifiants sont croissants (`prochains_id`). `stockage.js` : **IndexedDB, la base entière dans un seul enregistrement** (écriture atomique) ; `charger()` ne lève jamais ; `sauver()` rend un booléen que l'écran de fin affiche. **L'export n'est pas un raffinement** : Safari purge les sites peu visités. Une collection ajoutée après coup est **optionnelle à l'import** — l'exiger rendrait illisibles les sauvegardes existantes. **`migrer`** amène une base ancienne à la version courante, au chargement (`stockage.charger`) comme à l'import, une seule fois (le numéro de version l'empêche de repasser). Version 2 : la séparation du squat et des fentes (`SEPARES_EN_VERSION_2`) — une ligne **chargée** prend le nom de la forme chargée, une ligne à vide garde le sien ; un ancrage sur ces noms est gardé mais rendu inerte (il recalait un barème disparu) ; les séances locales nomment la forme chargée ; une préférence de variante suit la tête de la chaîne. Version 3 : les séances modifiées sur l'appareil (`seances_locales`, communes à ses profils) deviennent une copie perso **de chaque profil**, sous le même nom (une perso déjà là l'emporte), puis `seances_locales` disparaît.
- **Les statistiques disent ce qui a été fait, les niveaux ce qui est prouvé** : `statistiques_exercices` garde les séries manquées (seules une série vide et une séance abandonnée sont écartées).
- **La charge est portée par la série** : `resume_series(series, mode)` est le point d'entrée unique des pastilles (`11×5 kg`, `15` au poids du corps, une durée sans charge).
- Un seul marqueur de progrès dans l'historique : la montée de niveau.
- Le `<summary>` d'une séance porte date, durée et nombre d'exercices ; le nom d'un exercice mène à sa fiche (avec retour à la séance lue).

**Écran de fin** : la même fiche que l'historique (`dessiner_seance`, `brancher_fiches_de_seance`), relue en base. L'écriture est automatique ; le bouton « Enregistrer la séance » confirme, ou réessaie si le stockage a refusé. Le ressenti s'y saisit, et après coup depuis l'historique (`ressentis_ui.js` ne décide rien, il propose les réponses qui changent quelque chose).

**Séances et programmes perso** : ce qu'un profil crée ou modifie dans l'application vit **sur le profil** (`seances_perso` `{nom: blocs}`, `programmes_perso` `{cle: programme}`, mêmes formes que les fichiers), jamais sur l'appareil — deux personnes partagent la tablette. Ils voyagent dans l'export et partent avec le profil, sans code. Toute lecture passe par `seances_perso(profil)` / `programmes_perso(profil)` (pas de champ = rien créé). Une clé de programme perso porte `PREFIXE_PROGRAMME_PERSO` (`verifier_donnees` le refuse à une clé commune). Le catalogue d'un profil est `catalogue_effectif(fichier, seances_perso)`, recalculé avec le moteur (`rafraichir_catalogue`) : **à nom égal, la perso remplace la commune** pour ce profil, et c'est ce qui laisse un programme commun cocher la copie modifiée (il relit l'historique par nom). Renommer une perso emporte les programmes perso qui la citent, pas l'historique ; une perso citée par un programme perso ne se supprime pas, sauf si une commune du même nom prend le relais.

**Éditeur de séances** : enregistrer écrit une séance perso du profil — modifier une commune en fait une copie qui la **masque** (bouton « revenir à la version commune ») ; « + Créer une séance » et « Dupliquer » ouvrent le même éditeur sur une séance neuve (`seance_editee` nul), qui n'existe qu'à l'enregistrement. Le nom se règle dans l'éditeur : **un nom commun n'est accepté qu'en modifiant cette commune** — neuve ou renommée, une séance qui le prendrait la ferait disparaître de la liste sans rien annoncer ; une perso sans commune du même nom se supprime (refusé si un programme perso la cite). La carte d'une séance perso porte la pastille « Personnalisée » (`.puce-perso`) ; une édition faite loin de l'ordinateur ne doit pas disparaître au déploiement ; corollaire : une correction de `seances.json` n'atteint plus cette copie. Règles : partir des valeurs du moteur ; la cible va dans le champ de son mode (`MODES_DUREE`) ; refuser à l'enregistrement (`problemes_des_blocs`, liste complète) ; un nom orphelin reste sélectionné (`optgroup` « Inconnu ») ; l'entrelacement est un **drapeau « avec le bloc suivant »**, recalculé (`normaliser_entrelacement`, `seance.js`). **L'éditeur des blocs est un module** (`editeur_seance.js`, habillé par `editeur.css` sous `.editeur-blocs`), commun à l'application et à l'outil maître : il édite et ne décide de rien — valeurs de départ et enregistrement appartiennent à la page, qui enregistre une **copie** de sa liste de travail.

**Liste des séances** : la carte est un `<article>` dont seule la zone de titre est un bouton (**devant un élément qui ne peut rien contenir, changer l'élément porteur**). Elle porte une **durée estimée** (effort + repos, sans transitions) : `duree_estimee` (`duree.js`) fait **jouer le `Circuit` lui-même** sur une horloge simulée — les repos d'un superset ne se recalculent pas à côté — sur le circuit que construit `circuit_a_jouer`, le même assemblage que `demarrer` (variantes puis objectifs), si bien que la carte annonce la séance qui sera jouée. Le temps d'une répétition vient de `tempo` (`reglages.json`) ; un tempo manquant n'affiche rien. **Choisir n'est pas commencer** : le clic sélectionne, « Démarrer la séance » lance — `verrou_ecran.tenir()` et la préparation audio au plus près de ce clic. Le contenu ne s'affiche qu'une fois (déplié). Les cibles figées et « 1re fois » restent visibles sans clic. La carte de programme (`programme_resume.css`) montre la semaine et, pour chaque semaine passée, son compte (`2/3`) et sa date, lisibles sans toucher ; toucher une case est une bascule ponctuelle ; `null` dans `programme_choisi` invite à choisir. **La carte ne règle rien de durable** : le rythme, le jour de début et l'ordre se règlent sur l'écran Programmes, sous le programme suivi (`dessiner_reglages_semaine`).

**Programmes du profil** : l'écran Programmes montre `programmes_du_profil()` (les communs, puis les perso, relus à chaque appel) ; un perso porte « Personnalisé » et se modifie, un commun se **duplique** en perso — seule façon de l'adapter sans toucher à celui des autres. Le créateur (`#ecranCreateurProgramme`, `editeur_programme.js`) choisit dans le catalogue **du profil**, perso comprises, et refuse par `problemes_du_programme`. Chaque carte porte ses étiquettes (zone, « sans haltère », `etiquettes_du_programme`) ; le **filtre** (zones présentes, « Sans haltère », « Avec mon matériel ») ne s'affiche qu'à partir de deux programmes, ne cache jamais le programme suivi, et se retient en `localStorage` (commodité de l'appareil). « Sans haltère » pose la règle du matériel à un moteur d'inventaire déclaré vide (`moteur_sans_haltere`, construit une fois).

**HUD** (`hud.js`, `hud.css`) : tout `hud.js` est une fonction de `donnees` (`payload_etat`) — ni requête, ni horloge, ni caméra. Les commandes s'exécutent via `brancher_commandes(executer)`, par **nom**. Pendant l'effort, **Pause** et « Série terminée » restent sous le doigt (la pause n'a pas de geste) ; les commandes secondaires vivent dans un menu qui s'ouvre vers le haut et se referme **au changement de phase**, jamais à chaque image. **Le voile de repos ne couvre plus l'image** : pendant une pause on se regarde comme dans un miroir (squelette non dessiné, détection maintenue pour les gestes), et tout ce qu'il dit tient dans un panneau à gauche (`.rest-panneau`), la prescription en grand (cible et charge). Il n'a plus de copie de la barre de progression : centrée sur toute la largeur, elle passait sous le compteur ; la colonne droite est posée au-dessus de la barre du bas. La fiche à l'écran est un `<details>` replié pendant l'effort, déplié en pause, au-dessus du voile de repos (`z-index: 7`) ; `fiche` (courant) et `fiche_suivante` (pendant `repos_exercice`) sont deux champs ; **deux choses qui ne changent pas aux mêmes instants demandent deux repères** (`fiche_affichee`, `fiche_en_effort`). La vidéo de la carte suit les deux : même clé que les consignes (celle du **prochain** mouvement pendant `repos_exercice`), et lue seulement carte ouverte (`toggle` couvre l'ouverture par la phase comme au doigt). La colonne droite est bornée sous la barre du haut : c'est la carte des consignes qui défile, jamais le compteur. L'image est en `object-fit: contain`, **jamais `cover`** (recadrer cacherait ce que le modèle analyse). Socle CSS : **`[hidden] { display: none !important; }`** — sans lui, une règle `display` neutralise `hidden` en silence.

**Mise en page** (iPad, iPhone, Split View) : **elle suit l'espace, jamais l'appareil** — aucune détection d'iPhone ni d'iPad : Safari sur iPad se déclare comme un Mac, et un iPad en Split View est aussi étroit qu'un téléphone. Tout se fait en CSS, en trois cas :
- **large** (iPad), la mise en page historique, inchangée ;
- **étroit** (`max-width: 760px`, téléphone debout) : trois bandes qui ne se recouvrent pas — la barre du haut sur une rangée (le nom de l'exercice cède en points de suspension, les libellés des pastilles disparaissent, leur couleur les dit), **l'image entre les deux** (le canvas est raccourci : la caméra filme en 3:4 et un téléphone debout a de la place au-dessus et en dessous), et en bas le compteur en ligne, les commandes, la progression. Pendant l'effort, les consignes sont masquées (illisibles à trois mètres) ; en pause, c'est le compteur ;
- **bas** (`max-height: 500px`, téléphone couché) : utilisable, sans plus — tout se resserre, la colonne ne garde que le compteur.

Les bords de l'appareil passent par des variables (`--bord-haut`, `--bord-bas`, `--bord-gauche`, `--bord-droit` sur `.stage`, `max(marge, env(safe-area-inset-*) + …)`) : la barre d'état est translucide, et sans elles la barre du haut passait sous la Dynamic Island et la progression sur la barre d'accueil. Une zone sûre nulle rend la marge d'origine, d'où un iPad inchangé. **Une hauteur de bande est une variable, pas une constante recopiée** (`--haut-barre`, `--haut-compteur`, `--pied`, `--image-haut`, `--image-bas`) : le panneau de pause et la colonne se calaient sur un `80px` qui supposait une barre d'une rangée, quand elle en faisait trois. `.defile` et l'installation suivent aussi les zones sûres ; sous 600 px, les onglets se partagent la largeur et le profil se réduit à son initiale (`data-initiale`) ; sous 760 px, tout champ de saisie est à 16 px (iOS zoome en dessous). Le guide d'un exercice se centre par `margin: auto`, jamais `align-items: center` : un contenu centré plus haut que l'écran sortait par le haut, hors d'atteinte du défilement. Une mise en page se vérifie dans l'aperçu (`resize_window`) en mesurant les boîtes (`getBoundingClientRect`, chevauchements, `scrollWidth`) plutôt qu'à l'œil ; les vraies zones sûres et la lisibilité à trois mètres ne se jugent que sur l'appareil.

**Graphique** (`graphique.js`) : rend une chaîne SVG, l'axe part de zéro. Au doigt : un appui montre le détail, un second dans les 500 ms ouvre la séance (reconnu par le temps et la cible, pas `dblclick`) ; cible de toucher transparente (`fill="transparent"`) plafonnée à la moitié de l'écart entre points ; `touch-action: manipulation` ; état `.actif` (`:hover` ne dit rien au doigt).

**Veille** (`veille.js`) : deux mécanismes. Le **verrou** (libéré quand la page se cache, repris sur `visibilitychange` ; demandé **depuis le gestionnaire de clic, avant tout `await`**) et, en repli, la **vidéo de la caméra lue** dans un élément attaché et rendu (un pixel quasi transparent, jamais `display:none`). L'état s'affiche dans le voyant du HUD, sans prétendre distinguer les causes d'un `NotAllowedError`.

**Caméra** (`camera.js`) : ouverte **une fois par session** — entre deux exercices les pistes sont désactivées, pas arrêtées (chaque `getUserMedia` peut redemander l'autorisation). **Une seule pose par défaut** (36 images/s contre 24 à quatre poses) ; `choisirPose` suit la même personne d'une image à l'autre. `preparerDetecteur` sérialise ses appels. **Ne pas oublier `camera.preparer()`** : sans détecteur, `detecter` rend `[]`, exactement comme une image vide. **Le corps a deux formes** : `peindre` veut la pose brute, les règles veulent le corps nommé (`construire_corps`). Une exception dans un `requestAnimationFrame` gèle le flux définitivement : la boucle attrape, trace et replanifie.

**Barres d'onglets** : rendues par `remplir_barres_onglets()` dans chaque `[data-onglets]`, **avant** le câblage générique ; le bouton de profil est délégué au document. L'écran de séance n'a pas de barre.

### Simulateur de progression (`dev/progression.html`, `simulation.js`)

Deux questions seulement : **où démarre chaque exercice** selon la note (1 à 10), et **ce qu'il demande séance après séance** à quelqu'un qui **réussit toujours sans rien répondre** — chaque séance monte donc d'un palier, et le parcours est le barème lu depuis le départ, changements de variante compris. **Pas de modèle d'athlète** : une première version simulait force cachée, fatigue et ressenti, et c'était trop compliqué pour la question posée. Tout passe par le chemin de l'application (`construire_progression`, `variantes_en_cours`, `historique.js`, `resultats_par_exercice`, `montees`) : rien n'y est une règle. Une famille par simulation (un athlète qui réussit tout ne fait dépendre aucun exercice d'un autre) ; le résumé de tous les exercices se remplit une tâche à la fois, et une correction ne recalcule que sa famille. Le volume d'une chaîne est exprimé dans l'unité de sa tête (`volume_comparable` : la forme à vide d'un mouvement chargé se traduit par la part du corps). **On signale les baisses de volume** (`baisses`), changements de variante compris, et on les **corrige à la main** : séries et cible d'un palier, écrites en **surcharges** du barème (`reglages.json`, fichier à coller en bas de page, brouillon jeté si le déployé change, comme `dev/baremes.html`). Jamais le poids : une surcharge vise un **numéro** de palier, qui ne tombe pas sur le même haltère selon le matériel — d'où les profils superposés, et d'où `verifier_donnees`, qui refuse une surcharge mal formée (elle ferait lever `Baremes.palier`). Le tableau des paliers montre tous les paliers, le parcours ceux qu'on vit : une performance qui vaut un palier plus haut y fait sauter. Des courbes identiques sont réunies en une seule ; les couleurs de séries sont `--serie-1…7` de `palette.css`, dans cet ordre (vérifié pour le daltonisme contre le fond), et suivent le profil, jamais son rang.

### Démo et banc d'essai (`demo/index.html`)

Un exercice isolé, comptage et voix, sans séance ni historique : le livrable pour un testeur et l'outil de diagnostic. Elle lit les mêmes `mouvements.json` + `fiches.json` (mouvements comptés, `est_compte`, triés ; ceux `en_developpement` d'abord, sous leur propre titre et bordés de tirets) et les sons de `../sons/`. Les résultats s'accumulent (`localStorage`, attaché à l'origine : ne pas changer d'adresse) ; un QCM par exercice et un seul bouton de copie. Fluidité par minute **de caméra**, cumulée d'un exercice à l'autre, en histogrammes (arrondis, pas tronqués) ; un écart de plus de deux secondes est une suspension. `?poses=N` force le nombre de poses ; le nombre de répétitions à faire se choisit sur la fiche (10, 20 ou 40, retenu par l'appareil : une application installée n'a pas de barre d'adresse), ou par `?cible=N` (dix pas de montées de genoux tiennent en trois secondes).

**Le banc d'essai** (visible par défaut, `?banc=0` le masque) : jeton brut, armement, part de **temps** par jeton dès la préparation (`perdu` quand il n'y a pas de corps), jauges des instruments, angles sur l'image, faute de forme en direct, et un **journal des tentatives** (`SuiviTentatives`) : aller complet, aller interrompu, retour incomplet ; une tentative n'est un échec qu'au-delà de 30 % du chemin (`PROGRESSION_SIGNIFICATIVE`), sinon c'est une hésitation. Le journal dit tout ce que le suivi voit ; la consigne « Ça ne compte pas » attend, comme en séance, que l'échec soit confirmé (`confirmer_verdict`). Le résumé copié enregistre des nombres.

### Déploiement et cache

`scripts/empreinte_deploiement.py` (CI, copie `_site` seulement) marque chaque ressource locale de l'empreinte du commit (`camera.js?v=<sha>`, imports internes et `fetch("../donnees/*.json")` compris, adresses absolues jamais) : chaque fichier expire pour son compte, et un document neuf combiné à un module en cache échoue en accusant un code déjà corrigé. **Le document ne peut pas être marqué** : `version.js` relit `version.json` (seul fichier jamais marqué) en `no-store`, compare à sa propre empreinte (`import.meta.url`), et recharge sous `?maj=<empreinte>` en cas d'écart — sans toucher IndexedDB ni `localStorage`, et sans rien faire hors ligne. **Le sommaire du site** est à `sommaire.html` et à la racine (`scripts/sommaire.mjs`, joué par la CI sur `_site`). Son adresse propre existe parce que la racine a été une redirection vers la démo, qu'un navigateur peut garder en cache ; c'est `sommaire.html` qu'on met en favori. Il porte une carte par page `.html`, tirée de son `<title>` et de sa `<meta name="description">`, rangée par dossier. Une page ajoutée y apparaît d'elle-même ; `tester.mjs` refuse une page sans titre ni description, sans quoi sa carte ne dirait rien. **Les fiches de suivi** (`docs/exercices/`, hors du site) sont rassemblées de la même façon dans `dev/suivi.json` (`scripts/suivi.mjs <site>`, CI) : une page statique ne sait pas lister un dossier. Dérivé, jamais versionné ; en local, `node scripts/suivi.mjs web/static`.

**Les vidéos ne sont pas marquées** : leur adresse se construit à l'exécution (`adresse_video`), hors de portée de l'empreinte. Une vidéo remplacée sous le même nom met donc le délai de cache de Pages à arriver.

**En développement, utiliser `statique-dev`** (`Cache-Control: no-store`) : `python -m http.server` laisse le navigateur ressortir un module depuis son cache avec un statut 200, et *un import figé fait passer un code correct pour cassé*. L'entrée `statique` reproduit le déploiement.

**Vérifier une page dans le volet de prévisualisation** : un volet masqué ne déclenche aucun `requestAnimationFrame` — remplacer la fonction par un pas à pas avant le démarrage de la page. Une caméra se simule en remplaçant `getUserMedia` par le `captureStream()` d'un `<canvas>`. `HoldPosition` lit `performance.now()` : un test de geste doit laisser passer le temps réel. Le verrou d'écran ne se vérifie que sur l'appareil.

## Leçons générales

- **Un repli placé trop tôt répond à la place de celui qui savait**, et masque un branchement oublié. Il se reconnaît à ce que **deux causes opposées y produisent la même valeur** (détecteur absent = image vide ; bornes oubliées = table relative ; cible de test = échec). Devant deux vues de la même donnée, vérifier qu'elles passent par le même objet.
- **Une duplication reste invisible tant que les deux copies coïncident** ; c'est son premier écart qui se signale, souvent en production. Un jeu d'entrées dupliqué a le même défaut que le code qu'il surveille.
- **Une garde ne protège que ce qu'on lui a donné** : une recherche qui ne voit qu'une forme d'appel, un contrôle qui ne couvre que certains modules, un `grep -v` par numéro de ligne (il a masqué les deux appels orphelins qui empêchaient l'application de démarrer) — préférer un filtre par contenu, ou lire la sortie entière.
- **En JavaScript, un argument surnuméraire est muet** : une signature de raccourci est un site d'appel comme un autre (`coach_sequence` perdait sa clé de délai). Un renommage se vérifie aux **sites d'appel**, pas en appelant soi-même la fonction.
- **Un défaut en masque un autre** : après un correctif, rejouer le parcours entier, pas seulement l'étape visée.
- **Une consigne qui se déclenche à tort est pire qu'absente** : elle apprend à ne plus être lue. N'ajouter un critère de contrôle qu'après avoir nommé ce qu'il empêche.
- **Une correction en amont réveille les filtres en aval** (`completee` devenu honnête a faussé un graphe qui filtrait dessus).
- **Devant un diff massif et inattendu, se demander d'abord si les deux côtés lisent la même version des données.**
