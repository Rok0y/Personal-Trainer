# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Coach de fitness temps réel : la webcam détecte la pose (MediaPipe), l'app compte les répétitions, guide l'utilisateur à la voix (annonces françaises pré-enregistrées), enregistre l'historique des séances en SQLite, et expose une interface web locale (Flask) pour piloter la séance et consulter l'historique/records. Aucun clavier/souris n'est nécessaire pendant la séance : des gestes (bras en X, bras levés) pilotent la validation/reset des séries.

## Commands

```bash
python main.py          # lance l'app : caméra + serveur Flask (arrière-plan) + navigateur auto sur http://127.0.0.1:5000
```

Pas de linter ni de formatter configuré. Il n'y a pas de suite de tests au sens habituel, mais **neuf harnais de comparaison** qui vérifient que le portage JavaScript rend exactement les mêmes réponses que le Python : chacun se joue en deux temps, `python -m scripts.generer_<sujet>` écrit l'oracle et `node scripts/comparer_<sujet>.mjs` le rejoue et diffe.

```bash
for s in fixtures scenarios historique paliers niveaux ressenti objectifs programmes ligues; do
    python -m "scripts.generer_$s"
done
for s in detections seances historique paliers niveaux ressenti objectifs programmes ligues; do
    node "scripts/comparer_$s.mjs"
done
python -m scripts.verifier_hud     # les deux montages du HUD portent-ils les memes accroches ?
```

Les noms ne coïncident pas partout — `generer_fixtures` alimente `comparer_detections`, `generer_scenarios` alimente `comparer_seances` — parce que les deux premiers ont été écrits avant que la convention ne se fixe. Les fixtures ne sont pas versionnées (dérivées, quelques secondes à régénérer), donc **un comparateur lancé sans son générateur compare de vieilles réponses** : les régénérer tous avant une vérification d'ensemble. Node.js est requis pour la moitié de ce travail, et n'apparaît évidemment pas dans `requirements.txt`.

`node scripts/verifier_methodes.mjs` répond enfin à une question qu'aucun autre outil ne pose : **chaque `this.methode()` appelée existe-t-elle ?** Il vient d'un défaut réel — une méthode retirée de `camera.js` pendant que deux appels subsistaient dans la même classe, et l'application refusait de démarrer sur l'iPad. Trois choses l'avaient laissé passer, et aucune n'est un hasard : `node --check` ne voit rien (la syntaxe est parfaite, la résolution est à l'exécution) ; **aucun harnais ne couvre `camera.js` et aucun ne le peut**, puisqu'il importe MediaPipe depuis un CDN que Node refuse de charger — c'est le seul module du dossier dans ce cas ; et surtout **la recherche qui devait le trouver l'a masqué**, un `grep -v "camera.js:2"` destiné à écarter la ligne de définition écartant aussi les deux lignes d'appel, qui étaient aux lignes 226 et 238. *Un filtre par numéro de ligne ne distingue pas ce qu'il cache* — préférer un filtre par contenu, ou lire la sortie entière.

Une CI existe (`.github/workflows/demo.yml`) mais elle **ne lance aucun de ces harnais** : elle publie le site statique sur GitHub Pages à chaque push sur `main` ou `feat/portage-web`, et n'installe que numpy. Les harnais restent à lancer à la main.

`scripts/script_verification_positions.py` est un outil manuel qui ouvre la caméra pour vérifier interactivement la détection de pose/gestes. `scripts/script_niveaux.py` prend un profil en argument (`python -m scripts.script_niveaux Sophie`) et retombe sinon sur le premier : il n'y a pas d'écran de connexion en ligne de commande, et l'historique est cloisonné.

`scripts/script_verification_positions.py` et `audio/generer_annonces_manquantes.py` importent des modules du projet par chemin absolu (`mouvements.positions`, `session.seances`, ...) : lance-les avec `python -m` depuis la racine (ex. `python -m scripts.script_verification_positions`), pas en exécutant directement le fichier, sinon ces imports échouent.

## Architecture

Le point d'entrée est `main.py` : il possède la boucle caméra principale (une itération = une frame). Cette boucle orchestre à chaque frame, dans cet ordre : détection de pose → détection des gestes de contrôle (bras en X / bras levés) → avancement de la machine à états de la séance (`seance.update()`) → déclenchement du coach vocal sur changement de phase → exécution du mode d'exercice courant (`executer_mode`) → dessin du squelette → encodage JPEG de la frame pour le flux web.

**Tout texte destiné à l'utilisateur porte une clé** (`core/messages.py`).
C'est la convention du coach vocal (`audio/coach.py`, où `"debut_serie"` désigne
un `.wav`) étendue à l'écrit : une fonction d'erreur d'exercice retourne une clé
et non une phrase, `session.moteur.mettre_a_jour_erreur` la résout, et
`texte()`/`libelle_etape()` ne lèvent jamais — elles tournent dans la boucle
caméra, où une exception non rattrapée gèle le flux vidéo. Une clé inconnue rend
donc `None`, c'est-à-dire rien à l'écran. Conséquence utile : un détecteur
inachevé qui retournerait `True` reste muet, alors qu'il affichait auparavant le
texte « true » dans le bandeau. **Ajouter un message se fait dans ce module, pas
en dur là où il est produit** : sinon l'étape audio devra le retrouver à la main.

Quatre champs de `core/state.py` portent ces messages, et ils ne se confondent
pas : `erreur` reproche une faute de forme (bandeau rouge), `consigne` dit quoi
faire (bandeau bleu — « place-toi devant la caméra », « croise les bras pour
démarrer »), `stage` reste le **jeton brut** du détecteur et `etape_libelle` sa
traduction française. Le front affiche `etape_libelle` et n'a plus à deviner la
posture en comparant des chaînes. `fiche` porte les consignes de l'exercice
courant.

**L'état d'une séance appartient à un objet, pas à un module.** `core/state.py` expose la `dataclass` `EtatSeance` et le `SessionManager` en détient une instance (`controleur.etat_seance`) : c'est lui l'objet « une session », puisqu'il porte déjà la séance, le statut et le `RLock` qui le protège des deux appelants (boucle caméra et requêtes HTTP). C'était auparavant un espace de noms de variables globales de module, c'est-à-dire l'hypothèse « une seule séance à la fois » inscrite dans la *forme* du code plutôt que dans une décision : une deuxième personne connectée écrasait la séance de la première. Une seconde session ne demande désormais qu'un second `SessionManager`. Trois règles tiennent ce découpage. (1) **L'instance est remise à zéro, jamais remplacée** — `main.py` en garde une référence dès le démarrage, et lui substituer un nouvel objet laisserait la boucle caméra écrire dans un état que plus personne ne lit. (2) **`session/moteur.py` n'importe pas cet état, il le reçoit en paramètre** dans ses treize fonctions — ne pas y réintroduire d'import. C'est ce qui a rendu le découpage indolore pour lui, au renommage du paramètre près : le seul appel qui le passait **par mot-clé** (`state=state` dans `main.py`) a survécu à un remplacement global, et la signature attendant encore l'ancien nom, ça n'a explosé qu'au premier exercice joué. Leçon générale : un renommage vérifié en appelant soi-même les fonctions ne prouve rien sur les **sites d'appel** — ce sont eux qu'il faut confronter aux signatures (`inspect.signature(...).bind`), ce qu'un parcours d'AST fait sans caméra ni séance. (3) **Le flux vidéo vit à part** (`core/flux.py`, `FluxVideo`, instancié une fois par `web/app.py` puisqu'il y a une caméra par processus) : tout ce que porte `EtatSeance` se porte en JavaScript, alors qu'une image JPEG encodée côté serveur n'existe pas dans le navigateur, où c'est la caméra de l'appareil qui affiche la sienne. La frontière du portage est ainsi lisible dans les types et non dans un commentaire. Le nom `etat_seance` évite enfin la collision avec `SessionManager.etat()`, qui décrit le statut du contrôleur et non la séance.

Machine à états de séance (`session/`) :
- `circuit.py` — `Circuit` (une séance en cours) et `BlocExercice` (un exercice configuré : mode, séries, répétitions/durée, repos). Gère les phases (`preparation` → `exercice` → `recuperation_serie` → ... → `termine`/`abandonne`), la progression entre séries/exercices, et l'entrelacement de deux exercices (`entrelace_avec`, ex. superset gauche/droite) — logique la plus délicate du fichier (`_est_entrelace`, `terminer_serie`).
- `moteur.py` — `executer_mode` dispatche vers `gerer_mode_repetitions` / `gerer_mode_maintien` / `gerer_mode_chrono` / `gerer_mode_amrap` / `gerer_mode_echauffement` selon `bloc.mode`. Chacune calcule la progression de la série courante et, une fois la cible atteinte, appelle `_finaliser_serie` (termine la série + réinitialise les champs temporels du bloc via `Circuit.reinitialiser_etat_serie` — un seul endroit connaît la liste de ces attributs, à ne pas redupliquer si un mode est ajouté). Toute fonction de mode doit retourner un 3-uplet `(derniere_rep, repetitions, serie_terminee)` : `main.py` le déballe tel quel, et un mode qui retourne moins plante à chaque frame.
  **Le temps est mesuré de deux façons incompatibles dans ce fichier.** `gerer_mode_chrono` et `gerer_mode_amrap` utilisent un temps *mural* (`debut_chrono` posé une fois, puis `maintenant - debut_chrono`) : l'horloge continue de courir quand la fonction n'est plus appelée, donc ces modes ne se mettent pas en pause quand l'utilisateur sort du champ ni pendant une pause web. `gerer_mode_maintien` et `gerer_mode_echauffement` accumulent au contraire des *deltas* image par image, ce qui les suspend naturellement (`main.py` n'appelle les modes que si un corps est détecté). **Tous deux plafonnent chaque delta à `INTERVALLE_MAX`** (0,5 s), pour qu'un retour dans le champ après une longue absence ne crédite pas d'un coup toute la durée écoulée : un gainage lâché vingt secondes ne rapporte qu'une demi-seconde au retour. La constante s'appelait `INTERVALLE_MAX_ECHAUFFEMENT` du temps où seul l'échauffement l'appliquait — `gerer_mode_maintien` a longtemps cumulé sans borne, défaut bénin en local mais béant dès que le flux passe par un réseau ou par un onglet que le système suspend.
  **L'horloge de ces deltas est celle de la séance, `seance.maintenant()`, et non `time.monotonic()` en dur** — `moteur.py` n'importe plus `time` du tout. Elle vaut `time.monotonic` par défaut, donc le desktop ne change pas d'un iota, mais un client distant peut la remplacer par sa **propre horodatation** : la latence du réseau sort alors du calcul, et il ne reste que la gigue, que le plafond ci-dessus borne déjà. Elle est portée par `Circuit` et **surtout pas par le module** : chaque client a sa ligne de temps, et un serveur multi-sessions en fera tourner plusieurs à la fois — une globale de module les mélangerait. **Toutes les horloges de `circuit.py` y passent aussi**, et pas seulement les deltas des modes : le décompte de repos (`debut_repos`) et `duree_totale` lisaient `time.time()` en dur — neuf appels —, si bien que la moitié de la séance restait accrochée à l'horloge murale. Ce sont toutes des **différences** (`maintenant() - debut_repos`), donc les router vers `self.maintenant` ne change aucune durée, et `time` n'est plus importé que pour le défaut `time.monotonic`. Ne pas y réintroduire d'appel direct : c'est **la** condition pour qu'une séance de 45 minutes se rejoue en quelques millisecondes, ce dont vivent le harnais de scénarios et, avec lui, la fidélité du portage JavaScript. Effet de bord utile : une vérification peut injecter une horloge fictive au lieu de bricoler le module `time`.
- **Barre de progression** : il y en a **deux, jamais deux en même temps**. `Circuit.blocs_comptabilises` / `series_terminees` alimentent celle des exercices, `blocs_echauffement` / `series_echauffement_terminees` celle de l'échauffement (segments bleus), et `dans_echauffement` décide laquelle le front affiche. C'est bien ce drapeau et non « reste-t-il des échauffements ? » : une séance qui n'en a aucun doit montrer la barre des exercices dès la première frame. `exporter_configuration` prend pour cette raison la **liste de blocs** à décrire plutôt qu'un booléen `inclure_echauffement` — il en faut désormais deux, et un second booléen qui interagirait avec le premier serait pire. Côté JS, la mémoïsation d'`initialiserProgression` porte sur la liste, donc la bascule redessine d'elle-même.
- **Mode `echauffement`** : un mouvement guidé au chrono, joué en tête de séance. Deux règles le distinguent d'un exercice ordinaire. (1) Sa détection de pose est *facultative* — `Exercice.detection` peut valoir `None` (voir `MODES_AVEC_DETECTION_OBLIGATOIRE` dans `circuit.py`), et quand elle existe elle n'alimente que l'affichage, sans jamais conditionner l'avancement du chrono : un échauffement ne doit pas pouvoir se bloquer. (2) Il est **invisible dans les statistiques** — exclu de la progression automatique, de la barre de progression et de l'historique. Le point d'entrée unique de cette règle est `est_echauffement(bloc)` dans `circuit.py`. Le filtrage se fait **à la source, dans `Circuit.exporter_resultats()`** : aucune ligne d'échauffement n'atteint jamais SQLite, donc `historique/database.py` et `historique.html` n'ont rien à exclure de leur côté — ne pas y rajouter de filtre, ce serait dupliquer la règle. Dans `accueil.html`, les blocs `mode == 'echauffement'` sont en plus regroupés dans un `<details>` replié par défaut, séparé des exercices réels, aussi bien dans « Voir le contenu » que dans le formulaire « Objectifs et commentaires » — un simple regroupement d'affichage (le check de mode y est dupliqué en Jinja, comme `MODES_DUREE` l'est déjà dans ce fichier), à ne pas confondre avec l'exclusion des statistiques décrite ci-dessus.
- **Refaire la dernière série** (bouton « Refaire cette série » des pauses, `POST /api/serie/refaire`) vise la série qui vient d'être terminée, et **ne se déduit pas de l'état courant** : `Circuit.terminer_serie` a cinq sorties, n'incrémente `serie_actuelle` que s'il reste des séries, et a parfois déjà changé d'exercice (`repos_apres == 0`). Le calcul depuis `phase` + `serie_actuelle` était donc juste après une série intermédiaire et faux d'un cran après la dernière — c'est précisément ce que faisait `serie_precedente`, qui reste réservée à la navigation *pendant* l'exercice. La règle tient désormais dans un repère posé à la source : `terminer_serie` écrit `_derniere_serie_terminee` (index d'exercice, numéro de série, état d'entrelacement) **avant toute mutation**, et `refaire_derniere_serie` le restaure. Ne pas oublier `_exercice_precedent_entrelace` dans la restauration : sans lui, un superset croit être au milieu d'un aller-retour qui n'existe plus. L'ordre compte aussi — `index_exercice` d'abord, puisque `recommencer_serie` nettoie l'état temporel de `bloc_actuel`. Le résultat déjà enregistré est effacé tout de suite (`oublier_resultat_serie`) et non laissé à la déduplication d'`enregistrer_resultat_serie` : entre le clic et la fin de la nouvelle série, un abandon exporterait sinon la tentative qu'on vient de désavouer. Le repère, lui, est conservé après coup — recliquer restaure le même état au lieu de reculer encore.
- **Terminer une série à la main** (geste bras en X dans `main.py`, bouton « Série terminée » du site) est le seul chemin qui peut produire un `completee` **faux** : `Circuit.terminer_serie_manuellement` interroge `objectif_serie_atteint`, point d'entrée unique de « cette série compte-t-elle ». Le forcer à `True`, comme c'était le cas, faisait passer tout abandon pour une réussite — et privait de données le filtre de `progression.niveaux.performance_realisee`, qui n'avait donc jamais rien à écarter.
  La durée réalisée se lit avec `moteur.duree_realisee(bloc, state)`, qui va chercher le compteur **du mode du bloc**. Ne jamais revenir à une chaîne `state.temps_maintien or state.temps_chrono or state.temps_echauffement` : ces trois globales de `core/state.py` survivent d'une série et d'un exercice à l'autre, et un gainage lâché avant la première seconde laisse `temps_maintien` à 0 — donc *falsy*. La chaîne retombait alors sur la durée du dernier échauffement et enregistrait 30 s pour une série jamais tenue. `moteur.oublier_durees(state)` remet ces compteurs à zéro à chaque fin de série, en complément de `Circuit.reinitialiser_etat_serie` qui, lui, ne nettoie que le bloc.
- `controleur.py` — `SessionManager` : façade thread-safe entre les commandes web (démarrer/pause/reprendre/naviguer entre séries/abandonner) et le `Circuit` actif.
- `seances.py` — catalogue des séances prédéfinies (code) + séances personnalisées (persistées dans `seances_personnalisees.json`), et construction d'un `Circuit` à partir d'une configuration de blocs. Deux catalogues cohabitent : `CATALOGUE_EXERCICES` (exercices comptabilisés : matériel, objectifs, records) et `CATALOGUE_ECHAUFFEMENTS`. Ils restent séparés parce qu'ils n'alimentent pas les mêmes écrans, et sont fusionnés par `catalogue_mouvements()` uniquement pour *valider* une séance. `construire_circuit` refuse désormais un mode inconnu et un mode exigeant une détection sur un mouvement qui n'en a pas — mieux vaut un refus à l'enregistrement qu'un `TypeError` en pleine séance.
  **Un bloc porte `repetitions` et `duree` en même temps, et seul le mode dit lequel est joué.** C'est volontaire — changer de mode ne doit pas perdre l'autre valeur —, mais ça interdit le `repetitions or duree` qui traînait dans les affichages : il prend le premier non nul, c'est-à-dire parfois celui que le mode ne joue pas, et lui colle l'unité de l'autre. Un échauffement de 30 s saisi avec 10 répétitions s'annonçait « 1×10 s » sur la liste des séances de l'application. Le point d'entrée unique est `cible_du_bloc(bloc)` (`session/circuit.py`, jumeau dans `circuit.js`), adossé à `MODES_CIBLE_TEMPORELLE` — même liste que le `MODES_DUREE` des gabarits **plus l'AMRAP**, parce que celui-ci décide de ce qui fait avancer la série et non de ce que le formulaire présente. `construire_circuit` refuse en conséquence une **cible nulle dans l'unité jouée**, des deux côtés, et `problemes_des_blocs` la signale dans l'éditeur de l'application : une durée à zéro achève chaque série à la première image, si bien que la séance entière défile en une fraction de seconde et affiche son écran de fin — un défaut spectaculaire et parfaitement muet. `demarrer()` rejoue cette vérification avant de construire quoi que ce soit, pour qu'une séance déjà stockée dise *pourquoi* elle ne part pas.
  **Le nom d'une séance est à la fois sa clé et son titre à l'écran.** Il n'y a pas de champ « libellé » à côté : les séances ont été renommées en noms lisibles (`upper_push` → `Upper Push`, `jambes_abdos` → `Jambes et abdos`, `Séance bas du corps` → `Bas du corps`) plutôt que doublées d'un second nom qu'il aurait fallu tenir à jour. Ce nom est **référencé en cinq endroits qui ne se parlent pas**, et en rater un ne lève rien — ça rend simplement muet ce qui s'appuyait dessus : les clés de `seances_personnalisees.json`, les **valeurs** du dict `seances` de chaque programme (sans quoi `liaison_seances` rend None et le programme ne pilote plus rien), `seances.nom_seance` en base (« dernière fois » et `prochaine_seance`), `utilisateurs.seance_initiale`, et les clés de `CATALOGUE_SEANCES` — celles-ci doivent rester alignées sur le JSON qui les masque, faute de quoi les deux orthographes cohabitent et l'accueil affiche deux fois la même séance. `python -m scripts.renommer_seances` fait les quatre premières (table en tête de fichier, idempotent, `--essai` pour voir avant) ; la cinquième est du code, à corriger à la main. Conséquence assumée : une base d'application déjà installée garde son historique sous les anciens noms jusqu'au prochain import.
  Attention : `seances_personnalisees.json` **masque** le catalogue Python. Les séances qui y figurent (`Bras`, `Upper Push`, `Jambes et abdos`…) ignorent totalement leur définition dans `seances.py` — éditer le code pour elles n'a aucun effet au runtime. Depuis le branchement du moteur de progression, le poids, le nombre de séries et la cible qui y sont stockés sont de toute façon **écrasés au chargement** pour tout exercice doté d'un barème et non marqué `cible_manuelle` : le JSON ne fait plus autorité que sur la structure (quel exercice, quel mode, quels repos, quel entrelacement).

Progression (`progression/`) : le moteur de niveaux, qui pilote les cibles des séances (`appliquer_a_blocs` / `appliquer_a_circuit`). La seule table qu'il écrit est `corrections_niveaux` ; tout le reste de son calcul est dérivé de l'historique à chaque lecture.
**Le principe directeur du dossier est la distinction niveau / objectif, et rien ne doit la brouiller.** Le *niveau* est le plus haut palier **jamais** validé : un record, une preuve stricte (toutes les séries, sans exception), qui ne recule jamais et vit dans `niveaux.py`. L'*objectif* est ce que la prochaine séance demande : un plan, qui monte ou descend selon la réussite et le ressenti, et qui vit dans `objectifs.py`. Un objectif peut donc légitimement passer **sous** le niveau — c'est un délestage, pas une régression, et l'écran des records continue d'afficher le niveau acquis. Caler l'un sur l'autre était l'ancien défaut : une seule série manquée au développé épaule (12, 9, 12 à 8 kg) renvoyait à 3x15 à 5 kg, deux crans d'haltère en arrière, parce que c'était le dernier palier *pleinement* validé.
- `paliers.py` — le barème d'un exercice. Un palier est un triplet (poids, séries, cible) et un *niveau* en est l'index, à partir de 1. **L'invariant est le volume** (`séries x cible x poids`), qui ne redescend jamais d'un palier au suivant : après une hausse de poids, la cible repart de la plus petite valeur qui tient le volume déjà atteint, jamais de `cible_min`. Les tranches ont donc des longueurs inégales et le barème se **parcourt** (`_iterer_tranches`) au lieu de se calculer par arithmétique modulo — ne pas « simplifier » en recalculant un index direct, ça casserait l'invariant. L'ordre des bascules est cible → poids → séries ; un exercice au poids du corps n'a qu'une valeur de poids possible, donc sa deuxième roue ne tourne jamais et le barème se réduit de lui-même à « cible puis séries », sans cas particulier. `est_suivi_par_le_moteur(nom)` est le point d'entrée unique de la règle « cet exercice a-t-il des paliers ? » : les échauffements n'en ont pas, l'AMRAP est laissé de côté (son objectif est un plancher, pas une cible).
  **Le bas du barème appartient au débutant.** `cible_min` est ce qu'on propose à
  quelqu'un dont l'historique ne prouve rien ; le fixer au niveau d'un pratiquant
  confirmé laisse un débutant hors barème, donc **sans aucun objectif**. Sur les
  mouvements au poids du corps il est délibérément très bas. En baisser un est
  sans danger tant qu'on ne touche **ni `series` ni `poids_min`** : l'échelle de
  charge n'ayant qu'une valeur, la première tranche s'allonge par le bas et tous
  les paliers supérieurs se décalent d'une *constante*, sans changer de contenu.
  Toucher `series` ou `poids_min` fait au contraire recalculer le départ de
  chaque tranche par `_premiere_cible`, et rebat tout le barème. **`cible_max`
  aussi**, et c'est le réglage par lequel on ajuste un barème à un programme :
  il fixe le volume de fin de tranche, donc l'entrée de la suivante. Le baisser
  fait entrer les séries en jeu plus tôt — tant qu'il reste haut, le barème
  épuise les répétitions avant d'ajouter une série, et une prescription écrite
  en 6 séries n'a aucun palier de même forme.
  Piège du **baisser** : les séances déjà enregistrées portent des cibles qui
  peuvent désormais dépasser `cible_max`. `ressenti._cible_visee` ne sait alors
  plus les traduire en niveau, et l'objectif proposé retombe **sous** le niveau
  acquis — observé sur les fentes en passant de 15 à 10. C'est transitoire : la
  première séance jouée sur le nouveau barème rétablit un repère valide.
  Les **variantes assistées** (pompes inclinées, pompes et gainage sur les
  genoux, squat sur chaise) sont des exercices comptabilisés à part entière, pas
  des échauffements : elles ont un barème, des records, une progression. Chacune
  réutilise la détection du mouvement complet quand elle reste valable — seul
  `squat_sur_chaise_detection` est propre, parce que le repère coude-genou de
  `squat_detection` suppose des haltères qui pendent le long du corps.
  **Un angle ne se lit pas depuis n'importe quel point de vue, et c'est un piège
  récurrent** : les landmarks sont exploités en deux dimensions, or un angle dont
  la flexion se fait dans le plan sagittal — le genou, la hanche — est illisible
  de face, où le mouvement va *vers* la caméra. Mesuré sur une pose de face
  plausible, le genou ne descend pas sous 124° au plus profond d'un squat, là où
  le seuil en exigeait 110 : la détection restait bloquée sur `"fin"`, ne
  s'armait jamais et ne comptait rien — un testeur a fait l'exercice entier pour
  zéro répétition. Avant d'écrire une détection, se demander de quel côté sera la
  caméra, et préférer un repère **vertical** (une hauteur rapportée à un segment
  du corps, comme `_descente_hanche`) dès que la fiche demande une vue de face.
  Toute
  variante doit être inscrite aux **trois** endroits : `CATALOGUE_EXERCICES`,
  `MATERIEL_EXERCICES` (lu par `nombre_halteres`, donc par l'échelle de poids) et
  `SPECS`.
  **Le barème n'a pas de fin.** Une fois l'haltère le plus lourd et le plafond de séries atteints, il ne reste qu'un axe : les répétitions, qui montent alors sans plafond. C'est la *tranche ouverte* — `longueur` à None dans `_iterer_tranches` —, et elle a deux conséquences. D'abord, aucun objectif n'est jamais « hors d'atteinte » : il peut demander beaucoup de répétitions, mais son palier existe toujours (les états `hors_atteinte` d'un programme et `maximum_atteint` d'un niveau sont donc devenus inatteignables ; le code les conserve parce que `palier()` peut encore retourner None sur un exercice sans barème). Ensuite, « nombre total de paliers » n'a plus de sens — il n'existe qu'un `dernier_palier_borne`, qui repère où commence cette dernière tranche.
  Deux pièges. Le générateur de tranches est **infini** : il se termine toujours par la tranche ouverte, donc tout appelant doit poser sa propre condition d'arrêt ; celle de `_niveaux_candidats` s'appuie sur la monotonie du volume, pas sur une borne arbitraire. Et une spec à `cible_max=None` décrit un barème déjà linéaire, que `_iterer_tranches` ne sait pas traiter — chaque fonction publique la court-circuite en amont. Et une surcharge de palier ne peut que **corriger** un palier existant, jamais en insérer ni en supprimer : le décalage rendrait faux tous les niveaux au-dessus et changerait rétroactivement le sens de l'historique déjà interprété (c'est aussi ce que `signature()` sert à détecter, pour un futur cache).
  **Le jumeau JavaScript est `web/static/js/paliers.js`**, avec `materiel.js` pour l'inventaire. Les specs, les échelles et le matériel par exercice sont **exportés** du Python (`donnees/baremes.json`, écrit par `preparer_demo`) : aucune valeur de barème n'est écrite côté JS. `progression/paliers.py` n'ayant que des imports de bibliothèque standard au niveau module, l'importer depuis `preparer_demo` ne tire ni pygame ni opencv et le workflow (numpy seul) continue de passer. `python -m scripts.generer_paliers` pose 33 625 questions — chaque palier jusqu'au niveau 200, les tranches, `niveau_pour` sur des performances tirées au hasard — et `scripts/comparer_paliers.mjs` diffe. Trois décisions le tiennent. (1) **L'inventaire est injecté, jamais lu depuis le profil** : un oracle qui dépendrait du matériel déclaré ce jour-là ne rendrait pas deux fois le même verdict. Cinq inventaires sont balayés, du non-déclaré au complet, parce que l'échelle de poids **décale toutes les tranches** — c'est d'ailleurs là qu'est apparu le seul vrai défaut du portage : le matériel par défaut n'a **qu'un exemplaire** au-delà de 10 kg, donc un exercice à deux haltères s'arrête à 10, et court-circuiter `normaliser` quand rien n'est déclaré rendait la gamme entière. (2) **On monte jusqu'au niveau 200**, bien au-delà du dernier palier borné : la tranche ouverte est une *autre règle*, et un port qui s'arrêterait plus tôt passerait vert sans jamais l'atteindre. (3) **Le harnais ajoute deux exercices fictifs** (`fixtures_paliers_specs.json`, jamais dans `baremes.json`) parce que le catalogue réel n'exerce ni les **surcharges de palier** ni le **barème sans fin** : mesuré, un sabotage qui supprimait la condition de poids de `_valide` traversait les 30 935 premières questions sans être vu, `_niveaux_candidats` filtrant déjà sur le poids — seule une surcharge peut placer un palier ailleurs, et c'est là que la condition sert. Avec les exercices fictifs, le même sabotage sort 35 divergences.
- `niveaux.py` — déduction du niveau depuis l'historique, **sans table de faits supplémentaire** : le niveau est le plus haut palier jamais validé. Règle idempotente, insensible à l'ordre des séances comme à leur suppression, et qui applique d'elle-même le « pas de recul ». Une performance valide un palier si elle est **au moins aussi lourde et au moins aussi volumineuse** — à poids égal, la répartition séries/répétitions est libre, ce qui crédite le travail lourd et court. Le jugement porte sur un exercice et non sur une séance : le statut `abandoned` est donc volontairement ignoré ici, contrairement à `statistiques_exercices`.
  `etat_niveau(nom)` est le format que consomment les écrans, et il distingue **trois situations qu'un affichage ne doit pas confondre** : `niveau` à None = hors barème (aucune performance n'atteint le premier palier, ce qui n'est pas « niveau 0 ») ; `maximum_atteint` = barème épuisé, `suivant` vaut alors None et il n'y a plus rien au-dessus ; sinon `suivant` décrit le prochain objectif. Tout code qui lit un niveau doit traiter ces trois cas — `palier(nom, niveau + 1)` peut légitimement retourner None.
  `montees_de_niveau()` rejoue le même historique mais dans l'**ordre chronologique** (l'inverse de `recuperer_historique`, qui rend le plus récent en tête) pour repérer, séance par séance, l'instant précis où chaque niveau apparaît — c'est ce qui alimente le badge de montée de niveau dans `historique.html`. Même règle de non-recul et même traitement des ancrages que `niveaux_par_exercice` ; les deux fonctions dupliquent volontairement cette boucle plutôt que de la factoriser, l'une accumulant un maximum, l'autre un événement par franchissement.
  **Le jumeau est `web/static/js/niveaux.js`**, vérifié par `scripts/generer_niveaux.py` et `scripts/comparer_niveaux.mjs` : 360 historiques tirés au hasard, 2 259 séances, 1 440 réponses comparées. Les historiques sont volontairement **tordus** — séries inégales et inachevées, modes qui ne correspondent pas au barème, exercices répétés dans une même séance — parce que des séances plausibles n'éprouvent aucune des trois règles du module : des séries identiques rendent `min` équivalent à `max`, et des séries toutes complètes ne testent jamais le filtre `completee`. Les **ancrages sont posés au milieu** de l'historique, jamais au bout : à la fin ils ne feraient table rase de rien, au début ils ne serviraient jamais de plancher, et c'est entre les deux que leurs deux effets se voient — le sabotage qui décale leur borne d'une séance ne sort que 11 divergences, contre plus de mille pour le maillon faible, donc sans ce placement il serait passé inaperçu. Une divergence d'API assumée : `etats_niveaux` lit les ancrages en base côté Python, alors que le JavaScript les reçoit en argument — il n'a pas de base à lire, et le harnais détourne la lecture Python pour comparer les deux, du même genre que le coach injecté du moteur.
- `objectifs.py` — **c'est ici que le moteur pilote les séances**. `objectifs_par_exercice` applique deux règles, dans cet ordre : (1) le **repère de la dernière séance** fourni par `ressenti.py` — le palier alors demandé, plus ou moins ce que la réussite et le ressenti lui valent ; (2) à défaut de repère, le *premier palier non validé* (`niveau + 1`), et si le barème est épuisé, le dernier palier atteint plutôt que rien. C'est la règle (2) seule qui s'appliquait avant le ressenti, et elle reste le repli de tous les cas où l'historique ne dit rien d'exploitable. Conséquence directe : `Circuit.appliquer_progression()` **ignore les exercices suivis** — leur appliquer en plus son `+1` historique les ferait sauter un cran par séance réussie ; il ne sert qu'aux exercices sans barème, dont il ne reste aujourd'hui aucun : tout `CATALOGUE_EXERCICES` a un barème et les mouvements qui n'en ont pas sont des échauffements, que cette méthode saute aussi. Elle ne s'exécute donc plus sur aucune donnée réelle — le vérifier avant de la modifier plutôt que de lui ajouter des règles. Trois raisons, et trois seulement, font qu'un bloc échappe au moteur : pas de barème, un mode qui ne mesure pas la même chose que le barème (un exercice en `chrono` ne peut pas recevoir une cible en répétitions), ou une **cible manuelle**.
  **« Le moteur ne pilote pas ce bloc » et « le moteur n'a encore rien à proposer » sont deux réponses opposées**, d'où `_pilote_par_le_moteur` séparé d'`objectif_pour` : la première laisse la cible du fichier, la seconde déclenche un test de calibration. Le signal d'« aucune donnée » est `exercices_sans_donnees`, c'est-à-dire `etat_niveau["niveau"] is None` — **pas** une absence dans `objectifs_par_exercice`, qui ne se produit jamais : `etat_niveau` propose toujours `suivant`, donc le palier 1, à qui n'a rien fait. Confondre les deux programme un débutant au hasard au lieu de le mesurer. Les deux `appliquer_a_*` acceptent `sans_donnees` en argument pour la même raison qu'`objectifs` : `catalogue()` boucle sur toutes les séances et chaque calcul relit tout l'historique.
  `appliquer_a_blocs` (dictionnaires) et `appliquer_a_circuit` (`BlocExercice`) existent tous deux parce que les séances arrivent sous deux formes — le JSON des séances personnalisées et les `Circuit` écrits à la main du catalogue Python, qui ne passent jamais par `construire_circuit`. La règle, elle, vit dans le seul `objectif_pour`. **Les deux chemins doivent rester alimentés** : `creer_seance` pour la séance jouée, `catalogue()` pour l'affichage — sinon l'accueil annonce une cible que la séance ne joue pas.
- **Les ancrages** (`corrections_niveaux` en base) recalent un niveau que l'historique ne peut pas prouver : séance faite sans l'app, reprise après blessure, démarrage d'un nouvel utilisateur. Un ancrage agit **de deux façons à la fois** — il fait table rase de l'historique antérieur *et* sert de plancher. C'est la table rase qui lui permet de corriger un niveau vers le bas ; un simple plancher ne saurait que le relever. Le repère chronologique est `apres_seance_id`, **pas la date** : les dates de séance sont stockées en `JJ/MM/AAAA`, format dans lequel une comparaison de chaînes est fausse (`31/08` > `02/09`), alors que les identifiants sont `AUTOINCREMENT` donc strictement croissants. C'est un journal : on ajoute, on n'écrase pas, et seul le **dernier** ancrage d'un exercice compte pour le calcul du niveau (`recuperer_ancrages`). Le journal complet, lui, reste consultable et modifiable a posteriori : `recuperer_historique_ancrages` le liste en entier (plus récent en tête) et `supprimer_ancrage(id)` en retire une entrée précise — à distinguer de `supprimer_ancrages(nom)`, qui purge tout l'historique d'un exercice d'un coup. Supprimer une entrée qui n'est pas la dernière ne change rien au niveau calculé (par construction, seul le dernier compte) ; c'est un nettoyage du journal, pas une correction de niveau. L'API ne demande jamais un numéro de niveau (personne ne sait ce que vaut « niveau 27 ») mais une **performance**, dont le barème déduit le niveau — la même forme que prendra le test de calibration d'un nouvel utilisateur.
- `ressenti.py` — **de combien l'objectif bouge**, et point d'entrée unique de cette règle. Toute la progression tient dans la table `AJUSTEMENT`, indexée par le couple `(réussi, ressenti)` : réussi +1 par défaut, +2 si « facile », +3 si « trop facile » ; échoué 0 par défaut, −1 si « trop dur ». `None` y est l'absence de réponse, et c'est elle qui **reproduit exactement le comportement d'avant la feature** : le ressenti ne fait qu'accélérer ou freiner un moteur qui tourne déjà seul, jamais le remplacer. Les combinaisons absentes de la table (« facile » après un échec) retombent sur l'absence de réponse plutôt que d'inventer une règle — l'interface ne les propose pas, mais la page d'historique permet de saisir un ressenti a posteriori sans cette contrainte.
  Le repère de calcul est le **palier visé à la dernière séance**, jamais le niveau, et il n'est pas stocké : `_cible_visee` le re-dérive des colonnes `series_cibles`/`repetitions_cibles`/`duree_cible` déjà en base via `niveau_pour`. La réussite se lit avec `niveaux.niveau_prouve_par` (maillon faible, séries `completee` seulement) : une seule série manquée fait basculer l'exercice en échec. `base_apres_echec` porte la décision de **ne pas** faire reculer un objectif manqué — on redemande la même chose, et seul un « trop dur » explicite le fait descendre ; sa docstring explique pourquoi plafonner à `niveau + 1` serait une erreur.
  L'échelle stockée compte **cinq** valeurs (`trop_dur`, `dur`, `ok`, `facile`, `trop_facile`) alors que les écrans n'en proposent que celles qui *changent* quelque chose : « facile » et « trop facile » après une réussite, « trop dur » après un échec. **Pas de bouton neutre, volontairement** — ne rien sélectionner est déjà la réponse neutre, et en offrir un ferait croire qu'une réponse est attendue là où le cas courant est de passer son chemin. `ok` et `dur` restent acceptés et lisibles (ils valent l'absence de réponse) : les garder évite une migration le jour où on voudra les exploiter.
  **Le jumeau est `web/static/js/ressenti.js`** (`scripts/generer_ressenti.py` / `comparer_ressenti.mjs`, 1 101 réponses). La **table d'ajustement est comparée telle quelle**, ligne par ligne, en plus des historiques : c'est *toute* la règle de progression, et les combinaisons que l'interface ne propose pas (« facile » après un échec) n'apparaîtraient autrement qu'au hasard. Les trois sabotages qui comptent sont attrapés : « facile » ramené à +1 (17 divergences, dont la table elle-même), une séance abandonnée servant de repère (292), et surtout **le retour à l'ancienne règle** — replafonner un échec sur `niveau_acquis + 1` — qui en sort 337. Ce dernier est exactement le défaut que le module a été écrit pour corriger, et le harnais le reconnaît.
  **Les historiques aléatoires des harnais de `progression/` viennent d'un générateur partagé** (`scripts/historiques_au_hasard.py`), et il porte une décision qui vaut au-delà de lui : **une cible sur deux est prise sur le barème réel**. Tirée entièrement au hasard, elle ne correspond à aucun palier, `niveau_pour` rend None et `juger` abandonne la ligne — le harnais tournerait alors sur des historiques que le moteur ne sait pas lire, ce qui ne prouve rien. Même logique pour le mode, cohérent avec l'unité une fois sur deux seulement, et pour les séries, tirées *autour* de la cible pour visiter les deux côtés du seuil de réussite.
- `programmes.py` — les programmes sportifs, une couche de pure lecture par-dessus le reste. Un programme **ne stocke aucune progression** : il déclare une performance à atteindre par exercice, le niveau requis en est déduit, le niveau acquis vient de l'historique, et l'écart se recalcule à chaque affichage. Supprimer un programme n'efface donc rien, en ajouter un ne crée rien.
  **La ligne affiche les deux valeurs, et c'est indispensable.** `prescription` (ce qui est écrit dans le programme) vient en premier, `palier_requis.resume()` (sa traduction sur le barème) en second, et la seconde est masquée quand elle est identique. N'afficher que la traduction — ce que faisait `programmes.html` — rendait la page incompréhensible : on saisissait « 6x15 » dans l'éditeur et on relisait « 4x23 » sur la fiche, sans que rien ne relie les deux. Les charges s'affichent dans **deux conventions différentes sur la même ligne** (prescription = deux haltères, palier = un seul), d'où le rappel « (x kg par haltère) » quand `charge_haltere` diffère de `poids`, et la note d'explication posée une fois par programme.
  **Le barème fait foi : une exigence est calée sur un palier à l'enregistrement.** `_cale_sur_le_bareme`, appelée par `valider_programme`, remplace toute prescription par le premier palier qui atteint son volume — c'est donc le seul endroit où la règle vit, et le disque ne contient plus que des paliers valides. Avant, la prescription était stockée telle quelle et traduite à chaque affichage : deux valeurs cohabitaient (celle qu'on relit dans l'éditeur, celle que la page calcule), elles n'étaient jamais les mêmes, et rien ne disait laquelle faisait autorité. Le calage est **silencieux** — une saisie revient modifiée —, ce que l'aide de l'éditeur annonce explicitement. `etat_exigence` garde néanmoins l'affichage tolérant « prescrit · soit … sur ton barème » : il ne ressort plus qu'après un changement de spec, quand une exigence enregistrée sous l'ancien barème n'y correspond plus.
  **La traduction des prescriptions passe par le volume**, parce qu'un programme est écrit avec le matériel de son auteur : « 4x12 à 28 kg » n'a pas de palier correspondant si les haltères s'arrêtent à 10 kg, mais son volume, lui, se retrouve ailleurs sur le barème (`niveau_pour_volume`). `CHARGE_TOTALE` dit comment lire les charges écrites — pour les deux haltères réunis, ou pour un seul — et cette seule constante décide de la moitié des volumes exigés. Depuis que le barème se termine par une tranche ouverte, **aucune exigence n'est hors d'atteinte** : une prescription plus lourde que le matériel disponible se traduit simplement en davantage de répétitions à la charge maximale. Le drapeau `hors_atteinte` subsiste pour le cas d'un exercice sans barème, qu'`etat_programme` filtre déjà en amont.
  Le `pourcentage` d'un programme est la **moyenne des avancements** de ses exigences, pas la part de celles entièrement remplies : cette seconde mesure reste à zéro tant qu'aucune exigence n'est bouclée, ce qui affichait une barre vide alors que tout avait progressé. Les deux chiffres coexistent à l'écran (`pourcentage` et `atteintes`) parce qu'ils ne disent pas la même chose. Un avancement individuel est borné à 100 % : dépasser le niveau requis remplit l'exigence, ça ne fait pas déborder la barre.
  **Chaque libellé de séance d'un programme est relié à une séance jouable, et ce lien est une donnée.** `enregistrer_programme` appelle `synchroniser_seances`, qui écrit le couple `{libellé: nom de séance}` dans le champ `seances` du programme ; `liaison_seances` ne fait plus que le lire. C'était auparavant une heuristique par **recouvrement d'exercices** rejouée à *chaque affichage* : elle pouvait changer d'avis en silence, d'où le « via *upper_push* » qu'il fallait afficher partout pour la rendre vérifiable, et elle rendait None dès que le recouvrement était nul.
  **Adopter d'abord, créer ensuite.** Un programme s'écrit presque toujours après coup, sur des séances qui existent déjà — montées avec leurs échauffements, leurs repos, leur entrelacement. `seance_correspondante` cherche donc l'existante (nom identique aux accents près, puis meilleur recouvrement au-dessus de `RECOUVREMENT_MINIMAL` = la moitié des exercices du libellé) et on ne crée que si rien ne correspond. Le seuil n'est pas décoratif : sous la moitié, deux séances qui partagent un ou deux mouvements (des curls dans « bras » comme dans « Pull ») se confondent et le programme pilote la mauvaise. L'heuristique n'a pas disparu, elle ne sert plus qu'**une fois** ; ensuite c'est le lien écrit qui fait foi, et il se corrige à la main dans le JSON.
  **Une séance adoptée n'est jamais réécrite** : ses blocs sont à elle, un exercice exigé qui lui manque lui est simplement *ajouté*, rien n'est modifié ni retiré. Une séance du catalogue Python n'est pas touchée du tout — l'écrire créerait au passage une surcharge personnalisée que personne n'a demandée. Une séance *créée*, elle, est construite entièrement depuis les exigences.
  **Les cibles écrites ne sont pas jouées telles quelles** : une exigence est l'objectif de *fin* de programme (« 6x22 »). Ces blocs n'étant pas marqués `cible_manuelle`, `appliquer_a_blocs` les réécrit au palier du moment à chaque chargement — le fichier ne fait autorité que sur la structure. Conséquence d'affichage : l'accueil annonce le **nom de la séance** et non le libellé du programme (« jambes_abdos », pas « Jambes et abdos »), sinon le bandeau nommerait une séance absente de la liste juste en dessous. `prochaine_seance` dit laquelle enchaîner : celle qui suit la dernière réalisée dans l'ordre du programme, en boucle, une séance abandonnée ne comptant pas comme faite. Supprimer un programme ne supprime pas ses séances — elles sont jouables en dehors de lui.
  Limite connue de l'équivalence par volume : elle **aplatit la structure des séries**. `2x60 s` de gainage devient `1x120 s`, `3x35` pompes devient `5x21` — même volume, difficulté réelle différente sur les mouvements où la fatigue s'accumule au sein de la série.
  Les exigences forment une **liste plate**, chacune portant le libellé de sa séance ; le regroupement se fait à l'affichage, dans l'ordre d'apparition. Une structure imbriquée se lirait mieux mais s'éditerait beaucoup moins bien depuis un formulaire, or les programmes se modifient depuis le site (`/editer-programme/<clé>`, `/creer-programme`). `programmes_personnalises.json` **masque** le dict `PROGRAMMES` du code, exactement comme `seances_personnalisees.json` masque le catalogue de séances. **`PROGRAMMES` est désormais vide, et c'est délibéré** : « Road to TKT » existait des deux côtés avec des valeurs divergentes, si bien qu'éditer le Python n'avait aucun effet au runtime — sans que rien ne le signale. Le fichier est maintenant la seule source. Deux conséquences : y réintroduire une clé déjà présente sur le disque recréerait exactement ce piège, et tout programme étant devenu `est_personnalise`, sa suppression depuis le site est **définitive** là où elle restaurait auparavant la version du code. `valider_programme` refuse un exercice sans barème plutôt que de laisser une exigence inévaluable atteindre la page.
  **Une seule convention de charge, partout : le poids d'un haltère.** Il y en a eu deux — l'éditeur de programme acceptait la charge totale (`CHARGE_TOTALE`), traduite à l'affichage par `charge_par_haltere` —, et c'est précisément ce qui rendait le même nombre ambigu d'un écran à l'autre : un curl à 20 kg pouvait désigner 10 kg par bras ou 20, et un mouvement unilatéral n'étant jamais divisé, la règle changeait aussi d'un exercice à l'autre. Les deux fonctions ont disparu ; il ne reste que `LIBELLE_CHARGE`, à ne pas écrire en dur dans le template pour que l'étiquette ne puisse pas mentir. La conversion depuis un tableau qui annonce la charge totale se fait à la lecture, avant la saisie. Les valeurs déjà stockées dans `programmes_personnalises.json` ont été divisées par deux sur les mouvements bilatéraux — exactement l'inverse de l'ancienne règle d'affichage, donc aucune valeur à l'écran n'a bougé.
  **Le jumeau est `web/static/js/objectifs.js`** (`generer_objectifs.py` / `comparer_objectifs.mjs`, 3 622 réponses), et c'est le seul harnais du projet qui compare un **effet de bord** : `appliquer_a_blocs` et `appliquer_a_circuit` écrivent sur place, donc les blocs sont relevés avant et après, et **les deux formes de bloc sont jouées sur les mêmes données** — dictionnaire et `BlocExercice` ont chacune leur fonction et ne doivent pas diverger. Trois choses qu'un historique ordinaire ne visite pas sont fabriquées exprès : l'historique ne couvre **qu'une partie du catalogue**, seul moyen d'obtenir des exercices « sans données » donc à calibrer ; les modes sont incompatibles une fois sur trois, pour éprouver « le moteur ne pilote pas ce bloc », qui laisse la cible du fichier au lieu de marquer un test ; et les **dix formats de cible manuelle** sont comparés hors de tout historique, parce qu'un format mal lu fige une cible pour toujours et **en silence**. Le `round()` de l'avancement **doit** passer par `arrondi_python` : `Math.round` en sort huit divergences, l'avancement tombant sur un demi exact dès que le rapport est simple. Le `:g` de `prescription`, lui, **n'a pas de contrepartie à écrire** : la fonction défensive écrite pour ce piège a été retirée sans qu'aucune divergence n'apparaisse, JSON ne distinguant pas un entier d'un flottant et les nombres JavaScript non plus. Deux pièges anticipés au même endroit, un seul réel — et c'est le sabotage, pas le raisonnement, qui a dit lequel. Le troisième sabotage, celui qui fait compter une séance abandonnée comme faite, n'a d'abord sorti que **4 divergences sur 180 programmes** : le générateur partagé tire ses noms de séance parmi trois valeurs dont une seule est liée, si bien que le cas dépendait d'une coïncidence entre deux jeux de données. `_ancrer_dans_le_catalogue` le vise désormais directement et le signal passe à 14 — même leçon que le superset de `refaire_derniere_serie`.

- `calibration.py` — **du test d'un débutant à son niveau de départ**. Comme les
  ancrages, il ne pose jamais un numéro de niveau : il fabrique une *performance*
  et laisse `niveau_pour` la traduire. Le test mesure **une série unique au
  maximum**, que `COEFFICIENT_SERIE_UNIQUE` convertit en capacité de travail
  multi-séries — un repère d'entraîneur, pas une mesure. Le même coefficient sert
  aux répétitions et aux secondes : les deux ne fatiguent pas pareil, mais une
  règle unique vaut mieux que deux réglages dont personne ne saura lequel
  corriger.
  **Le test se joue en séance, il n'y a plus de tunnel d'accueil.** Une séance
  ordinaire rencontre un exercice dont rien n'est connu
  (`objectifs.a_calibrer`), remplace sa cible par un plafond inatteignable
  (`CIBLE_TEST`) à `charge_de_test` — le milieu de l'échelle *réellement
  disponible*, donc du matériel déclaré —, et `Circuit._cloturer_test` pose
  l'ancrage dès que la série est terminée à la main. L'avancement ne se stocke

  `niveau_estime` retournant `None` veut dire **hors barème**, pas « niveau 0 » ;
  `cloturer_test` ancre alors au palier 1 plutôt que de ne rien poser — sans
  ancrage l'exercice redemanderait un test à chaque séance, exactement la boucle

  **jamais sur les dictionnaires de blocs** : ceux-ci alimentent l'affichage mais
  repartent en écriture depuis le formulaire de l'accueil, et y graver `1 x 999`
  remplacerait l'exercice par son test dans `seances_personnalisees.json`. Ils ne

  pour la même raison : la fin de séance repasse par ce chemin.
  **Le jumeau est `web/static/js/calibration.js`**, et il porte une traduction qui ne se voit pas : `round()` en Python arrondit **au pair le plus proche** sur un demi exact (2,5 donne 2), là où `Math.round` arrondit vers le haut. Un maximum de 10 répétitions donne 10 × 0,65 = 6,5, donc une cible de 6 en Python et 7 en JavaScript — mesuré : 36 divergences sur le harnais. `arrondi_python` existe pour ça, et tout portage d'un `round()` doit y passer. Différence d'API assumée : `cloturer_test` **écrit** l'ancrage côté Python, alors que le JavaScript rend seulement `niveau_a_ancrer` — la persistance vit dans `historique.js`, et c'est l'appelant qui décide quand écrire.
- `ligues.py` — **ligues, divisions et XP : la couche qui rend la progression lisible.** « Niveau 14 au curl » ne se compare à rien et ne se fête pas ; une ligue, si. Comme tout `progression/`, le module ne stocke **rien** : la ligue d'un exercice se recalcule depuis son niveau, qui se recalcule depuis l'historique.
  **La ligue vient du volume, pas du numéro de niveau**, et c'est la décision structurante. Le rang se lit sur le volume du palier atteint, **rapporté au volume du palier 1 du même exercice**. Le volume ne croissant pas au même rythme d'un mouvement à l'autre — une hausse d'haltère fait un bond, une répétition de plus fait un pas —, deux exercices au même niveau ne sont pas à la même ligue : le niveau dit la position sur le barème, la ligue dit l'effort produit. Rapporter au palier 1 plutôt que de prendre le volume brut est ce qui permet **une table de seuils unique** malgré le `(poids or 1)` de `paliers.volume`, qui fait compter un mouvement au poids du corps pour 1 kg — sans quoi quatre séries de vingt pompes (80) seraient à jamais derrière quatre séries de douze curls à 12 kg (576). Une table par exercice, elle, se serait désynchronisée du barème au premier réglage de spec.
  **Distorsion connue et assumée** : à volume relatif égal, un exercice chargé couvre une bien plus grande amplitude qu'un mouvement au poids du corps — mesuré, les Pompes vont de 12 à 90 sur leurs paliers bornés (7,5x) quand le Curl biceps va de 48 à 1080 (22,5x), donc le premier plafonne plus bas en ligue. Le correctif éventuel (lire `utilisateurs.poids_corps_kg` au lieu du `or 1`) se ferait **dans ce module**, jamais dans `paliers.volume`, qui porte l'invariant du barème et dont dépend tout l'historique déjà interprété.
  Trois règles de forme héritées d'`etat_niveau`. `niveau` à None veut dire **hors barème**, donc `ligue_exercice` rend None : il n'y a pas de « rang 0 » et surtout pas de Bronze III offert. `rang_pour_volume` **sature** au dernier rang sans lever, la dernière tranche du barème étant ouverte. Et le pourcentage d'avancement est une donnée de `ligue_exercice`, jamais d'`etat_niveau`, qui reste sans notion d'avancement.
  `ligue_pour_rang` rend deux champs que les écrans consomment tels quels : `cle` (le nom sans accent, pour nommer une variable CSS) et `division_index`. Les calculer ici plutôt que dans chaque interface évite d'écrire deux fois la translittération de « Maître » — une fois en Jinja, une fois en JavaScript — et de la voir diverger au premier nom de ligue ajouté.
  **Le niveau général du profil suit une autre règle que les exercices, et il a fallu le mesurer pour le savoir.** Chaque niveau d'exercice rapporte de l'XP (`PALIERS_XP`, table ronde et réglable, croissante), et l'XP totale fait monter un niveau général au coût croissant. Faire gouverner la ligue générale par les mêmes seuils de volume aurait été plus élégant et c'est **faux** : l'XP cumulée croît bien plus vite que le volume relatif, si bien qu'un profil tout à fait ordinaire — le catalogue entier au niveau 20 — sortait déjà Maître III. La ligue générale avance donc d'**un cran par niveau général**, ce qui place Maître I au niveau 18, soit 17 000 XP, soit tout le catalogue autour du niveau 27. Tant qu'aucune XP n'est gagnée, il n'y a pas de ligue.
  **Le jumeau est `web/static/js/ligues.js`**, avec `ligues_ui.js` pour l'habillage. Les seuils, les noms et la table d'XP sont **exportés du Python** (`donnees/baremes.json`, clé `ligues`) et jamais réécrits côté JS. `python -m scripts.generer_ligues` pose 26 370 questions et `scripts/comparer_ligues.mjs` diffe. Deux décisions le tiennent. Les **seuils sont visités des deux côtés**, à un epsilon près : un seuil est exactement l'endroit où `>=` se distingue de `>`, et des ratios tirés uniformément n'y tombent jamais — le sabotage qui passe en comparaison stricte sort 61 divergences, aucune sans ces points. Et il réutilise les **exercices fictifs** de `fixtures_paliers_specs.json`, le catalogue réel n'exerçant ni les surcharges de palier ni le barème sans fin. Le harnais a trouvé une vraie divergence à son premier passage : `xp or 0` laisse passer une XP négative en Python — `-50` est *truthy* — là où le JS bornait déjà à zéro. C'est le JS qui avait raison, à l'inverse de la règle habituelle du projet.
- `scripts/script_niveaux.py` — vérification manuelle (`python -m scripts.script_niveaux`) : barème, contrôle de non-régression du volume, niveaux réels, et lignes d'historique écartées avec leur raison. À relancer après toute modification d'une spec.

**Les records ont fusionné avec les fiches d'exercice, et `records.html` n'existe plus.** Les deux écrans disaient la même chose du même mouvement depuis deux pages, alimentés par le **même `etats_niveaux()`** et le même tri : un niveau dit *où l'on en est*, le graphe *comment on y est arrivé*, la fiche *comment on fait*. `/exercice/<nom>` porte désormais les trois, et `/records` est une **redirection 301** vers `/exercices` — pas une 404, parce que des liens profonds ont pu être mis en favori. Côté application, `dessiner_fiche` a absorbé `bloc_graphique` et `bloc_recalage`, et `brancher_recalages(racine)` prend sa racine en paramètre au lieu du `$("listeRecords")` qu'il codait en dur.
La règle d'affichage qui survit à la fusion : **ni jauge de progression ni total de paliers**. Un record dit où l'on en est ; montrer la suite du barème n'est pas la même chose que fixer une cible. Ce qui exprime un objectif — barre d'avancement, part de barème parcourue, niveau à atteindre — appartient à la couche programme, et c'est pourquoi `etat_niveau` n'expose aucun pourcentage.
Deux conséquences de la fusion à connaître. La **clé d'itération a changé de sens** : l'écran des records parcourait les exercices *suivis par le barème*, la liste des fiches part du catalogue entier — un mouvement sans barème n'a simplement ni graphique ni recalage (`est_suivi_par_le_moteur` le décide, comme avant). Et le JS qui ouvrait le `<details>` ciblé **sur `load`** a disparu avec la page : il n'a plus d'objet sur une fiche mono-exercice.
Le formulaire « Recaler mon niveau » n'agit que sur le dernier ancrage (`POST`/`DELETE /api/niveaux/<nom>/ancrage`). Le lien « Historique des ancrages » sous ce formulaire charge à part, en JS et à la demande (`GET /api/niveaux/<nom>/ancrages`), le journal complet avec un bouton d'annulation par entrée (`DELETE /api/niveaux/<nom>/ancrage/<id>`) — deux routes distinctes de la première, à ne pas confondre au moment d'y toucher.

Bizarrerie à connaître partout où le palier suivant est affiché (ce n'est *pas* un bug) : il peut demander **moins** de répétitions que le palier courant, quand il s'accompagne d'une hausse de poids qui augmente le volume malgré tout (4x20 à 5 kg → 4x17 à 6 kg). Le template affiche une note explicative dans ce cas — la garder, sinon une progression ressemble à un recul.

Détection (`mouvements/`, `vision/`) :
- `vision/detector.py` télécharge au premier lancement le modèle MediaPipe (`pose_landmarker_full.task`, absent du repo, ignoré par git) et expose `PoseDetector.detect(frame)` → un `Body` (`vision/body.py`) qui regroupe les landmarks nommés (`vision/landmarks.py`). Le modèle `full` remplace `lite` : ce dernier perdait le tracking sur les mouvements rapides.
- `mouvements/exercices.py` définit chaque `Exercice` par une fonction `*_detection(corps)` qui retourne une position (`"debut"`/`"fin"`/`"milieu"`/`"maintien"`/`"repos"`) à partir d'angles/distances calculés sur le `Body`. Ces fonctions bilatérales (ex. pompes, développé couché) doivent comparer *les deux* angles gauche/droite au seuil — un bug historique où seul un côté était vérifié (`angle_droit and angle_gauche < seuil`, l'opérateur `and` ne portant que sur l'un des deux) a été corrigé ; rester vigilant si on ajoute un exercice bilatéral sur ce modèle.
  **La règle vaut tant que la caméra voit les deux côtés, et s'inverse quand la
  fiche demande une vue de profil** : le membre éloigné est alors *toujours*
  masqué et estimé par le modèle, si bien qu'exiger que les deux angles
  franchissent le seuil revient à exiger que cette estimation soit exacte. Le
  gainage s'arrêtait par intermittence pour cette raison. Ces détections-là
  **moyennent** les deux côtés (`detection_gainage`, `squat_sur_chaise_detection`)
  et renoncent à repérer un défaut d'un seul côté — que la vue de profil ne
  montre de toute façon pas. Moyenner n'est jamais un raccourci pour faire
  passer une détection récalcitrante : c'est justifié par l'occultation, et par
  elle seule.
  **Un angle de membre ne dit pas où ce membre se trouve.** Le développé
  épaule ne regardait que l'angle des coudes : bras baissés et tendus le long
  du corps, il dépasse aussi 150 degrés, si bien qu'abandonner une série
  comptait une répétition de plus. Il y manquait la **position** — les
  poignets au-dessus des épaules. Même famille de défaut que la planche
  latérale ci-dessous : une détection complète dit *quelle forme* a le corps
  **et** *où il est*, et l'oubli se manifeste toujours du même côté, en
  comptant ce qu'il ne fallait pas.
  **Une position de maintien se reconnaît à ce qui la rend difficile, pas à sa
  seule forme.** La planche latérale vérifiait l'alignement du corps, le côté au
  sol et la hanche au-dessus du coude — trois conditions que quelqu'un
  simplement *allongé sur le côté* remplit toutes, d'où du temps compté sans
  rien faire. Il manquait l'effort : le buste soulevé par l'appui sur
  l'avant-bras (`_appui_sur_le_bras`). Devant un maintien qui compte trop
  facilement, chercher la condition d'effort absente avant de resserrer un
  seuil géométrique.
- **`"debut"` et `"fin"` ne décrivent pas une posture, mais un moment du comptage.** `CompteurMouvement` s'arme sur `"debut"` et incrémente sur `"fin"` : la règle est donc que **`"fin"` est la position qui *valide* une répétition, c'est-à-dire la fin de la phase concentrique** — le haut d'un curl, mais aussi le verrouillage d'une pompe, le retour debout d'un squat ou d'un soulevé de terre. Les dix-sept détections d'`exercices.py` suivent cette convention ; l'inverser sur un mouvement le ferait compter sur la descente, si bien qu'une pompe non verrouillée ou un squat non remonté compterait quand même. **Un mouvement compté a deux seuils, un maintien n'en a qu'un**, et ça change la façon de les régler : l'écart entre `"debut"` et `"fin"` est une hystérésis qui absorbe le tremblement des landmarks, alors qu'un mode `maintien` bascule sur un seuil unique. Ouvrir ou resserrer un seuil de comptage se fait donc en déplaçant **les deux bornes ensemble** pour conserver l'écart ; resserrer un seuil de maintien trop près de la position parfaite le fait au contraire clignoter, et le chrono perd des fractions de seconde alors que la position est tenue. C'est aussi pourquoi le libellé de `"fin"` dans `core/messages.py` est neutre (« Position finale ») : « Position basse » n'est vrai d'aucun mouvement depuis l'alignement.
- **La fiche d'un exercice** vit sur `Exercice` (`session/circuit.py`) et sort par
  `Exercice.fiche()`, point d'entrée unique de « qu'affiche-t-on d'un mouvement ? ».
  Ses champs ne se recouvrent pas : `description` dit ce qu'est le mouvement,
  `mise_en_place` comment s'installer **avant** de commencer (cadrage caméra
  compris — première cause d'un comptage qui ne démarre pas, et qu'aucune
  détection ne dira jamais), `instructions` l'exécution, `erreurs_frequentes` de
  la pédagogie écrite. Ne pas confondre cette dernière avec `erreurs`, qui est
  une liste de **fonctions** exécutées à chaque frame. `variante_facile` /
  `variante_difficile` nomment un autre exercice du catalogue : c'est ce qui
  permet au test de calibration de rediriger quelqu'un qui ne tient pas le
  premier palier, au lieu de le laisser « hors barème ».
- **La fiche à l'écran de séance vit dans la colonne droite** (`.right-column` d'`index.html`), au-dessus du compteur, en `z-index: 7`. Son `padding` est posé sur `.fiche-card` : `.card` n'en définit aucun, chaque variante pose le sien (cf. `.position-card`), et sans lui le texte touche la bordure. — c'est-à-dire **au-dessus de `.rest-overlay` (6)**, et c'est ce seul chiffre qui la rend lisible pendant les pauses, le moment où on a justement le temps de la lire. `state.fiche` (l'exercice courant, écrit par `main.py` en phase `exercice` uniquement) et `state.fiche_suivante` (le prochain, écrit par `moteur.mettre_a_jour_prochain_exercice` en phase `repos_exercice`) sont deux champs distincts et doivent le rester : pendant `recuperation_serie` on refait le même mouvement et c'est le premier qu'il faut relire, pendant `repos_exercice` on prépare le suivant — matériel et cadrage caméra se décident avant la première répétition. Côté JS, la mémoïsation de `mettreAJourFiche` porte sur **le nom *et* la phase** : un superset peut avoir pour « prochain » l'exercice qu'on vient de quitter, et une clé réduite au nom n'y redessinerait rien.
- `mouvements/echauffements.py` déclare les mouvements d'échauffement, sur le même modèle qu'`exercices.py` mais avec `detection` facultative : les rotations articulaires (cou, poignets, coudes, épaules) sont volontairement sans détection, un mouvement trop petit pour être suivi de façon fiable valant mieux sans heuristique que avec une mauvaise. Devant un cycle côté JS, sortir la feuille plutôt que différer l'import.

Trois règles tiennent ce jumelage. (1) **Les noms sont ceux du Python, en snake_case**, contrairement à l'usage JavaScript : c'est ce qui rend les deux fichiers lisibles côte à côte et permet au harnais d'apparier les fonctions par leur nom, sans table de correspondance qui dériverait. (2) **Le Python fait autorité** — il tourne depuis des mois ; un écart est un bug du JS jusqu'à preuve du contraire. (3) **Aucune modification d'une détection ne se fait d'un seul côté.** `python -m scripts.generer_fixtures` rejoue 5 000 poses tirées au hasard (graine fixe) dans toutes les fonctions Python et écrit les jetons attendus ; `node scripts/comparer_detections.mjs` les rejoue en JS et diffe. Les poses sont aléatoires et non filmées à dessein : les détections étant des fonctions pures, elles doivent s'accorder sur n'importe quelle entrée, et le hasard couvre les abords des seuils bien mieux qu'une captation. Le recensement des fonctions se fait par **introspection** du module Python : une détection ajoutée sans jumelle JS fait échouer le harnais au lieu de passer inaperçue. Le `.jsonl` produit n'est pas versionné (24 Mo dérivés, 3 s à régénérer).
**`session/circuit.py` a son propre harnais, et il ne peut pas avoir la même forme** : une détection est pure, donc on lui jette des entrées au hasard ; `Circuit` a de la mémoire, donc il faut lui jeter une **histoire**. `python -m scripts.generer_scenarios` joue des suites de commandes horodatées sur les vraies séances et relève l'état après chaque pas ; `scripts/comparer_seances.mjs` rejouera les mêmes pas en JavaScript. Quatre décisions le tiennent. (1) Les circuits sont bâtis par `construire_circuit` et **jamais** par `creer_seance` : celle-ci passe par le moteur de progression, donc par l'historique, et les cibles changeraient à chaque séance jouée — un oracle doit rendre deux fois le même verdict (vérifié : même empreinte à deux exécutions). (2) **Faire avancer l'horloge est une commande**, au même titre que les autres : c'est elle qui fait expirer un repos, donc qui déclenche les transitions qu'`update` se contente ensuite de constater. (3) **Une exception est un comportement relevé, pas un incident** — si Python refuse une commande dans un état donné, le JavaScript doit la refuser aussi. (4) Marche aléatoire **et** scénarios nommés, parce qu'ils ne trouvent pas les mêmes choses : le hasard explore des enchaînements que personne n'écrirait, les scénarios nommés visent les pièges déjà connus (entrelacement, les cinq sorties de `terminer_serie`, le repère de « refaire ») et disent tout de suite lequel a cédé. Le levier principal de ce harnais est le nombre de champs relevés par `observer`, bien avant le nombre de pas. Les fixtures portent enfin une **empreinte du fichier de séances** : celui-ci est réécrit à chaque fin de séance jouée, si bien qu'une comparaison lancée après un entraînement produit un diff authentique et parfaitement trompeur (« poids 5 contre 6 ») qu'on met un moment à reconnaître pour ce qu'il est. L'empreinte est calculée **après retrait des retours chariot** : Python les traduit à la lecture, Node les garde, et deux verdicts opposaient sinon le même contenu. Le `.jsonl` n'est pas versionné non plus (5,5 Mo dérivés).
**Un harnais qui n'a jamais échoué ne prouve rien : le saboter est une étape du travail, pas une coquetterie.** Le portage de `circuit.js` est passé vert du premier coup sur 141 312 valeurs ; deux régressions introduites exprès ont montré que l'une était attrapée au pas 1 et **l'autre pas du tout** — celle qui oublie de restaurer l'entrelacement dans `refaire_derniere_serie`, précisément la ligne signalée comme indispensable. Deux causes, et il a fallu les deux. D'abord `observer` ne relevait que des sorties publiques, alors que le défaut est **dans un état interne** : `_exercice_precedent_entrelace` et `_derniere_serie_terminee` y figurent désormais, parce qu'observer la cause vaut mieux qu'attendre que son effet remonte. Ensuite et surtout, **la marche aléatoire n'atteignait jamais le cas** : mesuré, 408 « refaire » réussis dont **zéro** avec un entrelacement à restaurer, et 13 pas sur 6 144 au milieu d'un superset. Les états profonds d'une machine à états sont hors de portée du hasard ; il a fallu un scénario écrit (`superset_refaire`) qui y va directement, via une commande de harnais `aller_au_superset` **pilotée par les données** et non par un nombre de sauts en dur — un superset déplacé rendrait sinon le scénario muet sans prévenir. C'est l'argument qui justifie de garder les deux sources de scénarios, et la raison de rejouer un sabotage après chaque élargissement du harnais.
**Le harnais joue aussi de vraies images**, et c'est ce qui vérifie `moteur.js` : la commande `image` fait tourner `executer_mode` sur une pose tirée d'une **banque partagée** (`fixtures_poses.jsonl`, référencée par index plutôt que recopiée — 132 flottants par pas rendraient le fichier illisible). Le compteur, l'état et `derniere_rep` **survivent d'une image à l'autre**, comme dans la boucle caméra : les recréer à chaque pas masquerait la moitié de ce que le moteur doit gérer. Et les **annonces du coach sont enregistrées, jamais jouées** : *quand* l'application parle est une décision qui doit coïncider, alors que jouer le son ne l'est pas — c'est le seul canal qui vérifie « encore 3 » ou le bip de chaque seconde, et un sabotage de ce réglage n'est attrapé que par lui. Le harnais exporte enfin **son propre catalogue** (`fixtures_catalogue.json`) plutôt que de lire celui de la démo : les séances contiennent des échauffements, que `catalogue.json` ne liste pas et n'a pas à lister.
**Asymétrie connue entre les deux moteurs, et elle a un coût.** `session/moteur.py` reçoit un `coach` en paramètre, mais `annoncer_progression` et `annoncer_temps_restant`, importées d'`audio.coach`, appellent le **coach global de leur module** : le harnais déclenchait donc une vraie lecture audio, qui fait *planter* un processus sans carte son. Il détourne `audio.coach.coach` vers la même liste d'annonces, sans quoi ces décisions-là n'apparaîtraient dans aucune comparaison. Côté JavaScript, les deux fonctions vivent **dans `moteur.js`** et reçoivent le coach injecté, ce qui rend le module pur : si le Python est un jour aligné dessus, le détournement du harnais disparaîtra.
**L'historique est porté « par ce que le SQL produit », pas par le SQL.** `web/static/js/historique.js` tient la base dans un **objet JavaScript ordinaire** — cinq collections qui reprennent les cinq tables, clés étrangères comprises, et `utilisateur_id` seulement sur les deux tables racines comme en SQLite. Trois raisons, et la troisième commande les deux autres : l'historique d'une personne tient en mémoire et le Python recalcule déjà tout à la lecture ; l'export devient trivial puisque l'objet *est* le fichier ; et surtout **la logique redevient vérifiable**, ce qu'elle ne serait pas mêlée à IndexedDB, qui n'existe pas dans Node. `python -m scripts.generer_historique` joue des écritures sur une base **jetable** (jamais la vraie, qui contient de vraies séances) avec une **horloge figée** (sinon deux exécutions horodateraient différemment), relit **les deux profils après chaque écriture** — c'est ce qui vérifie le cloisonnement au pas où il cède et non trois cents pas plus loin —, et `scripts/comparer_historique.mjs` diffe. La persistance vit à part dans `stockage.js` : **IndexedDB et non `localStorage`** (synchrone, plafonné à 5 Mo, premier purgé), la base entière dans **un seul enregistrement** pour que l'écriture soit atomique, et `charger()` qui **ne lève jamais** — une panne de stockage doit laisser la séance se jouer, quitte à ne pas la retenir, alors qu'une exception au démarrage empêcherait de s'entraîner. `sauver()` rend un booléen pour que l'écran de fin puisse dire « ça n'a pas pu être enregistré, exporte » plutôt que de laisser croire le contraire. L'export n'est pas un raffinement : Safari purge les sites peu visités, une application de l'écran d'accueil y échappe *normalement*, et un historique d'entraînement ne se parie pas sur un « normalement ».
**Invariant du `Circuit` : la phase `exercice` implique un bloc courant.** Cinq méthodes posaient `phase = "exercice"` ou lisaient `bloc_actuel` sans vérifier qu'il existe (`commencer_exercice`, `recommencer_serie`, `remettre_serie_a_zero`, `terminer_serie`, `terminer_serie_manuellement`, plus l'accès `poids`), ce qui laissait un état impossible — phase active, plus aucun bloc — où la série suivante levait un `AttributeError` : 890 occurrences sur une seule marche aléatoire. `main.py` s'en protégeait de l'extérieur par un test de phase, et **c'est justement ce que le portage supprime** : le navigateur appellera la classe directement. La règle descend donc dans la classe, des deux côtés, là où elle ne peut plus être oubliée par un appelant.
**Le repère gauche/droite a été faussé pendant des mois, et il est désormais aligné — par la capture, pas par le code.** **Le verdict se mesure, il ne se juge pas** : `python -m scripts.script_verification_positions` affiche désormais « Image NON miroir » ou « IMAGE EN MIROIR », déduit de la position des épaules — MediaPipe étiquetant du point de vue du sujet, quelqu'un qui fait face à l'objectif a son épaule *droite* dans la moitié *gauche* de l'image ; l'inverse prouve que la source retourne. C'est une mesure parce que l'œil est ici un mauvais témoin : on est habitué à se voir retourné, donc une image miroir passe pour normale, et demander « te vois-tu en miroir ? » ne tranche rien. Le test se tait de profil ou de dos, où les épaules se superposent et ne portent plus l'information — se taire vaut mieux que de trancher à pile ou face. Il n'existe aucun `cv2.flip` dans le projet : le miroir du desktop venait entièrement de Camo, qui renvoyait l'image de l'iPad retournée. MediaPipe, qui ne peut pas savoir qu'une image est inversée, y étiquetait les membres à l'envers — « Curl biceps droit » comptait en réalité le bras **gauche**. Dans le navigateur la vidéo est passée brute au modèle, donc l'étiquetage y était correct depuis le début : **le portage était juste et l'original faux**, ce qui est l'inverse de la règle habituelle. Le miroir a été désactivé dans Camo, si bien que les deux côtés comptent maintenant le même bras. Trois choses à savoir. (1) **Ne jamais « corriger » le JS pour le faire coïncider avec un comportement observé sur PC** : c'est ce qu'on aurait fait sans avoir mesuré. (2) Les séances enregistrées **avant** ce réglage portent l'ancien étiquetage — leurs lignes « droit » décrivent le bras gauche, et inversement. Le moteur de progression lit cet historique, donc les niveaux des exercices asymétriques (`fente_droite/gauche`, `rowing_unilateral_*`, `detection_gainage_laterale_*`) se rapportent au mauvais côté tant que ces séances pèsent dans le calcul. (3) L'affichage du desktop n'est plus en miroir : le modèle reçoit la bonne image, mais on se voit à l'endroit, ce qui désoriente. Le navigateur, lui, sépare les deux (`Camera.miroir` ne touche que le dessin, jamais l'image analysée) — c'est le découpage à reprendre si le desktop doit retrouver son miroir d'affichage. Les sept fonctions bilatérales dont les variables `angle_..._droit`/`_gauche` sont croisées par rapport aux landmarks utilisés restent sans effet, leurs deux seuils étant identiques — mais rendraient le croisement visible le jour où une condition deviendrait asymétrique.

**L'application (`web/static/app/`) joue une séance entière, la démo reste le banc d'essai.** Deux pages et non une : la démo sert à tester **un exercice isolé** — c'est à ça qu'elle sert maintenant, `?banc=1` compris —, l'application enchaîne les blocs, les repos et l'historique. Les fusionner ferait perdre le banc d'essai, qui a déjà servi à diagnostiquer trois défauts. Elles partagent en revanche **tout le code** : `camera.js` porte le détecteur, le suivi temporel du sujet et le cycle de vie de la caméra, c'est-à-dire exactement les trois règles qu'une seconde copie ferait dériver ; `seance.js` monte un `Circuit` depuis les données exportées et en ressort des résultats enregistrables. Ces trois fonctions vivaient d'abord **dans la page**, où elles étaient invisibles à toute vérification : les en sortir est ce qui a permis de jouer une séance complète au harnais, et `resultats_par_exercice` porte la règle « les échauffements sont exclus à la source », jumelle de `Circuit.exporter_resultats`. Une page qui garde sa logique pour elle n'est pas seulement mal rangée : elle est **non vérifiable**.
Trois décisions de l'écran de séance. Le **son se prépare au clic sur une séance** et non au chargement : iOS refuse de jouer quoi que ce soit tant qu'un contexte audio n'a pas été créé pendant un geste tactile. La **table des sons est exportée depuis `audio/coach.py`** (`donnees/sons.json`) et jamais réécrite en JavaScript — mais elle est lue par **analyse syntaxique** et non par import, parce que `audio.coach` tire `pygame`, que le workflow de déploiement n'installe pas : l'importer ferait échouer le déploiement pour une raison sans rapport avec le son. Enfin l'écran de fin **dit si l'enregistrement a réussi** : `stockage.sauver` rend un booléen, et un échec affiche « exporte cette séance maintenant » plutôt que de laisser croire qu'elle est retenue.
**La carte de programme de l'accueil est partagée** (`static/programme_resume.css`) : l'application la montre en tête de sa liste de séances, là où le poste fixe la met en tête de l'accueil. Les deux réglages qu'elle porte ne se confondent pas, et c'est la distinction qui compte — **« Changer de programme » persiste** (c'est une préférence du profil, `utilisateurs.programme_choisi`), **« Commencer plutôt par » est une bascule ponctuelle** qui ne stocke rien et se contente de réécrire la cible du bouton de démarrage ; la proposition automatique reprend la main au prochain affichage. `null` dans `programme_choisi` veut dire « aucun choix », et la carte **invite alors à en faire un** au lieu de retomber sur le premier : ne rien écrire préservait la donnée, mais l'affichage prétendait quand même qu'un choix existait. Le sélecteur « Changer de programme » a quitté cette carte pour l'écran des programmes, seul endroit où la règle vit désormais.

**L'application édite ses séances, et l'appareil l'emporte sur le fichier.** Il n'y a pas de serveur à qui écrire — un site statique n'en a pas —, donc une séance modifiée dans l'application vit dans sa base, sous la collection `seances_locales` : un objet `{nom: blocs}`, exactement la forme du fichier qu'elle remplace. Elle **masque** alors la version déployée, de la même façon que `seances_personnalisees.json` masque le catalogue Python, un cran plus loin. L'arbitrage est assumé : une édition faite loin de l'ordinateur ne doit pas disparaître au prochain déploiement. Son corollaire l'est aussi et doit rester visible — une correction faite sur le PC n'atteint plus cette séance —, d'où le badge « modifiée sur cet appareil » et le bouton « revenir à la version du fichier ».

Trois règles tiennent cet éditeur. (1) **Il part des valeurs du moteur, pas de celles du fichier.** Le formulaire du poste fixe est rendu depuis `catalogue()`, qui applique déjà le moteur ; l'application doit faire ce geste explicitement (`blocs_a_editer`). Sans lui, les valeurs affichées datent d'avant plusieurs séances, et enregistrer sans rien toucher fige *tous* les exercices — mesuré : modifier une seule cible marquait les deux blocs de la séance. (2) **La cible va dans le champ de son mode et nulle part ailleurs** : `MODES_DUREE` décide, et un mode absent de cette liste verrait sa durée remise à zéro au premier enregistrement — c'est le piège déjà documenté des éditeurs de séance, qui se reproduit ici à l'identique. (3) **Le refus est à l'enregistrement**, jamais en séance : `problemes_des_blocs` est le jumeau des vérifications de `construire_circuit` — exercice inconnu, mode inconnu, mode exigeant une détection sur un mouvement qui n'en a pas — et rend la liste complète plutôt que de lever au premier, un formulaire devant pouvoir tout signaler d'un coup. Un nom d'exercice orphelin reste sélectionné via un `optgroup` « Inconnu », pour la même raison que dans `editer_seance.html` : sans lui le navigateur choisirait la première option et remplacerait silencieusement l'exercice.

(4) **L'entrelacement est un drapeau « avec le bloc suivant », jamais un nom.** Le partenaire est recalculé à chaque affichage et à l'enregistrement, ce qui lui permet de survivre à un réordonnancement — déplacer un bloc ne doit pas laisser un entrelacement pointant vers un exercice qui n'est plus à côté, et déplacer un bloc en dernière position défait le sien de lui-même, faute de suivant. L'éditeur de l'application reprend enfin `editeur.css` et ses classes : même pastille de mode, même liseré d'entrelacement, même ligne `⟷ séries alternées avec …`. Seule la mise en page diffère — la grille de onze colonnes du bureau suppose un écran large, donc en portrait on empile, dans le même ordre.

Point de structure de la base : `seances_locales` est **la sixième collection, et elle est optionnelle à l'import**. C'est une règle et non une tolérance — l'exiger rendrait illisibles toutes les sauvegardes déjà faites, c'est-à-dire précisément celles qu'on voudra relire le jour où l'appareil aura été effacé. Le refus bruyant d'`importer` vaut pour ce qu'on ne sait pas lire, pas pour ce qui n'existait pas encore.

**L'appareil ne doit pas s'endormir pendant une séance**, et il a fallu deux séances réelles pour en venir à bout : le `Screen Wake Lock` seul ne suffit pas. `web/static/js/veille.js` en tient donc **deux mécanismes**, et les deux comptent.

Le verrou d'abord, avec ses trois façons d'échouer là où on l'attendrait. (1) Il est **libéré dès que la page devient invisible** et **ne revient pas tout seul** — d'où la reprise sur `visibilitychange`, qui était la première correction. (2) Safari ne l'a que depuis iOS 16.4. (3) Il se demande **au plus près du geste de l'utilisateur** : une chaîne d'`await` — préparer l'audio, demander la caméra, charger le modèle — prend plusieurs secondes, au bout desquelles l'activation a expiré et la demande est refusée. C'était le défaut de la deuxième version, et c'est pour ça que la demande part maintenant du gestionnaire de clic, avant toute attente.

La vidéo ensuite, en repli : iOS garde l'écran allumé tant qu'une vidéo est lue, et c'est la méthode qui marchait avant l'API. On réutilise **le flux de la caméra**, déjà ouvert — aucun fichier à embarquer. Le point qui décide de tout : l'élément doit être **attaché au document et rendu**. Une vidéo détachée, ou masquée par `display:none`, ne compte pas comme lue — et c'est précisément ce qu'était la vidéo de `camera.js`, créée par `createElement` et jamais ajoutée à la page. D'où un carré d'un pixel quasi transparent, jamais un élément caché.

`camera.js` portait d'ailleurs un **second verrou**, demandé une fois, jamais repris, avec un `relacher_ecran` que personne n'appelait — deux verrous concurrents sur la même page sont surtout deux façons de croire qu'on tient l'écran. Il a été retiré.

**L'état est lisible, et c'est la partie la plus utile.** Un échec silencieux se paie en séance : l'écran s'éteint au milieu d'un gainage et rien ne dit pourquoi. Le voyant de statut du HUD — qui annonce « connexion perdue » sur le poste fixe et n'a aucun sens dans le navigateur, où il n'y a pas de connexion à perdre — affiche donc « Écran gardé allumé » ou « L'écran peut s'éteindre », réévalué à chaque image et réécrit seulement au changement. Le message d'erreur, lui, **ne nomme aucune cause** : mesuré, un appel hors geste utilisateur rend `NotAllowedError` exactement comme un refus système, et prétendre distinguer les deux serait inventer. Limite de vérification assumée : le verrou ne peut pas être éprouvé depuis le volet de prévisualisation, qui n'a jamais le focus que Chrome exige — seul le repli vidéo y est vérifiable.

**Le graphique de progression est partagé** (`static/js/graphique.js`, `static/graphique.css`) : il vivait dans le `<script>` de l'écran des records du poste fixe, et celui de l'application n'en avait aucun — ce qui lui retirait la seule vue d'ensemble du projet, un niveau disant *où l'on en est* et le graphe *comment on y est arrivé*. Le module rend une **chaîne de SVG** et ne touche jamais au document, ce qui lui permet de servir les deux pages et d'être vérifiable sans navigateur. La seule chose qui diffère est le lien d'un point — le poste fixe pointe vers `/historique/<id>`, l'application n'a pas d'URL —, d'où une fonction `lien` qui peut rendre null : les points deviennent alors de simples groupes. Règle d'affichage qu'il porte : **l'axe part toujours de zéro**, jamais du minimum de la série, sans quoi une variation de trois pour cent ressemble à une falaise. `statistiques_exercices` est porté dans `historique.js` pour l'alimenter, et **comparé par le harnais de l'historique** : c'est une fonction dérivée, qui peut donc diverger sans que `recuperer_historique` bouge (sabotée sur le filtre `completee`, elle sort 3 divergences).

Détail d'affichage de l'historique qui n'en est pas un : **la charge est portée par la série, pas par l'exercice**, et le détail l'affiche désormais (`11×5 11×5 10×5`). On baisse souvent d'un cran en cours de séance, et « 11 11 10 » ne dit pas si les trois ont été faites au même poids. Dans l'application, `resume_series(series, mode)` est le **point d'entrée unique** de cette écriture, et il rend les pastilles `.series-detail` / `.serie-puce` — **une case par série**, pas une phrase à points médians : c'est ce qui rend l'écart visible d'un coup d'œil, `15×8 kg` et `12×10 kg` étant alors deux blocs à comparer plutôt qu'un texte à lire. Les **trois** écrans qui montrent une performance passée y passent : le détail d'une séance dans l'historique, le dépliant « Dernière fois » des cartes de séance et la réponse à un appui sur un point du graphique. Deux pièges de cette mise en commun : un `<div class="series-detail">` ne peut pas vivre dans un `<p>` (le navigateur ferme le paragraphe avant lui, en silence), et la charge d'une pastille étant un `<i>` comme le ressenti de « Dernière fois », la règle de couleur de ce dernier a dû être portée à `.detail-ligne > span > i` — sinon les kilos passaient en rouge. Deux règles y tiennent — une durée ne se rapporte à aucune charge (un gainage se tient, il ne se soulève pas) et un poids nul n'est pas une charge de zéro kilo mais un mouvement au poids du corps, d'où `15` et non `15×0 kg`.

**L'application a désormais ses profils**, et ils n'ont presque rien coûté : tout le cloisonnement était déjà là. `historique.js` filtre par `utilisateur_id` exactement comme SQLite, et `progression/` retombe dessus par en dessous — seule la constante `PROFIL = 1` empêchait d'en avoir plusieurs, ce qui était un choix provisoire assumé et non une limite de structure. L'écran « Qui s'entraîne ? » reprend celui du poste fixe, à une différence près : **il ne s'impose jamais au lancement**. L'application rouvre sur le dernier profil utilisé, dont l'identifiant est retenu dans `localStorage` — et **pas dans la base** : c'est une commodité de cet appareil, pas une donnée d'entraînement, elle n'a rien à faire dans une sauvegarde qu'on réimporte ailleurs, où elle désignerait un identifiant qui n'existe peut-être pas. La lecture comme l'écriture y sont enveloppées dans un `try/catch` : ne pas se souvenir du profil est un désagrément, pas une panne. Changer de profil **reconstruit le moteur**, pour la même raison que le questionnaire de matériel : `Baremes` normalise l'inventaire une fois pour toutes à la construction, et sans ça le second profil verrait les objectifs calculés sur les haltères du premier, en silence.

**Les cibles de l'application viennent de l'historique local, plus du fichier.** `demarrer` construit le `Circuit` depuis `donnees/seances.json`, puis lui applique `objectifs.appliquer_a_circuit` : le JSON ne fait plus autorité que sur la structure — quel exercice, quel mode, quels repos, quel entrelacement. La liste des séances affiche le palier visé par exercice, ou « à tester » pour ceux dont rien ne prouve le niveau : sans ça, le moteur travaillerait sans que personne puisse voir qu'il travaille. L'**ancrage d'un test se pose dès la série terminée** (`cloturer_test_eventuel`) et non à la fin de la séance : la performance vient d'être mesurée, et l'ancrage doit exister avant que le moteur ne recalcule quoi que ce soit. Le `Baremes` portant l'inventaire du profil, changer de matériel impose de **reconstruire le moteur** (`construire_moteur`) — il normalise une fois pour toutes à la construction.

**Il n'y a plus qu'un seul écran de séance, monté deux fois.** Il vivait en double — le `<style>` et le `<script>` de `templates/index.html` d'un côté, une réécriture dans `static/app/index.html` de l'autre — et les deux avaient cessé de se ressembler : palette différente (`#0c1117` contre `#0a0d13`, bleu contre orange/teal), typographie différente (police système contre Bebas Neue + Space Grotesk), disposition différente (tout empilé en bas contre topbar + colonne gauche + colonne droite). C'est le contraire de l'objectif du portage, et c'était **structurel** : deux fichiers que rien n'oblige à s'accorder divergent à chaque correction faite d'un seul côté.

Le partage se fait en trois morceaux, et le découpage compte. `static/palette.css` ne porte que les variables de couleur — `base.css` l'importe, donc les sept gabarits n'ont pas bougé, et l'application la lie directement. `static/hud.css` porte le calque de séance en entier. `static/js/hud.js` porte **l'affichage**, c'est-à-dire tout ce qui était écrit deux fois : badges, compteur multi-modes, fiche, bandeaux, voile de repos, bulle de maintien, barres de progression. Les deux pages montent le **même balisage**, aux mêmes classes et aux mêmes identifiants. Ce qui n'est **pas** partagé : `base.css`, qui est une mise en page de *site* (conteneurs, onglets, largeurs fixes) et n'a rien à faire dans une page qui est un calque plein écran.

Une règle de socle que les deux portent désormais chacune de son côté (`base.css` et le `<style>` de l'application) : **`[hidden] { display: none !important; }`**. L'attribut `hidden` ne vaut qu'un `display:none` de faible priorité, donc n'importe quelle règle de page qui pose un `display` le neutralise — un formulaire en `display:grid` ou en `flex` marqué `hidden` reste parfaitement visible. L'erreur est silencieuse : le code croit avoir caché quelque chose, et rien ne le contredit. Les deux formulaires de mesures sont tombés dedans le même jour, l'un en `.mesures { display:grid }`, l'autre en `.form-ancrage { display:flex }`.

**Tout `hud.js` est une fonction de son argument, et c'est la condition du partage** : ni requête, ni horloge, ni accès caméra n'y entrent, sinon une des deux pages cesserait de pouvoir l'utiliser. L'objet qu'il reçoit est celui que `/etat` renvoie — Flask y sérialise `EtatSeance` + `SessionManager.etat()`, et `seance.payload_etat` le fabrique côté navigateur depuis le `Circuit` local. **C'est le contrat entre les deux applications** ; y ajouter un champ se fait des deux côtés. `payload_etat` relit les champs dérivés du circuit au lieu de les recopier dans `etat` au fil de la boucle comme le fait `main.py` : une copie ne peut que se périmer, et la boucle n'a alors plus rien à tenir à jour pour l'affichage.

La seule chose qui ne se partage pas est **l'exécution** d'une commande : le poste fixe POSTe sur une route Flask, le navigateur appelle directement le `Circuit`. D'où `brancher_commandes(executer)`, et surtout des **noms** de commande (`reset`, `passer_pause`, …) plutôt que des URL dans le balisage — ce sont déjà les clés de `commandes_autorisees`, là où l'ancienne version identifiait un bouton par son URL puis la retraduisait en nom avec une table d'exceptions.

**`scripts/verifier_hud.py` garde ce jumelage**, parce que partager le code d'affichage ne suffit pas : il reste le balisage, et un identifiant manquant ne se signale pas — `$("reps")` rend `null`, la ligne suivante lève, et la boucle d'affichage s'arrête au milieu, dans la console d'un onglet que personne ne regarde. Il vérifie que les 40 identifiants réclamés par `hud.js` existent **dans les deux pages**, que les 11 commandes y sont les mêmes, et qu'elles sont à la fois autorisées par `SessionManager.etat()` et exécutables par le dictionnaire `COMMANDES` du navigateur. Il a trouvé un défaut à son premier passage : `abandonner` ne figurait pas dans `commandes_autorisees`, et le front grisant tout ce qui n'y figure pas, le bouton « Abandonner » du poste fixe n'avait **jamais** pu être cliqué.

Trois écarts subsistent entre les deux montages, tous délibérés. L'image vient d'un `<img>` alimenté par le flux MJPEG de Flask d'un côté, d'un `<canvas>` alimenté par la caméra de l'appareil de l'autre — les deux portent la classe `.video`, et le reste du calque les ignore. L'application affiche cette image en **`object-fit: contain` et jamais `cover`** : recadrer masquerait une partie de ce que le modèle analyse, on se verrait entier pendant que le contrôle de cadrage signale un genou hors champ, c'est-à-dire exactement la confusion qu'il est là pour lever. Et l'application ajoute un bouton « Je commence », parce que le poste fixe a un clavier là où une tablette posée par terre n'a rien.

**L'anneau de geste n'est pas décoratif.** Le desktop l'a toujours eu ; l'application en était dépourvue, et le premier test réel s'est soldé par « mes bras en croix n'ont rien lancé du tout ». Tenir une position sans aucun retour ne dit pas si le geste est pris ou si l'on s'y prend mal — **un geste sans retour visuel est indistinguable d'un geste qui ne marche pas**. Il est désormais alimenté des deux côtés par `progression_maintien`, que `observer_gestes` relève à chaque image dans le navigateur comme `main.py` le fait sur le poste fixe. Cette même fonction a rapatrié deux choses que l'application n'avait pas : `position_actuelle` (la carte « Position » affichait « Aucune » en permanence) et le geste **deux bras levés**, qui remet le compteur à zéro sans valider la série. Elle lit l'avancement du geste **sans appeler `update`** : `HoldPosition` ne rend la transition « terminé » qu'une seule fois, et un second appel par image la consommerait — la série ne se validerait plus jamais. Les durées de tenue sont enfin alignées sur `main.py` : 1,5 s pour entrer dans la séance, **3 s** pour valider une série ou la remettre à zéro, là où l'application validait à 1,5 s.

La barre de progression reste **vide pendant un test de calibration** : il n'y a pas d'objectif à remplir, et la montrer à zéro sur une cible de 999 donnerait l'impression d'un échec avant d'avoir commencé.

**La saisie du ressenti est partagée, et son absence était un défaut silencieux.** `ressenti.js` était porté et branché dans le moteur de l'application depuis l'étape 4 — mais **aucun écran ne permettait d'y répondre**. Le moteur lisait donc toujours « pas de réponse », c'est-à-dire `+1` après une réussite et `0` après un échec, pendant que le poste fixe accélérait à `+2`/`+3` ou reculait à `−1` : **les deux versions ne progressaient pas au même rythme**, et rien ne le disait. Ça ne se voyait pas sur un écran, ça se voyait trois séances plus tard, sur un objectif qui n'était pas le même. Un module porté mais non branché à l'interface est pire qu'un module absent — l'absence, elle, se remarque.

Le partage suit le découpage de `hud.css` / `hud.js` : `static/ressentis.css` pour l'habillage, `static/js/ressentis_ui.js` pour le comportement des boutons. Ce module **ne décide rien** — la règle vit dans `ressenti.js` / `progression/ressenti.py` — et ne porte que *quelles réponses proposer*, ce qui en découle directement : proposer « trop dur » après une réussite afficherait un bouton dont la table d'ajustement ne fait rien. Les deux écrans de saisie sont ceux du poste fixe : la fin de séance, et l'historique pour répondre **a posteriori** — on ne sait pas toujours sur le coup que c'était trop dur. La seule différence est l'origine du jugement : le poste fixe interroge `/api/historique/<id>/ressentis`, le navigateur appelle le même `Ressenti` sur sa base locale. `construire_moteur` expose pour cette raison l'instance sous `moteur.ressenti` : les écrans s'en servent pour **juger** une séance passée, pas seulement le moteur pour calculer un objectif.

La règle vivait en fait à **trois** endroits, et le troisième était en Jinja : `historique.html` construisait ses boutons côté serveur avec ses propres listes `RESSENTIS_REUSSITE`/`RESSENTIS_ECHEC`, dont les libellés avaient déjà divergé de ceux de `fin.html` (« Facile » contre « C'était facile »). La page dépose désormais les jugements calculés par le serveur (`jugements|tojson`) et laisse le module partagé les habiller. Une zone de ressenti y vit dans une carte cliquable : elle doit arrêter la propagation du clic, sinon répondre replie la séance.

Les fiches d'exercice portent le **recalage de niveau**, avec le même formulaire et le même journal des deux côtés — `static/ancrages.css` est partagée. La règle d'interface est identique et c'est elle qui compte : **on ne demande jamais un numéro de niveau**, personne ne sait ce que vaut « niveau 27 ». On demande une performance, et le barème en déduit le niveau ; une performance qui n'atteint pas le premier palier est refusée des deux côtés, avec le palier manquant dans le message, plutôt que d'ancrer un niveau inventé. La seule différence est où vit la base : le poste fixe POSTe sur `/api/niveaux/<nom>/ancrage` et laisse Flask déduire le niveau, le navigateur appelle `niveau_pour` sur place. Les deux boutons de suppression restent distincts des deux côtés — celui du formulaire purge tout l'historique d'ancrages de l'exercice (`supprimer_ancrages`), celui du journal retire une entrée précise (`supprimer_ancrage`), et comme seul le dernier ancrage compte, retirer une entrée antérieure ne change aucun niveau : c'est un nettoyage, pas une correction.

**La carte de séance est un conteneur, plus un bouton, et c'est ce qui a permis de tout y ramener.** Le crayon « Modifier » et le `<details>` « Dernière fois » vivaient *à côté* d'elle, en nœuds frères, parce qu'un `<button>` ne peut contenir ni bouton ni `<details>` — le navigateur déplacerait le nœud en silence. La carte est donc devenue un `<article>` dont seule la zone de titre est un `<button class="carte-lancer">` : le crayon, le contenu dépliable et le bandeau « dernière fois » sont à l'intérieur, et la contrainte HTML disparaît au lieu d'être contournée. **Devant un élément qui ne peut rien contenir, changer l'élément porteur plutôt que sortir le contenu.** S'y ajoute un `<details>` « Voir le contenu » qui liste *tous* les exercices avec leur objectif, les échauffements regroupés dans un sous-`<details>` comme le fait déjà `accueil.html`.

**Choisir n'est pas commencer.** Le clic sur une carte *sélectionne* la séance et fait apparaître un bouton « Démarrer la séance » dans cette carte ; il n'ouvre plus la caméra directement. C'est le comportement du poste fixe, et il a une raison : on ouvre une carte pour lire son contenu et sa dernière fois, pas pour se retrouver devant l'objectif. Le geste utilisateur a simplement changé de bouton — `verrou_ecran.tenir()` et la préparation audio restent **au plus près du clic**, avant tout `await`, sinon iOS refuse. La sélection vit dans le document (une classe sur la carte) et non dans une variable : `dessiner_liste` reconstruit tout, et une variable survivrait au redessin en désignant un nœud disparu.

**Le contenu d'une séance ne s'affiche qu'une fois.** La carte portait aussi, sous son titre, les cinq premiers exercices avec leur cible — juste au-dessus du `<details>` qui déplie les mêmes lignes, en plus complet. La liste tronquée a disparu (et `puce_objectif` avec elle) ; ne reste que la ligne de compte (« 6 exercices · 7 échauffements »), qui dit l'ampleur sans dire le contenu et qu'on ne lit nulle part ailleurs sans déplier. Deux corollaires. Le **badge orange de cible manuelle** vivait dans ces puces : il est devenu un badge agrégé (« 2 cibles figées ») posé au-dessus du repli, parce qu'un décrochage ne doit jamais demander un clic pour se voir ; le détail déplié colore en plus la cible concernée. Et le crayon « Modifier » est passé en `position:absolute` dans le coin haut-droit de la carte, discret : c'est une retouche, pas l'action principale, et l'action principale est la carte elle-même. Dans le contenu déplié, la cible suit **immédiatement** le nom au lieu d'être rejetée contre le bord droit par un `space-between` — sur une ligne courte, l'œil devait traverser la carte pour relier les deux.

La liste des séances de l'application porte enfin les deux éléments de l'accueil qui lui manquaient : le **badge orange de cible manuelle** et le bandeau **« dernière fois »**. Le second est le jumeau du calcul que `web/app.py` fait pour l'accueil — pour chaque nom de séance, la plus récente non abandonnée, et par exercice ses séries `completee` seulement, plus le ressenti quand il signale un écart (`LIBELLES_RESSENTI` n'y liste ni `ok` ni `dur`). **Le badge, lui, est en lecture seule, et c'est une conséquence directe de « le fichier fait autorité »** : retirer la marque écrit dans `seances_personnalisees.json`, ce qu'un appareil hors ligne ne peut pas faire. L'écran le dit explicitement plutôt que d'afficher une croix qui ne marcherait pas — le badge existe pour rendre le décrochage *visible*, et il remplit ce rôle sans le bouton. Détail de structure : le `<details>` vit **à côté** de la carte et non dedans, la carte étant un `<button>` qui lance la séance — un `<details>` imbriqué dans un bouton est invalide et le navigateur déplacerait le nœud en silence.

L'onglet **Exercices** porte les deux mêmes écrans que `/exercices` et `/exercice/<nom>` : le catalogue, qui **sépare les exercices des échauffements** comme partout ailleurs, et la fiche d'un mouvement — qui porte depuis la fusion « où j'en suis », la progression par paliers, le graphique et le recalage, en plus des consignes. C'est le seul endroit où un mouvement s'explique hors séance. Aucune logique n'était à porter — `decrire()` exportait déjà presque toute la fiche ; il lui manquait `materiel` et `est_echauffement`, les deux champs que `fiche_mouvement` ajoute côté Flask. `static/exercices.css` est partagée par les deux, et sa règle `.carte` est délibérément sans élément : le poste fixe en fait un `<a>` vers une URL, l'application un `<button>` qui change d'écran — la carte est la même, son élément porteur non. Les variantes (`variante_facile`/`variante_difficile`) y naviguent d'une fiche à l'autre des deux côtés.

L'onglet **Programmes** de l'application montre la même chose que `/programmes` : jauge d'avancement, exigences groupées par séance, prescription **et** sa traduction sur le barème — les deux, parce que n'afficher que la seconde rendait la page incompréhensible. Il y ajoute la prochaine séance à enchaîner, que le poste fixe porte sur son accueil. `static/programmes.css` est partagée par les deux, comme `hud.css` et `ressentis.css`. `resume_palier`, jumeau de `Palier.resume()`, vit dans `programmes.js` et sert aussi aux fiches d'exercice, qui en avaient leur propre copie — écrite avec « × » là où le Python écrit « x ».

L'historique de l'application porte aussi la **suppression d'une séance**, avec la même confirmation que le poste fixe : `historique.supprimer_seance` était déjà porté, seule l'interface manquait. Le bouton vit dans un `<details>` et doit appeler `preventDefault`, sinon le clic replie la fiche.

**Le questionnaire de matériel de l'application** reprend la forme de celui du site : un `<select>` par poids (Aucun / Un / Une paire) plutôt que deux cases, parce que « une paire » et « un haltère seul » ne sont pas deux options indépendantes mais **une quantité** — deux cases laisseraient cocher « paire » sans « seul », ce que `normaliser` devrait ensuite rattraper. Enregistrer **reconstruit le moteur** (`construire_moteur`) : `Baremes` normalise l'inventaire une fois pour toutes à la construction, donc sans ça les cibles resteraient calculées sur l'ancien matériel, **en silence**. L'effet se voit immédiatement sur la liste des séances, et c'est voulu : en retirant tout au-dessus de 4 kg, un objectif de `4×14 à 5 kg` devient `5×14 à 4 kg` — même volume, une série de plus faute de charge.

**L'historique et les records de l'application reprennent les formes du site desktop**, pas son CSS : mêmes classes, mêmes proportions, variables de l'application. Lier `base.css` aurait été plus court mais aurait fait entrer une mise en page de site — conteneurs, onglets, largeurs fixes — dans une page qui a la sienne, avec des collisions de cascade à démêler. Reprendre le **langage visuel** sans le **document** est ce qui évite que les deux aient l'air de deux applications différentes. Une décision d'affichage vaut d'être gardée : l'historique montre **le détail des séries**, pas seulement leur somme, parce que c'est lui qui rend visible le **maillon faible** — deux curls de même volume total, `12 12 10 12` contre `12 12 12 12`, donnent le niveau 14 et le niveau 16, et une ligne agrégée (« 46 répétitions ») ne permettrait pas de comprendre pourquoi. Les séries inachevées y sont colorées à part, puisqu'elles ne prouvent rien. L'écran des records distingue les **trois situations** d'`etat_niveau` sans les confondre : hors barème (« à tester », ce qui n'est pas « niveau 0 »), barème épuisé, et le cas ordinaire — avec la note qui explique qu'un palier suivant peut demander **moins** de répétitions quand il monte en charge. Les onglets **redessinent** l'écran qu'ils ouvrent : l'historique change à chaque séance, et un écran dessiné une fois pour toutes serait périmé.

**Un écran de suivi doit mener quelque part, et se lire replié.** Trois règles qui valent des deux côtés. (1) La date, la durée et le nombre d'exercices sont **dans le `<summary>`** de chaque séance : replié, on doit pouvoir reconnaître une séance sans la déplier (le poste fixe le faisait déjà ; l'application a dû remonter son `.meta` dans le summary, qui devient un bloc de deux lignes). (2) **Le nom d'un exercice mène à sa fiche** — c'est le seul endroit où un mouvement s'explique, et « c'était quoi, déjà ? » se demande justement en relisant sa séance. Le poste fixe pose un `<a href="/exercice/…">`, l'application un `<button class="vers-fiche">` qui change d'écran, avec `preventDefault()` puisqu'il vit dans un `<details>`. Elle retient d'où l'on vient (`retour_de_la_fiche`) : repartir systématiquement vers le catalogue ferait perdre la séance qu'on lisait. (3) **Le graphique de progression n'est plus replié** et **chaque point mène à sa séance**. Il était replié du temps où l'écran des records les empilait tous ; depuis la fusion, une fiche ne parle que d'un mouvement et le graphe y est la réponse à la question qu'on est venu poser. Pour les liens, `graphique.js` n'a pas eu à bouger : il enveloppe un point dans un `<a>` dès que l'appelant fournit un `lien`, et l'application lui passe une **ancre** (`#seance-<id>`) qu'elle intercepte pour déplier la carte visée et y faire défiler, là où le poste fixe passe l'URL `/historique/<id>`. **Un clic montre, un double-clic emmène** — côté application seulement : un point mesure six pixels, et partir sur un autre écran au premier contact punit un doigt approximatif. Le premier appui écrit sous le graphe la date et le détail des séries de cette séance (`resume_series`), le second dans les 500 ms l'ouvre dans l'historique. Le seuil est délibérément plus large que le double-clic du système : au doigt, deux appuis se séparent davantage qu'au pointeur. Le second appui est reconnu **par le temps et par la cible** et non par un événement `dblclick`, qui n'arrive de toute façon qu'après le premier `click` et n'est pas fiable au toucher sur iOS. Le poste fixe garde son lien ordinaire, et le module n'a toujours pas bougé : c'est l'appelant qui décide de ce qu'un clic fait.

**Un point de graphique se touche au doigt, et trois choses en découlent** — apprises en le vérifiant à largeur d'iPad, pas en le supposant. (1) Un tap *est* un `click` sur iOS, donc la mécanique marche telle quelle ; c'est `dblclick` qui ne serait pas fiable, d'où la reconnaissance par le temps et la cible. (2) **Le disque visible n'est pas la cible** : six unités de viewBox font environ huit pixels sur une tablette, qu'on ne vise pas au doigt. Chaque point porte donc un second cercle transparent (`.chart-cible`, `fill="transparent"` et non `fill="none"`, qui ne reçoit aucun événement), **plafonné à la moitié de l'écart entre deux points** : sur un historique fourni les cibles se chevaucheraient et c'est le dernier dessiné qui gagnerait — on toucherait un point pour en ouvrir un autre. Les règles de couleur visent en conséquence `.chart-disque` nommément ; écrites sur `circle`, elles peindraient la cible et la rendraient visible. (3) `touch-action: manipulation` sur le point retire le **double-tap pour zoomer** de Safari, qui sinon agrandit la page au lieu d'ouvrir la séance — sur ce seul élément, le reste de la page garde son zoom. S'y ajoute un état `.actif` sur le point touché : `:hover` ne dit rien au doigt (et reste collé sur les tablettes qui l'émulent, d'où la garde `@media (hover: hover)`), or sans retour visuel rien ne relie le détail affiché au point qui l'a produit. D'où l'`id="seance-<id>"` sur chaque `<details>` de l'historique.

**La sauvegarde vit sous l'historique**, et non sous l'accueil où elle s'intercalait entre la liste des séances et le choix du jour : c'est l'historique qu'elle sauvegarde, et elle est la suite naturelle de ce qu'on vient de relire. Sa ligne d'état (`mettre_a_jour_etat_base`) se recalcule néanmoins depuis les deux écrans — une séance enregistrée en fin de séance ne repasse pas forcément par l'onglet Historique.

**Le matériel se lit en trois groupes, pas en une phrase.** Le résumé du profil tenait sur une seule ligne — « paires : 3 kg, 4 kg · seuls : 2 kg · accessoires : … » — où le **même point médian séparait les catégories et les poids entre eux**, si bien que rien ne se détachait. Trois groupes étiquetés (paires / haltères seuls / accessoires), chacun une rangée de pastilles, rendent visible la distinction qui compte et que le questionnaire enseigne déjà : une paire n'est pas un haltère seul.

**Faire passer un historique du poste fixe à l'application** se fait avec `python -m scripts.exporter_profil <profil>`, qui écrit une sauvegarde que l'écran des séances relit (« Importer un fichier »). La migration est presque un transfert direct — les cinq collections JavaScript reprennent les cinq tables SQLite colonne par colonne —, et deux points seulement demandent de l'attention, tous deux liés au profil. Le **cloisonnement** : `utilisateur_id` ne vit que sur les deux tables racines, donc on filtre les racines puis on descend par les clés étrangères ; filtrer les quatre tables indépendamment laisserait passer les exercices d'un autre profil. Et **le profil exporté devient le numéro 1**, celui que l'application connaît, sinon l'historique importé serait invisible. Les compteurs `prochains_id` repartent au-dessus du plus grand identifiant existant : les réutiliser écraserait une séance à la première enregistrée sur l'appareil.
Le fichier produit **n'est jamais versionné** et le script refuse d'écrire dans le dépôt — c'est la même règle qui a fait retirer `personaltrainer.db` du suivi Git. Vérification faite sur l'historique réel : les 19 exercices ayant un niveau le gardent à l'identique des deux côtés, ce qui éprouve d'un coup la migration, `historique.js` et `niveaux.js` sur de vraies données plutôt que sur des tirages.

**La démo statique (`web/static/demo/`)** est le premier livrable testable par quelqu'un d'autre : un exercice au choix, comptage et voix, sans séance ni historique ni base. Elle est **volontairement hors de Flask** — trois raisons qui ne se remplacent pas l'une l'autre : elle n'expose ni `/video` (le flux webcam) ni l'écran de connexion sans mot de passe, elle ne dépend d'aucun profil connecté, et surtout elle peut être **déposée telle quelle sur un hébergeur statique gratuit**, avec une adresse stable et sans qu'aucun PC reste allumé — ce qui rend des testeurs autonomes, là où un tunnel impose une adresse qui change à chaque redémarrage. Servir `web/static` comme racine (entrée `statique` de `.claude/launch.json`) reproduit exactement la forme du déploiement.
`python -m scripts.preparer_demo` exporte le catalogue et rapatrie les sons : **le catalogue n'est jamais recopié à la main**, il est dérivé de `CATALOGUE_EXERCICES` via `Exercice.fiche()`, plus le nom de la fonction de détection — que le JS retrouve dans `DETECTIONS` puisque les deux portent le même nom. Un exercice ajouté au catalogue apparaît donc dans la démo à la prochaine exécution, avec sa fiche. `catalogue.json` est versionné (23 Ko, et son absence rendrait la page vide sans rien dire) mais `sons/` non (copies de fichiers déjà versionnés) : **le régénérer avant tout déploiement**.

**Chaque déploiement marque ses ressources de l'empreinte du commit** (`scripts/empreinte_deploiement.py`, appelé par le workflow sur la copie `_site` seulement). Sans ça, un navigateur qui tient encore l'ancien module en cache le combine avec le nouveau document, et l'application échoue sur une fonction disparue **en accusant un code déjà corrigé** — observé sur un iPad, au démarrage d'une séance, après un correctif pourtant déployé et vérifié en ligne. **Le cache n'est pas en cause, sa granularité l'est** : GitHub Pages sert `Cache-Control: max-age=600` mais chaque fichier expire pour son compte, si bien que le document peut être frais pendant que le module qu'il importe est vieux. Sur iOS il n'existe pas de « recharger en ignorant le cache », et un site ajouté à l'écran d'accueil garde ses modules plus longtemps encore. Changer l'adresse (`camera.js?v=<sha>`) plutôt qu'espérer l'expiration est la seule façon d'être sûr qu'un déploiement est servi entier. Trois détails le rendent correct : les **modules s'importent entre eux**, donc leurs imports internes sont marqués aussi — sinon un module neuf charge ses dépendances depuis le cache ; les **données** le sont également (`donnees/*.json` est relu à chaque ouverture) ; et les **adresses absolues ne sont jamais touchées**, un CDN gérant son propre cache. Rien de tout cela n'a lieu en développement, où le serveur local ne cache rien.

**Le déploiement est automatique, et c'est ce qui rend la règle ci-dessus tenable** : `.github/workflows/demo.yml` relance `preparer_demo` puis publie `web/static` sur GitHub Pages à chaque push sur `main` ou `feat/portage-web`. Le site ne peut donc pas être en retard sur le code, et rien de dérivé n'a besoin d'être versionné. Trois points à connaître avant d'y toucher. Le workflow n'installe **que numpy**, parce que `preparer_demo` n'importe que le catalogue d'exercices — jamais `vision/` ni `audio/` : installer tout `requirements.txt` tirerait opencv et mediapipe pour rien, et si l'arbre d'imports s'alourdit un jour, l'étape doit échouer bruyamment plutôt que d'être blindée à l'avance. La racine du site est une **redirection** écrite par le workflow et non un fichier du dépôt : un lien partagé sans son `/demo/` final tomberait sinon sur une 404 muette, mais ce fichier n'a rien à faire dans le dossier statique de Flask. Enfin le `localStorage` de la démo — résultats accumulés et mesures de fluidité — est **attaché à l'origine** : changer d'adresse (tunnel → Pages, Pages → nom de domaine acheté) efface ce qu'un testeur avait accumulé. C'est la raison de fixer l'adresse **avant** que de vrais usages s'y accumulent, pas après.
**La démo existe pour récolter un avis, pas seulement pour fonctionner** : les résultats s'**accumulent** (`localStorage`, un exercice testé passe au vert et le reste après rechargement), chaque fin d'exercice propose un QCM des problèmes courants plus un commentaire libre, et le bouton de copie vit en tête de la **liste** — un seul envoi pour toute la session, là où un bouton par exercice obligerait le testeur à écrire dix fois. La caméra y occupe tout l'écran en `object-fit: contain` et **jamais `cover`** : recadrer masquerait une partie de ce que le modèle analyse, or c'est précisément le cadrage qu'on cherche à vérifier à l'œil.
**Le résumé rapporte aussi la fluidité, minute par minute**, parce que le panel de test comprend des appareils anciens et que la question n'est pas « combien d'images par seconde » mais « est-ce que ça s'effondre à la cinquième minute », quand la chauffe fait ralentir l'appareil. Trois décisions y tiennent. Le découpage se fait par minute **de caméra** — le temps pendant lequel des images défilent — et **se cumule d'un exercice à l'autre** : la chauffe ne se remet pas à zéro entre deux, alors qu'une mesure par exercice la remettrait. Chaque minute est stockée comme un **histogramme** d'une image/s de large et non comme la liste de ses images : c'est borné (61 nombres, que la minute compte 300 images ou 3000), ça se relit après un rechargement — un vieil iPad ferme l'onglet dès que la mémoire manque, et c'est précisément l'appareil qu'on mesure —, et deux tranches se fusionnent en s'additionnant, ce qu'une médiane déjà calculée ne sait plus faire. Les cases s'indexent par **arrondi et non par troncature** : un flux parfaitement régulier à 12 images/s se mesure 11,9999 en virgule flottante, et une troncature le rangerait systématiquement une case trop bas. Enfin un écart de plus de deux secondes entre deux images n'est **pas** compté comme une image lente : c'est une suspension (écran verrouillé, appel entrant, onglet en arrière-plan), comptée à part, sinon une mise en veille passerait pour un effondrement thermique.

**Chercher plusieurs personnes coûte cher : une seule pose est le défaut.** Mesuré à l'aveugle entre les deux réglages, même iPad et même modèle `full` : **36 images/s et un squelette stable à une pose, contre 24 et un squelette qui saute à quatre**. Chercher plusieurs poses garde son sens en salle de sport — le modèle pourrait se fixer sur un passant — mais ça se paie sur les deux tableaux, donc c'est devenu une case à cocher sur la fiche (`POSES_ENTOURE`) et non l'ordinaire. `?poses=N` force la valeur, et le réglage effectif est **reporté dans le résumé du testeur** : sans lui, deux tests se compareraient sans qu'on sache s'ils tournaient pareil.

Deux règles tiennent le détecteur. `choisirPose` **suit la même personne d'une image à l'autre** (la plus proche du dernier centre retenu) et ne reprend la plus grande qu'au premier choix, ou après un saut de plus de `SAUT_MAX`. Reprendre la plus grande à chaque image semblait sûr et ne l'était pas : deux candidats de tailles voisines échangent leur rang d'une image à l'autre — mesuré à **22 changements de sujet sur 200 images** —, le squelette saute d'un corps à l'autre, et un seul aller-retour suffit à faire compter une répétition qui n'a pas eu lieu. C'est aussi ce qui donnait au squelette l'air de trembler. Et `preparerDetecteur` **sérialise** ses appels au lieu de les laisser se chevaucher : le modèle est fabriqué dès l'ouverture de la fiche, pour que sa quinzaine de secondes de téléchargement soit recouverte par le temps de lecture des consignes, et un clic rapide sur « Démarrer » doit retrouver ce travail en cours plutôt que d'en lancer un second — deux détecteurs coexisteraient, dont un jamais libéré. Pas de fabrication plus tôt que la fiche, en revanche : allouer un détecteur pour quelqu'un qui ne fait que parcourir la liste coûte de la mémoire sur les appareils qui en manquent le plus.

**Le banc d'essai (`?banc=1`) répond à « pourquoi ça ne compte pas ? ».** Il affiche le jeton brut renvoyé par la détection, l'état d'armement du compteur, et la part de temps passée dans chaque jeton depuis le début de l'exercice. C'est la deuxième ligne qui porte le diagnostic : un squat filmé avec une barre sur les épaules rend `fin 100 %` et ne s'arme jamais, là où le seul jeton courant ne dit rien — il a fallu reconstruire ce raisonnement à la main après un test en salle où dix répétitions avaient donné zéro. Deux décisions : il est **derrière un paramètre d'URL** comme `?poses=N`, parce qu'un testeur ordinaire n'a que faire de voir passer « milieu » ; et il compte du **temps** et non des images, parce que c'est de temps que parle quelqu'un qui teste (« je suis resté en bas deux secondes et rien ») et qu'une cadence variant de 16 à 36 images/s rendrait un comptage d'images incomparable d'un appareil à l'autre. Le délai entre deux images y est plafonné par `INTERVALLE_MAX`, pour la même raison qu'ailleurs.

**Vérifier une page dont la boucle vit dans `requestAnimationFrame`** demande un détour : un volet de prévisualisation masqué ne déclenche **aucune** image (mesuré : zéro en 500 ms), donc la page semble morte sans qu'aucune erreur n'apparaîsse. Remplaçer `window.requestAnimationFrame` par un pas à pas avant que la page ne démarre sa boucle rend celle-ci pilotable image par image — c'est ce qui permet de tester **le code de la page** et non une réplique de sa logique écrite à côté, qui passait au vert pendant que la page était cassée. Une réserve : `HoldPosition` lit `performance.now()` et non l'horodatage de la boucle, donc un test de geste doit laisser le temps **réel** s'écouler entre deux images.
**Le cadrage se vérifie pendant la préparation, et seulement là** (`web/static/js/cadrage.js`). Une testeuse a posé la caméra à 40 cm du sol, fait dix squats, et l'application n'a rien compté ni rien dit : la consigne de cadrage existait pourtant — sur la fiche, lue avant de commencer, puis jamais rappelée. Un cadrage faux ne se voit pas de l'intérieur, on se voit à l'écran donc on se croit vu. **La règle première est de ne parler que lorsque la détection ne peut pas travailler**, et elle a été apprise à ses dépens : un contrôle de distance mesurait l'étendue *verticale* des points requis, ce qui n'est un indice d'éloignement que pour quelqu'un **debout** — une planche parfaitement cadrée, qui remplit l'image en largeur, mesure 0,13 de hauteur et s'entendait dire « approche-toi », sur trois exercices d'affilée. Il a été **supprimé et non réglé** : être loin n'empêche pas la détection, MediaPipe suit très bien un corps petit dans l'image, alors qu'être hors champ l'empêche puisque le landmark est alors une invention du modèle. Une consigne qui se déclenche à tort est pire qu'absente : elle apprend à ne plus la lire. N'ajouter un critère ici qu'après avoir nommé la détection qu'il rend impossible. Quatre décisions tiennent le reste du module. (1) **Les points dont un exercice a besoin ne sont pas déclarés, ils sont observés** : `points_utilises` rejoue la détection sur un corps espion (`Proxy`) qui note chaque landmark qu'on lui demande — même principe que le mode déduit du jeton renvoyé, rien à maintenir à côté du code donc rien qui puisse mentir, et une détection ajoutée est couverte le jour où elle est écrite. Le buste est ajouté d'office, parce qu'`elevation_laterale_detection` ne regarde qu'une épaule et un poignet et qu'un cadrage réduit au haut du corps passerait. (2) **La `visibility` n'entre volontairement pas dans le calcul** : elle s'effondre sur le membre éloigné de toute vue de profil, où le cadrage est pourtant parfait — s'en servir rouvrirait exactement le défaut que les deux gainages viennent de corriger en moyennant les côtés. Le cadrage se juge sur la **position** dans l'image, pas sur la confiance du modèle. (3) **Le contrôle passe avant l'immobilité** : quelqu'un de parfaitement immobile hors champ est « prêt » au sens de `mesurerMouvement`, et c'est précisément la séquence qui produit un exercice entier à zéro répétition. (4) **Il se tait au décompte** : un squat profond fait légitimement sortir des points du cadre, et signaler pendant l'effort reviendrait à crier pendant le mouvement — le filet de sécurité reste le bouton « je commence », qui court-circuite tout.
La consigne se compose de **deux clés** — ce qui manque, quoi faire — et jamais d'une phrase en dur : une table unique des combinaisons en demanderait vingt-huit, et la formulation doit pouvoir se corriger sans toucher à l'arbitrage. Deux règles de rédaction en découlent. Parmi les parties sorties par un même bord, on nomme **la plus éloignée de ce bord** (les genoux plutôt que les pieds), parce qu'elle implique toutes les autres, là où nommer la plus proche laisse croire qu'il ne manque qu'un centimètre. Et **aucune consigne ne dit gauche ni droite** : l'image est affichée en miroir, un côté à l'écran est l'autre dans la pièce ; le centre, lui, est le même des deux côtés. Coupé en haut *et* en bas, il n'y a plus de partie à nommer — ni monter ni baisser la caméra n'y change quoi que ce soit, la seule réponse est de reculer.

**La caméra est ouverte une fois par session, pas une fois par exercice.** Chaque `getUserMedia` est une demande d'autorisation potentielle : sur une session de 23 exercices, Safari a redemandé l'accès trois fois à un testeur, en plein test. Entre deux exercices les pistes sont donc **désactivées** (`enabled = false`) et non arrêtées — plus aucune image ne circule, donc rien n'est analysé ni affiché, mais la permission reste acquise. Elles ne sont réellement arrêtées que dans deux cas : un changement de caméra, et le `pagehide` qui rend le périphérique en quittant la page. Le prix est que le voyant de la caméra reste allumé pendant les temps morts, ce que l'écran de fin annonce explicitement plutôt que de le laisser subir.

Le mode d'un exercice — compter des répétitions ou chronométrer un maintien — **se déduit du jeton renvoyé** (`maintien`/`repos` contre `debut`/`fin`/`milieu`) et non d'une métadonnée exportée : il n'y a donc rien à déclarer, et rien qui puisse mentir. L'accumulation de temps y plafonne chaque delta comme le fait `INTERVALLE_MAX` côté Python — un onglet suspendu par iOS ne doit pas créditer d'un coup tout le temps écoulé.

**`web/static/js/lecteur.js` est le jumeau du lecteur et de `coach()`.** Il a manqué : la première version web jouait chaque son dès qu'il était demandé, tous en même temps — « le compte se marche un peu dessus », ce qui n'était pas un raffinement à venir mais une **pièce non portée**, et une régression par rapport au desktop. Trois règles la composent, toutes venues du Python : **un son à la fois** (le lecteur attend la fin du précédent, comme le thread attend `mixer.get_busy()`), **une file à priorités** (`compteur` vaut 1, `bip` 2, `fin_serie` 10), et **un événement ≥ 5 vide les petits sons en attente** plutôt que de faire la queue derrière eux — quand une série se termine, les bips de comptage n'ont plus rien à dire. S'y ajoute le délai minimal entre deux annonces d'un même type (`DELAIS_ENTRE_ANNONCES`), sans lequel la correction de gainage se répète à chaque image où la position se perd. Les **trois tables sont exportées du Python** par `preparer_demo` (`donnees/sons.json`) et jamais réécrites : ni les fichiers, ni les priorités, ni les délais. Vérifié en rejouant la même salve des deux côtés sur un rythme réaliste (répétitions à 40 ms, sons de 100 ms) : même ordre `1, 2, 3, fin_serie`, jamais deux sons simultanés. Une réserve mesurée : sur une salve de quelques microsecondes, l'ordre diverge — en JavaScript le premier son est pris **synchroniquement** à l'empilement, tandis qu'en Python producteur et consommateur sont deux threads et que c'est une course. Ce cas n'existe pas dans une séance réelle, mais il interdit de comparer les deux files sur un tir groupé.
**Le coach parle pendant les pauses, et il a fallu deux corrections pour ça.** Le déclenchement par changement de phase *était* porté (`annoncer_changement` dans l'application), mais amputé : il annonçait l'entrée en repos, puis plus rien pendant les soixante secondes suivantes, et rien non plus au retour à l'effort. Ce qui manquait est `annoncer_temps_repos`, désormais jumelée dans `web/static/js/moteur.js` sur le modèle exact d'`annoncer_temps_restant` — deux différences : le repère `repos_restant_precedent` vit sur la **séance** et non sur le bloc (un repos n'appartient à aucun bloc, il est entre deux), et `annoncer_changement` le remet à `null` à chaque entrée en pause *et* au retour en `exercice`, sans quoi le repos suivant hériterait du compte du précédent. Le décompte est appelé avec `Math.trunc` et non `Math.round` : le Python fait `int(...)`, qui tronque, et une demi-seconde d'écart décale le franchissement d'un seuil — même famille de piège que le `round()` de `calibration.js`.
Second défaut, plus instructif : `annoncer_temps_repos` réclamait la clé `"repos_20"`, **absente du dictionnaire `messages`** alors que `repos_20.wav` était sur le disque depuis toujours. `coach()` sortant silencieusement sur une clé inconnue — par la même prudence qui interdit de lever dans la boucle caméra —, le seuil des vingt secondes était muet **des deux côtés**, sans que rien ne le signale jamais. *Une table de clés qui ne lève pas se vérifie de l'extérieur* : `set(priorites) - set(messages)` sort encore `temps_30`, laissée telle quelle faute de fichier.
**Reste non porté, délibérément** : `annoncer_prochaine_etape`, qui annonce le nom du prochain exercice. Elle cherche ses fichiers par glob dans `audio/Fichiers/annonces_etapes/` et ne passe pas par `sons.json`, donc rien ne l'exporte au navigateur. L'application dit « repos » puis « changement d'exercice » là où le poste fixe nomme le mouvement.

Coach vocal (`audio/`) : `coach.py` associe des clés d'événements (`"debut_serie"`, `"repos"`, `"compteur"`, etc.) à des fichiers `.wav` dans `Fichiers/`, choisis parfois aléatoirement ; `lecteur.py` les joue via `pygame`. **L'ouverture de la carte son et le démarrage du thread de lecture se font au premier son joué, jamais à l'import** : ce module réclamait un périphérique audio dès qu'on l'importait, si bien qu'importer `audio.coach` — ce que font `session/` et `main.py` — suffisait à faire planter une machine qui n'en a pas, c'est-à-dire un serveur. Une initialisation qui échoue coupe le son et laisse l'application tourner, au lieu de l'emporter. Ne pas remettre d'effet de bord au niveau du module. `nettoyer_sons.py`/`generer_annonces_manquantes.py` sont des scripts d'outillage (nettoyage de silence, génération de sons manquants) opérant sur `a_traiter/` → `Fichiers/`, pas sur le chemin critique de l'app.

Persistance (`historique/database.py`) : SQLite (`personaltrainer.db`), aucune ORM. Les colonnes ajoutées après coup passent par un mini-système de migration maison (`PRAGMA table_info` + `ALTER TABLE ADD COLUMN` conditionnel dans `initialiser()`) — pas de table de version, pas de numéro de migration : c'est ce pattern qu'il faut suivre pour toute nouvelle colonne. `enregistrer_seance` écrit une séance complète avec ses séries détaillées et **retourne son identifiant**, dont l'écran de fin a besoin pour annoter les lignes qu'elle vient de créer ; `enregistrer_ressentis` fait cette annotation (`UPDATE`, pas `INSERT`) et refuse une valeur hors échelle ; `recuperer_historique`/`statistiques_exercices`/`derniere_performance` recalculent volumes/records/PB à la lecture. `corrections_niveaux` stocke les ancrages de niveau du moteur de progression (`enregistrer_ancrage`/`recuperer_ancrages`/`recuperer_historique_ancrages`/`supprimer_ancrage`/`supprimer_ancrages`) — c'est la seule table que le moteur écrit, tout le reste de son calcul étant dérivé. Pas de gestion d'erreurs SQL (pas de try/except autour des connexions) — à garder en tête si on touche ce fichier.

**La base n'est pas versionnée, et ne doit pas le redevenir.** `*.db` figure dans `.gitignore`, mais un `.gitignore` n'a aucun effet sur un fichier déjà suivi : `personaltrainer.db` l'a été longtemps, ce qui publiait un historique d'entraînement réel dans un dépôt public et produisait un diff binaire à chaque séance jouée. Il en a été retiré (`git rm --cached`, le fichier restant sur disque). Un clone démarre donc **sans base** : `sqlite3.connect` la crée au premier lancement et `initialiser()` en pose les tables, cas déjà prévu puisque c'est l'écran de connexion qui crée le premier profil sur une base vierge. Ne jamais la remettre sous suivi (`git add -f`) — ce serait publier les données des utilisateurs.

**Un profil se lit, se crée entier, et se supprime.** Trois décisions liées. (1) La page de profil est en **lecture seule** par défaut, des deux côtés : un formulaire toujours ouvert donne l'impression qu'il y a quelque chose à remplir alors qu'on vient le plus souvent vérifier ce qui est déclaré. « Modifier mes informations » et « Modifier mon matériel » dévoilent les champs déjà écrits ; le bloc matériel du poste fixe, déjà en lecture avec son lien vers `/materiel`, est le modèle. Ne pas oublier `construire_moteur()` après l'enregistrement du matériel dans l'application — `Baremes` normalise l'inventaire une fois pour toutes à la construction. (2) **Les quatre mesures sont demandées à la création**, pas après : une page de profil qu'on ne visite jamais revient à ne jamais les avoir. Elles restent facultatives, rien dans le barème n'en dépend. Côté Flask, `POST /api/utilisateurs` accepte un bloc `mesures` que `_mesures_valides` — partagé avec `POST /api/profil`, pour que les deux acceptent exactement la même chose — valide avant `definir_mesures`. Le matériel et la première séance restent sur `/bienvenue` : c'est le tunnel d'accueil, qui a sa propre logique de garde. (3) **Un profil est supprimable, entièrement**, `supprimer_utilisateur` des deux côtés : la descente suit les clés étrangères (séries → exercices → séances, puis ancrages, puis la ligne) exactement comme `supprimer_seance`, et filtrer les quatre collections indépendamment laisserait les exercices d'un autre profil. Deux refus vivent dans la couche données plutôt que dans chaque écran : le **dernier** profil (une base sans profil rend l'application inutilisable, `_profil_courant` levant par conception) et, côté Flask uniquement, le profil **connecté** (la session désignerait une ligne disparue). Rien ne rattrape ce geste, donc l'export est proposé avant : `GET /api/utilisateurs/<id>/export` sert la fonction de `scripts/exporter_profil.py` — le format n'a qu'une définition — et l'application propose `historique.exporter(base)`. La jumelle JavaScript est **dans le harnais de l'historique**, qui crée pour ça un troisième profil et continue de le relire après sa suppression : c'est le seul moyen de voir une séance, un exercice ou un ancrage laissé derrière. Sabotée (ancrages non supprimés), elle sort des divergences au pas où elle cède.

**Le cloisonnement par profil tient en une colonne et un résolveur.** `utilisateur_id` ne figure que sur les deux tables *racines*, `seances` et `corrections_niveaux` ; `exercices` et `series_realisees` héritent par leur clé étrangère et ne doivent pas la dupliquer — ce serait une dénormalisation à maintenir. Toute fonction cloisonnée prend un `utilisateur_id=None` qu'elle passe à `_profil_courant` : `None` veut dire « le profil connecté » (résolu via `core/utilisateur.py`), un entier veut dire « ce profil-là ». C'est ce paramètre explicite qui rend un futur classement possible (`etats_niveaux(recuperer_historique(utilisateur_id=2))`) sans toucher à la couche données. Sans profil connecté, `_profil_courant` **lève** au lieu de retomber sur un défaut : écrire la séance de quelqu'un dans l'historique d'un autre est une corruption qu'on ne voit jamais, un plantage se voit. Conséquence directe : rien dans `progression/` n'a été modifié pour les profils — tout le module retombe sur `recuperer_historique()` sans argument, donc le cloisonnement s'applique par en dessous.

**Le profil porte quatre mesures du corps, et aucune ne pilote le barème** : `sexe`, `date_naissance`, `taille_cm`, `poids_corps_kg`. Elles suivent le mini-système de migration maison (`PRAGMA table_info` + `ALTER TABLE ADD COLUMN` conditionnel), **sans `DEFAULT`** — `NULL` veut dire « non renseigné », et personne n'est obligé de les donner. Écriture par `definir_mesures`, qui ne touche que les clés présentes et traduit une chaîne vide en `NULL` (c'est ce que rend un champ de formulaire qu'on vide à la main) ; comme toute écriture sur `utilisateurs`, elle doit être suivie d'un `rafraichir()`.
**Le nom `poids_corps_kg` est délibéré et ne doit pas être raccourci.** Partout ailleurs dans le projet, « poids » désigne la **charge soulevée** — `exercices.poids`, `series_realisees.poids`, les haltères du matériel, le champ du formulaire de recalage. Un champ nommé `poids` sur le profil créerait une ambiguïté permanente à la lecture, du même genre que celle qu'`etat_seance` évite face à `SessionManager.etat()`.
Les deux côtés les portent : quatre colonnes SQLite (plus les **quatre endroits qui décrivent un profil** : la migration, `_profil_depuis_ligne`, et les deux `SELECT`) et quatre champs dans `creer_utilisateur` de `historique.js`. L'import de sauvegarde n'a rien demandé — il recopie les collections entières, pas une liste blanche de champs.
`/profil` et l'`ecranProfil` de l'application regroupent identité, mesures, matériel et changement de personne. Côté Flask, la page **renvoie vers `/materiel`** plutôt que de recopier le questionnaire ; côté application, `ecranMateriel` a été absorbé, ce qui impose de **conserver l'appel à `construire_moteur()`** après enregistrement — `Baremes` normalise l'inventaire une fois pour toutes à la construction, et l'oublier laisserait les objectifs calculés sur l'ancien matériel, en silence. `/profil` n'est volontairement **pas** dans `ROUTES_ONBOARDING` : un profil neuf déclare d'abord son matériel, et une route de trop dans cet ensemble ouvre l'application entière.

**Le matériel appartient au profil** (`core/materiel.py`, colonne `utilisateurs.materiel` en JSON). C'est **un inventaire, pas deux échelles** : `progression/paliers.py` raisonne sur `ECHELLE_UN_HALTERE` (2→18) et `ECHELLE_DEUX_HALTERES` (2→10), mais ce sont deux *vues* d'un même stock — « une paire jusqu'à 10 kg, des haltères seuls jusqu'à 18 ». Le profil déclare `{poids: quantité}` une fois et `echelle_disponible` en dérive les deux (`quantité >= 1`, `quantité >= 2`), ce qui interdit de posséder une paire de 12 kg sans posséder l'haltère de 12 kg. Ces deux constantes ne sont plus que la **gamme de référence** du questionnaire.
Deux règles à ne pas confondre. Le matériel **restreint** l'échelle mais ne la vide jamais : `echelle_exercice` finit par `retenue or echelle[:1]`, donc une échelle vide ferait planter tout le moteur — y compris l'affichage des records — sur quelqu'un qui n'a coché aucun haltère. `echelle_disponible` retombe pour cette raison sur la gamme complète plutôt que de rendre `()`. La question « puis-je faire ce mouvement ? » vit **à part**, dans `exercice_realisable`, qui est strict là où l'échelle est permissive : rien ne casse s'il répond non. `normaliser(None)` rend le matériel complet d'avant la colonne — un profil existant ne change donc pas de barème —, mais un inventaire *déclaré* vide reste vide : les deux ne veulent pas dire la même chose.

La migration s'appuie sur un détail de SQLite : `ALTER TABLE … ADD COLUMN … DEFAULT 1` **remplit rétroactivement** les lignes existantes, si bien que l'historique d'avant les profils se rattache seul au profil 1. `initialiser()` crée ce profil (`NOM_PROFIL_REPRIS`) **seulement s'il y a des séances à lui donner** : sur une base vierge, c'est l'écran de connexion qui crée le premier profil, et personne n'hérite par accident de l'historique d'un autre.
`statistiques_exercices` garde le `seance_id` de chaque record (`meilleure_charge`, `meilleur_volume`, ...), lu par la fiche d'exercice. **`historique.html` ne l'affiche plus** : la page ne porte qu'un seul marqueur de progression, la montée de niveau (`montees_de_niveau`). Le badge de record de volume qui l'accompagnait disait la même chose en moins bien — il ne lisait que `meilleur_volume`, donc était **structurellement muet sur tout exercice au poids du corps** (volume nul : pompes, gainages, squats), et ne pouvait apparaître qu'une seule fois dans tout l'historique, sur la séance détentrice du record courant, là où les montées de niveau jalonnent la timeline. Conséquence assumée : un record de volume sans franchissement de palier (plus de séries à charge égale) n'affiche plus rien.

**Liens vers les fiches.** Ils pointaient sur `/records#exercice-<slug>`, fabriqué par un filtre Jinja `ancre` ; depuis la fusion ils visent directement `/exercice/<nom|urlencode>`, ce qui supprime d'un coup l'ancre, le filtre et le JS qui dépliait la bonne carte à l'arrivée — **une URL qui désigne une page vaut mieux qu'une URL qui désigne un fragment qu'il faut ensuite ouvrir soi-même**. Les points de départ sont le nom d'exercice et le badge de montée de niveau dans `historique.html`, et le nom d'exercice dans `programmes.html`. `_ancre` reste, mais pour les seules clés de programme.

L'accueil porte un **résumé de programme, et un seul** : on n'en suit qu'un à la fois. Le choix est une préférence **par profil** (`utilisateurs.programme_choisi`, même chemin que `seance_initiale` : migration `ALTER TABLE` sans `DEFAULT`, ajout aux quatre endroits qui décrivent un profil, `definir_programme_choisi` suivi d'un `rafraichir()`).
**`NULL` veut dire « aucun choix », et plus rien ne le recouvre.** `programme_de_l_accueil` retombait sur le premier programme disponible sans rien écrire ; il rend désormais `None`, et l'accueil **invite à choisir** au lieu de proposer un programme que personne n'a demandé. Le repli silencieux était la moitié d'une bonne intention : ne rien écrire préservait la donnée, mais l'affichage prétendait quand même qu'un choix existait — donc la distinction était perdue là où elle comptait, à l'écran.
La même règle gouverne `/programmes` : **tant qu'aucun choix n'est fait, tous les programmes s'affichent, repliés** (leurs exigences dans un `<details>`, l'entête et la jauge toujours visibles pour qu'on puisse comparer) ; **dès qu'un choix est fait, seul celui-là reste**, et un bouton « Changer de programme » repasse `programme_choisi` à `NULL`. Voir les autres sous le sien inviterait à papillonner, ce qui est exactement ce qu'un programme sert à éviter. Le sélecteur « Changer de programme » de la carte d'accueil a disparu au profit d'un lien vers `/programmes` : deux endroits pour la même règle, c'était deux endroits à corriger le jour où elle change. Reste sur la carte « Commencer plutôt par », une **bascule ponctuelle** qui ne stocke rien et se contente de réécrire l'attribut `data-seance` du bouton de démarrage — la proposition automatique de `prochaine_seance` reprend la main au prochain chargement. Ce bouton n'a pas de gestionnaire propre — il porte un `data-seance`, et le gestionnaire générique de l'accueil s'en charge déjà ; seul le défilement vers la carte correspondante est ajouté. **Le bandeau annonce la séance retenue, pas la proposition automatique.** Dès qu'une séance du programme est sélectionnée, elle prime sur `prochaine_seance` — côté serveur au chargement (`index` compare `controleur.nom_selectionne` aux séances liées), côté client par `refleterSeanceDuProgramme`, appelé aussi bien par le sélecteur que par `selectionnerSeance`. Sans cela, cliquer « Push » laissait le bandeau afficher « Jambes et abdos », et le bouton lançait autre chose que ce qui était écrit. Une séance hors programme ne touche pas au bandeau, qui garde sa proposition. Les séances proposées dans la bascule sont filtrées par `seances_du_programme` : `liaison_seances` rend `None` pour un libellé sans recouvrement d'exercices, et il n'y aurait rien à lancer. Les onglets Historique / Programmes / Exercices figurent sur les pages de suivi, plus le profil poussé à droite. Le troisième ouvre le catalogue des fiches (`/exercices`, `/exercice/<nom>`) : c'est le seul endroit où un mouvement s'explique — et, depuis la fusion, où l'on lit son niveau et sa progression.

Web (`web/app.py`) : serveur Flask exposant l'API JSON pilotant le `SessionManager` global (démarrage/pause/navigation de séance, CRUD des séances personnalisées, suppression dans l'historique) et les pages HTML (`templates/`) — accueil, création/édition de séance, historique, records, flux vidéo MJPEG (`/video`, lit `state.latest_frame`).

**La connexion est un garde global, pas un test par vue.** `_exiger_un_profil` (`@app.before_request`) redirige vers `/connexion` — ou répond 401 sur `/api/` — tant qu'aucun profil n'est connecté ; seules les routes de `ROUTES_SANS_PROFIL` y échappent. Une trentaine de routes touchent la base : en oublier une donnerait la page d'erreur brute de `_profil_courant` au lieu de l'écran de connexion. **Ajouter une route au flux de connexion oblige à l'inscrire dans cet ensemble.** Le nom du profil arrive dans les templates par un `@app.context_processor` (variable `profil`), et non route par route.

**Une séance d'un seul exercice s'enregistre sous le nom de cet exercice**, et
c'est à ça que `est_seance_de_test` la reconnaît pour la tenir hors de
l'historique d'entraînement (elle compte quand même pour les records). Le mode
test posait `nom_selectionne = "test"`, un nom qu'aucun exercice ne porte : le
filtre ne se déclenchait donc jamais. Même règle pour `derniere_performance`,
qu'il faut interroger avec le nom de l'exercice.

**Un profil neuf déclare son matériel avant tout le reste.** Second
`@app.before_request` (`_exiger_onboarding`) plutôt qu'une condition ajoutée au
premier : les deux ne protègent pas la même chose et n'ont pas la même liste
d'exceptions, et celui-ci ne s'applique qu'à quelqu'un de déjà connecté.
`/bienvenue` ne contient plus que le questionnaire de matériel et le choix de la
première séance — le tunnel de calibration exercice par exercice a disparu, son
test se jouant désormais **en séance**. `/materiel` sert le même template en
modification, et `/api/materiel` écrit les deux colonnes à la fois : déclarer
son matériel *est* l'accueil, les séparer laisserait un profil coincé sur
`/bienvenue` après avoir répondu.
`ROUTES_ONBOARDING` a le même piège que `ROUTES_SANS_PROFIL` — une route oubliée
renvoie l'utilisateur sur `/bienvenue` en boucle — mais aussi le piège inverse :
**une route de trop y ouvre l'application entière**. Un test rapide de
cohérence : `ROUTES_ONBOARDING - {r.endpoint for r in app.url_map.iter_rules()}`
doit être vide, sinon un nom d'endpoint mal orthographié ne protège rien en
silence.
Deux colonnes portent l'état (`utilisateurs.onboarding_termine`,
`seance_initiale`). Le `DEFAULT 1` de la migration existe pour les profils *déjà
là* — `creer_utilisateur` pose explicitement `0`, sinon un nouveau venu
sauterait le tunnel. Le profil connecté (`core/utilisateur.py`) transporte
désormais ces colonnes pour que le garde n'interroge pas la base à chaque
requête : **toute écriture dessus doit appeler `rafraichir()`**, faute de quoi la
session garde une vue périmée et le tunnel se rouvre.
Le bouton « Je passe cet exercice » ancre au palier 1 : c'est un écart assumé au
caractère obligatoire du tunnel, sans lequel une blessure ou un matériel
manquant bloquerait définitivement l'accès à l'application.

**Une séance appartient au profil qui l'a choisie, pas à celui qui est connecté quand elle s'écrit.** `SessionManager.selectionner` fige `Circuit.utilisateur_id`, et `main.py` le passe à `enregistrer_seance`. Ce n'est pas une précaution théorique : le statut bascule sur `finished` avant que le thread caméra n'écrive, l'utilisateur peut changer de profil dans cet intervalle, et une lecture du profil connecté à ce moment-là créditerait le mauvais athlète — ou lèverait dans un thread où rien n'attrape les exceptions, emportant la boucle caméra.

La barre d'onglets vit dans `templates/_navigation.html`, **premier et seul `{% include %}` du projet** : elle était dupliquée à l'identique dans quatre pages, et y ajouter le profil en aurait fait une cinquième copie. Ses styles sont passés dans `static/base.css` ; chaque page ne garde de `.tabs` que sa marge. Ne pas généraliser en `{% extends %}` au passage — les templates restent des documents autonomes. Son lien de profil mène à `/profil` et non plus à `/connexion` : changer de personne est une des choses qu'on fait sur sa page, pas la seule.
**L'application a connu exactement la même histoire, et pour la même cause.** Sa barre était recopiée à la main dans ses cinq écrans, et le bouton de profil n'existait que dans la copie de l'accueil ; c'est en voulant le rendre accessible partout qu'il a fallu la factoriser. `remplir_barres_onglets()` la rend désormais dans chaque `<div class="onglets" data-onglets="<écran>">`, **avant le câblage générique** — celui-ci boucle sur les `.onglet` porteurs d'un `data-ecran` et ne verrait rien à brancher si la barre était rendue après lui. Chaque section dit elle-même quel écran elle porte, ce qui évite une table de correspondance qui dériverait. Le bouton de profil n'a **pas** de `data-ecran` (le câblage générique l'ignore) et son clic est délégué au document, pour qu'un écran ajouté plus tard ait le sien sans rebranchement. `majOngletProfil` passe pour cette raison par un `querySelectorAll` : il y en a cinq, et un `getElementById` en laisserait quatre au nom du profil précédent. **L'écran de séance n'a volontairement aucune barre** — on ne quitte pas une séance par un onglet.

**Le ressenti se saisit après coup, jamais pendant l'écriture.** La séance est enregistrée par le **thread caméra** (`main.py`, dès le passage en phase terminale), c'est-à-dire avant que l'utilisateur n'ait vu `fin.html` : le statut bascule sur `finished` *puis* la base est écrite. `fin.html` n'a donc pas son `seance_id` à coup sûr au moment du rendu et attend qu'il apparaisse dans `/etat` avant d'activer ses boutons, en renonçant au bout de quelques secondes — cas légitime, une séance sans aucune répétition n'est jamais écrite. Les deux écrans (`fin.html`, `historique.html`) tapent la même route `POST /api/historique/<id>/ressentis` ; `GET` sur la même URL rend le jugement par exercice (réussi ou non, ressenti courant) qui décide des réponses à proposer. Ne pas déplacer cette saisie dans `enregistrer_seance` : elle arriverait toujours trop tôt.

**La cible manuelle.** Un bloc dont la cible s'écarte de ce que le moteur propose est marqué `cible_manuelle` dans `seances_personnalisees.json`, et le moteur ne le touche plus : la valeur est **collante** jusqu'à ce qu'elle soit remise sur le palier proposé. L'utilisateur ne déclare rien, c'est l'écart qui est détecté — `marquer_cibles_manuelles`, appelé par `SessionManager.creer_seance_personnalisee` et `.modifier_configuration`, c'est-à-dire les deux seuls chemins par lesquels une édition d'utilisateur atteint le disque. Ne pas appeler cette fonction depuis `enregistrer_configuration_seance` (la fin de séance) : elle comparerait des valeurs posées par le moteur à un objectif qui a pu changer entre-temps, et marquerait manuel tout ce qui a progressé. **Une séance menée à son terme entérine ses cibles figées** : `enteriner_cibles_manuelles` (`progression/objectifs.py`, jumelle dans `cible_manuelle.js`) lève la marque du profil courant sur tous les blocs, et le badge orange disparaît. Ce n'est pas une annulation — l'historique porte désormais la performance réalisée, donc `ressenti._cible_visee` repart *de cette valeur* : figer était une exception provisoire, la jouer en fait la référence. Une séance **abandonnée** garde sa marque, elle ne prouve rien. Deux pièges. Côté poste fixe, l'appel est dans `SessionManager.marquer_terminee`, et l'écriture du fichier ne doit **pas** rester accrochée à `appliquer_progression()`, qui ne rend presque jamais True (il n'existe plus d'exercice sans barème) — y accrocher la levée reviendrait à ne jamais la faire. Côté application, `terminer()` n'agit que si la séance est locale (`est_seance_locale`) : sur une séance venue du fichier déployé, lever la marque imposerait d'en écrire une copie locale, donc d'échanger un badge contre un autre. Et surtout, **ne jamais appeler `marquer_cibles_manuelles` à cet endroit** : elle *détecte* un écart au palier proposé et effacerait les marques des blocs que la séance n'a pas joués. Le harnais des objectifs la compare (sabotée pour effacer la marque des autres profils, elle sort des divergences).

Le formulaire « Objectifs » de l'accueil **ne saisit plus de commentaire** (le champ ne servait pas), mais il réécrit toujours tous les blocs : le commentaire existant est reporté par un `data-commentaire` sur la ligne, comme le sont déjà l'entrelacement et les repos. Retirer ce report effacerait silencieusement les commentaires à la première sauvegarde. Son bandeau « dernière série » affiche en outre le ressenti déclaré, mais seulement s'il signale un écart : `LIBELLES_RESSENTI` n'y liste ni `ok` ni `dur`, un drapeau neutre n'apprenant rien.

**Un exercice à calibrer n'est jamais une cible manuelle**, et l'oublier produisait un blocage définitif et silencieux. `appliquer_a_blocs` laisse ses valeurs telles quelles — celles du fichier — parce qu'il n'a rien à proposer tant que rien n'est mesuré ; `marquer_cibles_manuelles` les comparait au palier calculé et les déclarait donc **toujours** différentes. Conséquence : enregistrer le formulaire « Objectifs » de l'accueil sans rien modifier figeait tout exercice pas encore testé, et comme `appliquer_a_circuit` écarte les cibles manuelles *avant tout le reste*, son test de calibration ne se déclenchait plus jamais. La fonction prend désormais `sans_donnees` et court-circuite ce cas. Le défaut a vécu longtemps parce que **`marquer_cibles_manuelles` n'était comparée par aucun harnais** : elle l'est maintenant (sabotée, elle sort 257 divergences). Une fonction qui écrit une marque *collante* mérite la même vérification qu'un calcul — c'est même l'inverse : un calcul faux se voit à l'écran, une marque collante ne se voit jamais.

**La marque appartient à un profil, pas à la séance** — les séances étant partagées, `cible_manuelle` stocke une *liste d'identifiants de profils* (`[1, 3]`), et l'ancien booléen se lit encore comme « le profil 1 ». Trois fonctions de `progression/objectifs.py` portent toute la règle : `profils_cible_manuelle` normalise (une valeur d'un format inconnu vaut « personne » — un faux positif fige une cible pour toujours, en silence, alors qu'un faux négatif se voit et se corrige d'un clic), `est_cible_manuelle` répond « est-ce figé *pour moi* ? », `definir_cible_manuelle` calcule la valeur à stocker. D'où la règle d'export : `exporter_blocs` (disque) garde la valeur **brute**, `exporter_configuration` et `catalogue()` (affichage) la **résolvent** en booléen — jamais l'inverse, sinon l'écriture aplatit la donnée des autres.

Cela ne suffit pourtant pas, parce qu'un enregistrement **réécrit tous les blocs** avec ce que le seul profil connecté voit : les marques des autres ne sont pas dans la requête, donc la sauvegarde les effacerait. C'est `enregistrer_seance_personnalisee` — point de passage unique vers le fichier — qui les recolle depuis le disque (`fusionner_cible_manuelle` : les autres profils viennent du disque qui fait autorité pour eux, seul le bit du profil connecté vient de la valeur entrante). Un client n'a ainsi jamais à transporter l'état de quelqu'un d'autre. Limite connue et acceptée : le *drapeau* est par profil, mais la *valeur* figée reste partagée — deux profils qui figent le même bloc à des cibles différentes se marchent dessus, et un renommage de séance écrit sous une clé neuve et perd les marques des autres.

L'accueil affiche un badge orange sur ces blocs, pour que le décrochage reste visible plutôt que silencieux, avec une croix pour le retirer directement (`session.seances.retirer_cible_manuelle`, exposée par `DELETE /api/seances/<nom>/cible-manuelle/<exercice>`) : elle ne fait qu'effacer le flag sur le bloc concerné, sans recalculer de valeur — c'est `appliquer_a_blocs`/`appliquer_a_circuit` qui reprend la main au prochain chargement, comme pour n'importe quel bloc non marqué.

**Piège des éditeurs de séance — à lire avant d'ajouter un mode.** Le formulaire « Objectifs et commentaires » de `accueil.html` ne modifie en apparence que quelques champs, mais il **réécrit tous les blocs de la séance** à l'enregistrement. La règle « ce mode a une cible en secondes, celui-là en répétitions » y était dupliquée cinq fois (deux conditions Jinja, trois conditions JS, plus une dans `editer_seance.html`) : un mode absent de ces listes voyait sa `duree` remise à zéro au premier clic sur « Sauvegarder les objectifs ». La règle est désormais nommée `MODES_DUREE` dans chaque template — **la mettre à jour lors de l'ajout d'un mode à cible temporelle**. Même vigilance sur `editer_seance.html`, dont la liste d'exercices, si elle ne contient pas le nom du bloc courant, laisse le navigateur sélectionner la première option et remplace donc silencieusement l'exercice à l'enregistrement (d'où l'`optgroup` « Inconnu » qui réinjecte un nom orphelin).

Outillage racine : `core/` contient `state.py` (l'état partagé décrit plus haut), `materiel.py` (l'inventaire du profil, décrit plus haut) et `utilisateur.py`, qui ne garde que l'identité connectée — le SQL des profils vit dans `historique/database.py`, et cette séparation est ce qui permettra à « qui est connecté ? » de devenir une session HTTP sans que la couche données bouge ; ses imports de `historique.database` sont différés pour casser le cycle, comme dans `paliers.py`.  `scripts/` regroupe trois genres d'outils, tous hors du chemin critique. Les **vérifications manuelles** (`script_verification_positions.py`, `script_niveaux.py`, `verifier_hud.py`), les **harnais de portage** par paires `generer_*.py` / `comparer_*.mjs` avec leur générateur d'historiques partagé (`historiques_au_hasard.py`), les **migrations ponctuelles** (`renommer_seances.py`, idempotent et `--essai`), et les **exports** : `preparer_demo.py`, qui dérive du Python tout ce que le navigateur relit (catalogue, séances, sons, barèmes, programmes), et `exporter_profil.py`, qui fait passer un historique SQLite dans l'application. `main.py` reste seul fichier `.py` à la racine du dépôt — c'est le point d'entrée, tout le reste vit dans un sous-module dédié.
